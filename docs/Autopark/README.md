# Autopark — автопарк бензовозов (Bemol)

Модуль автоматизирует расчёт заработной платы водителей бензовозов по
нормативному пробегу, контроль маршрутов и расхода дизельного топлива,
планирование поставок нефтепродуктов на АЗС — по ТЗ клиента Bemol
(конспект см. `TZ_BEMOL.md`, исходный docx —
`docs/Planograms/Bemol Автоматизация расчета расходов АВТОПАРКА.docx`).

Изолированный модуль ядра портала: весь код лежит в `modules/autopark/`,
ядро (`core/module_loader.py`) подключает его само под
`/UNA.md/orasldev/autopark`. Общий код (`app.py`, `models/`,
`deploy_oracle_objects.py`) не тронут.

## Oracle-объекты (префикс `FLT_`)

Все объекты установлены собственным DDL модуля
(`modules/autopark/sql/*.sql`), собственным установщиком
(`modules/autopark/scripts/autopark_deploy.py`) — общий
`deploy_oracle_objects.py` их не разворачивает и не знает про них.

Новые колонки: `FLT_STATION_TANKS.MAX_FILL_L / MIN_STOCK_L / MAX_COVER_DAYS`,

`127_flt_supply_seed.sql`. Код: `supply_rules.py` (расчёт без БД),
`supply_store.py`, `supply_controller.py`, `supply_routes.py`,
`templates/_supply_panel.html`. API — `/api/supply/*`.

**Ставка зарплаты с 18.09.2026 — 3,50 лея/км, доплата за рейс 0** (прежние
2,75 + 600 заменены новой редакцией ТЗ). Обе величины — настройки.

### Аудит контура (`AUDIT.md`)

Отдельный вопрос от тестирования: не «работает ли функция», а **можно ли
доверять числу**, которое контур выдал бухгалтеру и руководству.

| Объект | Назначение |
|---|---|
| `audit.py` | Движок: 13 процедур пересчёта по 100 % популяции, оценка контролей по дизайну и операционной эффективности, находки, карта рисков, заключение. **Чистый**: ни одного импорта БД |
| `audit_data.py` | Популяция из двух источников: боевая из Oracle одним подключением и сгенерированная с известным числом заложенных дефектов |
| `excel_bi.py` | Конструктор книг Excel без бизнес-логики: плитки показателей, таблицы, светофор, диаграммы, срезы `DataValidation` |
| `audit_excel.py` | Сборка книги на 13 листов. Показатели — формулами `SUMPRODUCT`/`COUNTIF` по кубам, а не посчитанными числами |
| `audit_controller.py`, `audit_routes.py` | Сводка для панели и выгрузка книги за выбранный период |
| `templates/_audit_panel.html` | Панель «Аудит контура» целиком: разметка и скрипт |
| `scripts/autopark_audit.py` | XLSX + PDF + скриншоты + акт в markdown одной командой |

Два правила оценки, заложенные в движок:

1. **Дефект дизайна ограничивает итог.** Контроль, который легко обойти,
   не получает оценку выше «требует улучшения», даже если в периоде его
   никто не обходил.
2. **«Ноль отклонений из нуля объектов» — это не «эффективен»,** а
   отдельная оценка `RATE_NA` («не тестировался»). В схеме `FLT_TRIPS`
   нет `CREATED_BY` и журнала статусов, поэтому на боевых данных
   контроли FLT-C-09 и FLT-C-10 получают именно её —
   `live_population` не подставляет заглушку вместо отсутствующего
   реквизита.

Пересчёт выполнен **отдельной реализацией формул**: `audit.py` не
вызывает `rules.py` и `supply_rules.py`, хотя считает то же самое. Иначе
совпадение доказывало бы только то, что код равен сам себе.

Самопроверка методики: набор генерируется с известным числом дефектов,
проверка гоняется вслепую, лист «Самопроверка» сравнивает «подложено» с
«найдено». Текущий результат — 616 дефектов по 13 процедурам
воспроизведены полностью, ложных срабатываний нет.

```bash
venv/bin/python modules/autopark/scripts/autopark_audit.py \
  --demo --pdf --png --md docs/Autopark/AUDIT_ACT.md \
  --out docs/Autopark/examples --png-dir modules/autopark/static/docs
```

## Формулы

- **Нормативный пробег** = сумма участков маршрута (пункт загрузки → АЗС1
  → АЗС2 → … → конечный пункт), каждый участок — из `FLT_DISTANCES`.
- **Зарплата** = Норм. пробег × `RATE_PER_KM` (2.75 лея) + Внутренние
  рейсы × `TRIP_BONUS` (600 леев). Импортные рейсы (в т.ч.
  Кишинёв–Констанца–Кишинёв) доплату не получают. DRAFT-рейсы в расчёт
  не входят.
- **Минимальный страховой запас** = среднесуточная реализация × `SAFETY_DAYS`
  (6 дней по умолчанию).
- **Запас в днях** = текущий остаток / среднесуточная реализация.
- **Объём поставки (need_volume)** = `max(0, мин.запас + прогноз реализации
  − остаток − в пути)`, ограничен сверху свободной вместимостью
  резервуара.
- **Расход ДТ**: норматив = норм. пробег × норма расхода / 100;
  отклонение = факт − норматив; превышение — когда `|откл.| / норматив ×
  100 > FUEL_DEVIATION_PCT` (деление на ноль защищено — нулевой норматив
  с положительным фактом сам по себе считается превышением).
- **Отклонение пробега** = факт − норматив; превышение — когда
  `|откл.| > KM_DEVIATION_LIMIT`.

## Деплой Oracle DDL

Собственный установщик модуля (общий `deploy_oracle_objects.py` не
трогает объекты `FLT_*`):

```bash
./venv/bin/python modules/autopark/scripts/autopark_deploy.py --dry-run
./venv/bin/python modules/autopark/scripts/autopark_deploy.py --yes
```

Опция `--only 120|121|122|123|124` запускает только один файл. `--dry-run`
только показывает разбиение на операторы — не доказывает, что схема
встанет; после правок DDL установщик обязательно прогоняется вживую.
Файл `124_flt_gps.sql` содержит `ALTER TABLE ... ADD` — при повторном
запуске это штатно даёт `ORA-01430` («column already exists»), которую
установщик уже держит в общем списке допустимых кодов (не отдельном для
124 — тот же список покрывает все файлы модуля), так что повторный
прогон безопасен (проверено вживую дважды подряд).

## Демо-данные

```bash
./venv/bin/python modules/autopark/scripts/autopark_demo.py --reset
```

Идемпотентный скрипт: заводит справочники (АЗС, бензовозы, водители,
матрица расстояний), суточный учёт остатков за 10 дней, несколько
накладных → автоформирование рейсов → утверждение → факт GPS (рейс с
превышением пробега, рейс с перерасходом ДТ), один ручной
многоостановочный рейс логиста и один импортный рейс
Кишинёв–Констанца–Кишинёв (без доплаты 600 леев — печатается проверка
формулы в отчёте зарплаты). `--reset` чистит только бизнес-данные модуля
(в порядке FK), справочники из seed (`122_flt_seed.sql`) не трогает.

```bash
./venv/bin/python modules/autopark/scripts/autopark_prices.py --yes
```

Дневной ряд по 4 продуктам. Часть данных — реальные предельные цены
ANRE (`SOURCE='ANRE'`), полученные 26.08.2026 через WebFetch с
`anre.md/benzina-95-3-2` и `anre.md/motorina-3-3` (рабочая, живая
страница отдаёт только короткое скользящее окно за последние даты, без
полного архива за 2 года) плюс опорные точки из ретроспективных статей
ANRE за 2025/2026 — только для A95 и DIESEL. Для A92/A98 у ANRE нет
публичной страницы истории вовсе — весь их ряд синтезирован
(`SOURCE='MODEL'`). Модельная часть (остальные даты A95/DIESEL и весь
A92/A98) — дрейф + сезонность + 6 резких скачков ±(8–12)% за 1-2 недели
с частичным откатом (типичный профиль решений ANRE, включая реальный
скачок конца июля 2026 из-за напряжённости на Ближнем Востоке). Загрузка
— один batch `cursor.executemany()` c MERGE по `(PRICE_DATE,
PRODUCT_CODE)` (`AutoparkStore.upsert_fuel_prices`), идемпотентно.

Загружено на боевой ADB 26.08.2026: 2900 строк (4 продукта × 725 дней),
53 дня со скачком >3%, ANRE 40 строк (1.4%), MODEL 2860 строк (98.6%).

## Операционная история за 2 года (для презентации)

```bash
./venv/bin/python modules/autopark/scripts/autopark_history.py --dry-run
./venv/bin/python modules/autopark/scripts/autopark_history.py --reset --yes
```

Генерирует 2024-09-01..2026-08-26: суточный учёт остатков по всем
АЗС/продуктам (баланс `OPEN − SALES + RECEIVED = CLOSE`, недельная
сезонность пт/сб, летний пик бензина / зимний пик дизеля, ±15% шум,
поставка — когда запас падает к ~4 дням), рейсы (1-3 в день, 3
бензовоза × 4 водителя чередуются, маршруты 1-3 АЗС через
`rules.plan_trips`, `NORM_KM` — честно через матрицу `FLT_DISTANCES` и
`rules.route_legs`/`norm_route_km`, статус `APPROVED`, ~4% рейсов с
превышением км-лимита, ~3% с перерасходом топлива, ~1 импортный рейс
Кишинёв–Констанца–Кишинёв в месяц без доплаты). Пишет пакетно через
`cursor.executemany()` (ID для рейсов/стопов/позиций/накладных
предзапрошены `SEQ.NEXTVAL ... CONNECT BY LEVEL`, а не поштучным
INSERT) — иначе тысячи round-trip к облачному ADB заняли бы часы.
`--reset` чистит только операционные таблицы (рейсы/стопы/позиции/
накладные/учёт остатков), справочники и цены не трогает; без `--reset`
скрипт находит рейсы старше 30 дней и отказывается дублировать историю.

Загружено на боевой ADB 26.08.2026 (реальная master-конфигурация: 9 АЗС,
22 пары АЗС×продукт — отсюда 15 950, а не «ровно 26 000», строк учёта,
это тот же порядок величины при фактическом числе резервуаров):
2199 рейсов, 4216 остановок, 4414 позиций/накладных, 15 950 строк учёта
остатков, из них 24 импортных рейса (~1/мес) и 84 рейса (3.8%) с
превышением км-лимита. Сверка зарплаты за один месяц (ручной расчёт
км×2.75 + внутр.рейсы×600 из сгенерированных рейсов против
`AutoparkController.payroll_report`) сошлась 1-в-1 по всем 4 водителям.

## Отчётность XLSX/PDF (`autopark_reports.py`) и телеграм-бот (`autopark_bot.py`)

```bash
# пакет из 6 отчётов (ТЗ §14) в Excel и PDF
./venv/bin/python modules/autopark/scripts/autopark_reports.py \
    --report all --date-from 2026-07-01 --date-to 2026-07-31 \
    --xlsx --pdf --out docs/Autopark/examples

# бот логиста: команды локально, без Telegram API
./venv/bin/python modules/autopark/scripts/autopark_bot.py \
    --dry-run /stock "/pay 2026-07" "/control 7"
```

Шесть отчётов (`driver|truck|station|summary|management|prices`) собирает
`modules/autopark/reports.py` по единому контракту
`{title, period, columns, rows, totals, notes}` поверх существующих
методов store/controller; XLSX — openpyxl, PDF — деловой HTML +
`soffice --headless --convert-to pdf`. Готовые примеры (июль 2026 + YTD)
— `docs/Autopark/examples/`. Подробно — `REPORTS.md`.

Телеграм-бот (long polling, чистый urllib, токен `AUTOPARK_TG_TOKEN` и
белый список `AUTOPARK_TG_CHAT_IDS` в `.env`): команды `/stock`, `/plan`,
`/trips`, `/pay`, `/control`, `/prices` и пуш-мониторинг `--monitor`
(запас ниже страхового, превышение лимитов; антидубль). Без белого
списка не отвечает никому. Подробно — `TELEGRAM_BOT.md`.
