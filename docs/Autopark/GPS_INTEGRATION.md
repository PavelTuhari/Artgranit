# GPS-прослойка Autopark — как подключить провайдера

Модуль Autopark разделяет две вещи, которые в первых версиях подобных
систем обычно смешивают: **откуда берётся координата бензовоза** и **что
система с этой координатой делает** (карта, replay, сверка факт/норма).
Первое — заменяемая прослойка (`modules/autopark/gps.py` + таблицы
`FLT_GPS_PROVIDERS`/`FLT_GPS_TRACKS`), второе — код, который не меняется
вне зависимости от того, кто прислал точку: симулятор сегодня или
настоящий трекер завтра.

## Контракт прослойки

Любой источник точек — симулятор, реальный трекер, ручная загрузка —
попадает в систему одним и тем же вызовом:

```
POST /api/gps/ingest
{
  "provider": "SIM",       -- CODE из FLT_GPS_PROVIDERS
  "trip_id": 2207,
  "points": [
    {"ts": "2026-08-26T08:00:00", "lat": 47.010932, "lon": 28.849170, "speed": 55.2},
    ...
  ]
}
```

Обработка (`AutoparkController.gps_ingest` → `modules/autopark/gps.py::normalize_points`):

1. `provider` ищется в `FLT_GPS_PROVIDERS` по `CODE` — оттуда же берётся
   `KIND` (`SIM`/`HTTP_PUSH`/`HTTP_PULL`); клиент не выбирает `KIND`
   сам, это защита от того, что чужой провайдер пришлёт точки под чужим
   типом.
2. Каждая точка проверяется независимо: `ts` обязателен и разбирается
   как ISO-дата, `lat`∈[-90,90], `lon`∈[-180,180], `speed`
   необязателен. Невалидные точки не рушат запрос — они отбрасываются,
   а причина попадает в `warnings` ответа.
3. Валидные точки пишутся в `FLT_GPS_TRACKS` пакетно
   (`cursor.executemany`), привязанные к `trip_id` и `provider_id`.

Ровно этот контракт используют:

* **симулятор** (`modules/autopark/scripts/autopark_gps_sim.py --live`) —
  играет роль внешнего устройства, шлёт HTTP на `/api/gps/ingest` с
  `provider: "SIM"`;
* **replay** (`AutoparkController.gps_replay` → `POST /api/gps/replay`) —
  внутренний путь, который тоже в итоге кладёт точки через
  `AutoparkStore.insert_track_points` (тот же путь записи, что и
  ingest, просто без прохода через HTTP и normalize — точки уже
  посчитаны интерполяцией);
* **будущий реальный провайдер** — подключается без единой строки в
  `store.py`/`controller.py`/`routes.py`.

## Как подключить настоящего GPS-провайдера

### Способ 1 — HTTP_PUSH (провайдер сам шлёт данные системе)

Ровно тот же путь, что у симулятора:

1. Завести строку в `FLT_GPS_PROVIDERS`: `CODE` (например `WIALON`,
   `RUPTELA`), `NAME`, `KIND='HTTP_PUSH'`.
2. Выдать провайдеру учётные данные портала (или отдельный сервисный
   логин — вне рамок первой очереди) и адрес
   `POST /UNA.md/orasldev/autopark/api/gps/ingest`.
3. Провайдер (или переходник рядом с ним) переводит свой формат в
   `{"provider": "<CODE>", "trip_id": ..., "points": [{"ts","lat","lon","speed"}]}`
   и шлёт пачками. `trip_id` провайдер не знает сам — сопоставление
   "устройство/номер машины → активный рейс сегодня" делает переходник,
   опираясь на `GET /api/trips?date_from=...&date_to=...` (в нём есть
   `truck_id`) — этот шаг НЕ входит в `gps.py`/`store.py`, он specific
   для конкретного провайдера и живёт в самом переходнике.

Если формат провайдера отличается от `{"track"/"device": [...]}` —
единственное место, которое придётся расширить, это ветка внутри
`gps.normalize_points()` по `provider_kind`/`KIND`: остальной код
(store, controller, routes, UI) не знает о формате вообще.

### Способ 2 — HTTP_PULL (система сама опрашивает провайдера)

1. Завести строку в `FLT_GPS_PROVIDERS` с `KIND='HTTP_PULL'`.
2. Написать отдельный скрипт по образцу
   `autopark_gps_sim.py --live` (или cron-задачу), который вместо
   генерации точек локально — ходит в API провайдера, получает текущие
   координаты бензовозов, преобразует в тот же формат `points` и шлёт
   их **тем же** `POST /api/gps/ingest` с `provider` = код провайдера.
   Система-потребитель (`gps_ingest`) не отличает push от pull — разница
   только в том, кто инициирует HTTP-запрос.

В обоих случаях реального провайдера подключают, ДОБАВИВ строку в
регистр и (при новом формате) ветку в `normalize_points` — не трогая
`routes.py`/UI и не переписывая существующий путь симулятора.

## Как работает симулятор (`autopark_gps_sim.py`)

Скрипт **не импортирует** `modules.autopark.store` и не открывает
соединение с Oracle напрямую — он логинится по HTTP (форма `/login`,
cookie-сессия) и работает исключительно через тот же публичный API, что
будет использовать реальный трекер. Единственный внутренний импорт —
`modules.autopark.gps` (чистая геометрия/интерполяция без БД) — нужен,
чтобы понимать, где по времени должна быть точка на маршруте; сама
точка уходит в систему только через `/api/gps/ingest`.

* `--live [--interval N] [--duration N]` — раз в `N` секунд (по
  умолчанию 10) тянет список сегодняшних рейсов (`GET /api/trips`) и
  геоточки (`GET /api/gps/geo`), строит профиль движения тем же
  `gps.interpolate_route`, что использует `AutoparkController.gps_positions`
  для live-карты, и шлёт накопившиеся с прошлого тика точки через
  `POST /api/gps/ingest`.
* `--replay-recent N` — находит N последних не-DRAFT рейсов
  (`GET /api/trips` окном назад по датам) и для каждого вызывает
  `POST /api/gps/replay` — это и есть «подключение источника треков
  вместо тестового набора фактов»: `FLT_TRIPS.FACT_KM` рейса
  заменяется длиной сгенерированного (интерполяция + шум GPS-приёмника
  ±150 м) трека, а не остаётся числом из демо/истории.
  Предпочитает настоящий HTTP (тот же контракт, что и `--live`); если
  `--base-url` не отвечает, скрипт честно печатает это в лог и
  переключается на `app.test_client()` — разрешённый резерв для
  проверки цепочки без поднятого процесса Flask, а не тихая подмена
  бизнес-пути.

## Формулы

* `haversine_km(lat1, lon1, lat2, lon2)` — расстояние по прямой (большой
  круг), используется и для длины сохранённого трека, и внутри
  интерполяции профиля движения.
* `interpolate_route(geo_points, depart_ts, avg_speed_kmh, stop_minutes)`
  — строит временной профиль по ломаной LOAD → STATION... → END:
  равномерное движение между точками + стоянка `stop_minutes` на каждой
  промежуточной точке. Используется и live-позициями (`gps_positions`,
  ничего не пишет в БД, считает на лету), и replay (`gps_replay`,
  сохраняет получившиеся точки).
* `position_at(profile, ts)` — линейная интерполяция позиции в момент
  `ts`: до выезда — старт (`started=False`), после финиша — конец
  (`finished=True`), внутри стоянки — стоим на месте.
* Сравнение факт/норма (`GET /api/gps/track`) — `track_km` (haversine по
  сохранённым точкам) против `NORM_KM` (расчёт по матрице расстояний,
  как и раньше). Разница закономерно отрицательна: реальная дорога
  всегда длиннее прямой между точками, это не ошибка расчёта.

## Допущения первой очереди

1. Выезд симулируется в 08:00, средняя скорость 55 км/ч, стоянка на АЗС
   25 минут — константы `GPS_DEPART_HOUR`/`GPS_AVG_SPEED_KMH`/
   `GPS_STOP_MINUTES` в `modules/autopark/controller.py`; их значение
   отражает первую очередь, не физику конкретного грузовика.
2. `gps_positions()` ничего не пишет в БД и не хранит историю — это
   именно "где сейчас", а не журнал позиций; постоянный трек живёт
   только в `FLT_GPS_TRACKS` (через ingest/replay).
3. Сопоставление "устройство реального провайдера → `trip_id`" — задача
   переходника конкретного провайдера, не входит в `gps.py`/`store.py`:
   схема ждёт уже готовый `trip_id` на входе `POST /api/gps/ingest`.
