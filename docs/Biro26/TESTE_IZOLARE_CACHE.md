# Тесты каталога и общий кэш: почему шесть проверок падали вместе

**12.09.2026**

## Что наблюдалось

Шесть тестов каталога (`get_products_stock`, `get_product_tree`,
`get_product_brands`) падали **вместе**, а поодиночке проходили. После
запуска приложения на живой базе падали и подавно.

## Причина

Кэш каталога общий для всех процессов: значения пишутся не только в
память, но и в файл во временной папке — чтобы второй воркер gunicorn не
платил заново за тяжёлые запросы (`_CACHE_DIR` в
`models/biro26_oracle_store.py`). В бою это правильно.

В тестах это источник ложных падений: один тест кладёт в кэш свой ответ,
следующий получает его **вместо обращения к подставной базе** — и
проверяет запрос, которого не было. `fake.last_sql` оказывается `None`,
тест падает с `TypeError`.

Файлы кэша переживают и прогон, и перезапуск: лежат в `$TMPDIR/biro26_cache`.

## Решение

`tests/conftest.py` — автоматическая фикстура, очищающая кэш (и память, и
диск) до и после каждого теста. Продуктивный код не тронут.

## Заодно: устаревшие сверки SQL

Ещё пять тестов сверяли **написание** запроса — `TIP='P'`,
`g.GRUPA=:grupa`, `MIN(BARCODE)`. Запрос переписали (пагинация через
`ROWNUM`, фильтры ушли в подзапрос по `BIRO26_GOODS`, марок стало
несколько — `BRAND IN (:br0)`), и проверки развалились, хотя поведение
не менялось.

Проверено, что поведение на месте:

| Что проверяли | Как выглядит теперь | Работает |
|---|---|---|
| фильтр по группе | `GRUPA = :grupa` в подзапросе | да |
| фильтр по марке | `BRAND IN (:br0)` | да |
| поиск по штрихкоду | `UNION SELECT COD FROM TMS_MPT_BARCODE` | да |
| штрихкод в выдаче | `MIN(b.BARCODE)` | да |

Сверки переведены со написания на смысл: пробелы нормализуются, псевдоним
таблицы не важен.

## Отдельно — защита от дублей

Тест требовал `ROW_NUMBER() OVER (PARTITION BY g0.COD_UNIVERS)`. Этой
конструкции больше нет, и это выглядело как потеря защиты от дублирования
строк.

Проверено на живой базе: **дублей нет**. Выборка идёт по `TMS_UNIVERS`, а
фид подсоединяется по `COD_UNIVERS`, который в нём уникален —
200 строк дали 200 товаров. Повторяется только строка с пустым
`COD_UNIVERS` (37 376 незагруженных позиций), а `NULL` не соединяется
никогда.

Защита осталась, но держится **устройством запроса**, а не оконной
функцией. Тест теперь проверяет ключ соединения.

## Что осталось красным

`test_timeout_kills_the_worker_and_the_pool_recovers` — падает примерно
раз из трёх прогонов. Причина: фоновые нити приложения (прогрев кэшей)
делят общий пул воркеров с тестом, и ответ на «зависший» вызов иногда
приходит от чужого запроса. Тест выдерживает один повтор, но полное
решение — изолировать пул на время теста, а это уже правка самого пула.
