# Учёт заказов на забалансовых счетах

Реализовано 22.08.2026. Заказ регистрируется на забалансовом счёте с
**пассивным** смыслом, отгрузка его закрывает. В универсальном отчёте любой
заказ виден положительным числом.

## Счета (группа 9***)

| Счёт | Назначение | Смысл | Как виден в отчёте |
|---|---|---|---|
| **9301** | Заказы клиентов | пассивный | заказ — положительное число в **Ct** |
| **9302** | Склады поставщиков | активный | остаток — положительное число в **Dt** |

Счёт 9992 уже занят под заявки на возврат (`ORDER_CONT` документа 1235) —
поэтому для заказов взят **9301**, он был свободен: ни в конфигурации, ни в
проводках не встречался.

Номер счёта **не зашит в код**: он лежит свойством `ORDER_CONT` у действия и
приходит в процедуру bind-переменной `:ini_order_cont`. Поменять счёт можно
из uniConf, не трогая PL/SQL.

## Как это работает

```
Счёт на оплату (SYSFID 12280)          Накладная FF (SYSFID 1228)
   действие «Generare formule            действие «Inchiderea
    comanda»                              comenzii»
        │                                       │
        ▼                                       ▼
   Ct 9301  ← заказ зарегистрирован     Dt 9301  ← заказ закрыт
   (пассив, видно в Ct)                 (актив, гасит остаток)
```

Связь заказа и отгрузки — через `VMDB_ST201M.CTNRDOC`: при создании накладной
из счёта (`yimc_inventar.create_doc_1228_form_12280`) номер накладной пишется
в шапку счёта. Процедура закрытия идёт по этой ссылке в обратную сторону.

Аналитика в проводке одинаковая с обеих сторон, чтобы остаток гасился точно:
товар (`sc`), подразделение (`dep`), клиент (`sc1`), номер заказа (`nrdoc`).

## Пакет `y_ai_BIRO26_comenzi`

| Процедура | Что делает |
|---|---|
| `order_gfc(p_nrdoc, p_cont)` | по счёту — Ct-проводки на 9301 по строкам |
| `order_close(p_nrdoc, p_cont)` | по накладной — Dt-проводки, закрывающие заказ |
| `order_sold(p_nrdoc, p_cont)` | сколько по заказу осталось неотгруженным |

Проводки пишутся в `VMDB_CMI` **одной стороной** — так и положено
забалансовым счетам (образец: `Yimc_Tvr_Docs.doc_tvr_return_order_gfc`).

Перегенерация безопасна: процедура удаляет только свои строки по своему
счёту (`WHERE nrdoc=… AND ct=p_cont`), остальные проводки документа не
трогает. Поэтому у действий намеренно **не** выставлены
`DELETEALLFCFROMCM` / `DELETEFCFROMCM` — они стирают все формулы документа.

## Проверено на живых данных

Счёт 339 (1 строка, 230 лей) и созданная из него накладная 340:

```
order_gfc(339)   → Ct 9301  товар 207930, клиент 160415, 230 лей
order_close(340) → Dt 9301  та же аналитика, ссылка на заказ 339
order_sold(339)  → 0        заказ закрыт полностью
```

Тестовые проводки после проверки удалены.

## Ловушка: формат даты сессии

Триггер `YTRG_TMDB_CM_NOT_UPD` содержит `v_date date := '01.01.2014'` —
неявное преобразование строки в дату. В сессии с американским NLS
(`NLS_DATE_FORMAT=DD-MON-RR`) любая вставка в `VMDB_CMI` падает с
**ORA-01843: not a valid month**.

Это не дефект нашего кода: в родном клиенте UNA формат сессии румынский и всё
работает. Но при вызове из скриптов и из Python-воркера Biro26 нужно сначала:

```sql
ALTER SESSION SET NLS_DATE_FORMAT='DD.MM.YYYY';
```

## Что спроектировано, но не реализовано

Владелец описал более широкую схему; сделана её первая часть. Осталось:

1. **Стоки поставщиков на 9302** (активный смысл) — когда поставщики дадут
   доступ к своим остаткам. Аналитика: товар в `sc`, склад поставщика в
   `dep`, сам поставщик в `sc1`. Тогда в универсальном отчёте рядом встанут
   их остаток в Dt и наши заказы в Ct.
2. **Разные склады одного поставщика** — уже покрывается полем `dep`, но
   нужен справочник складов поставщика и правило, как их различать.
3. **Проводки закупки и продажи товара** при отгрузке — сейчас действие
   закрывает только забалансовый заказ; балансовые проводки формируются
   штатным механизмом документа.
