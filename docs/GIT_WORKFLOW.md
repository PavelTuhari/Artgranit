# Git-концепция Artgranit: много сессий ИИ, один репозиторий, ничего не теряется

Владелец, 02.09.2026: *«так всё разрабатывай, чтобы никто не мог случайно
стереть! и все push commit на git!»* — после того как код mTLS-источников
TBControl пропал без следа. Этот документ — как именно это обеспечивается.
Краткая версия для агентов — [`AGENTS.md`](../AGENTS.md) в корне.

## 1. Почему терялось

| Причина | Что происходило |
|---|---|
| **Все сессии в одном каталоге** `/Users/pt/Projects.AI/Artgranit` | сессия A редактирует файл, сессия B через час пишет тот же файл из своей устаревшей копии в контексте — версия A исчезает; hook честно коммитит «auto: update» обеими, конфликта нет |
| **Hook привязан к одному каталогу** (`cd /Users/pt/Projects.AI/Artgranit`) | сессии в worktree (`.claude/worktrees/*`) писали файлы, а hook пытался добавить их в *другой* репозиторий → молча ничего не коммитил |
| **Ветка = «где сейчас стоит каталог»**, а не «чья это работа» | на `feat/autopark-module` осели TBControl, OTRS, MyLoyalWalletCard, SDA… чужой `git checkout`/`stash`/`restore` в общем каталоге уносил чужие правки |
| **Логика в общих файлах** (`app.py`, `controllers/`, `templates/`) | один `Write` целого файла = потеря всего, что туда добавили другие |

## 2. Четыре правила, которые это закрывают

### Правило A. Одна задача = один worktree = одна ветка

Ни одна сессия **не работает в `/Users/pt/Projects.AI/Artgranit` напрямую**.
Каждая задача получает свой каталог и свою ветку:

```
/Users/pt/Projects.AI/Artgranit            ← только main, только для merge/деплоя
/Users/pt/Projects.AI/Artgranit-<ключ>     ← worktree задачи, ветка feat/<ключ>
```

Создаётся одной командой (раздел 4). Худшее, что может сделать чужая сессия —
испортить *свой* каталог. Общий каталог держится на `main` и обновляется
только `git pull --ff-only` + merge готовых веток.

### Правило B. Код задачи живёт только в своих путях

Модуль — целиком в `modules/<ключ>/` (правило №1 CLAUDE.md), документация —
в `docs/<Модуль>/`, тесты — `tests/test_<ключ>.py`, мобильное/внешнее —
`ios/<Имя>/`, `scripts/<ключ>_*.py`. В общих файлах — **ничего**, максимум
одна строка вызова. Тогда две ветки физически не могут конфликтовать: у них
нет общих файлов. Проверка: `git diff --name-only main HEAD` показывает только
свои пути.

### Правило C. Каждый шаг — commit + push, автоматически

Hook `PostToolUse` на `Write|Edit` (`.claude/settings.local.json`) коммитит
и пушит **в репозиторий того файла, который изменён** (`git -C <каталог файла>`),
а не в фиксированный каталог. Работает и в worktree. Агент дополнительно
после каждого законченного шага делает осмысленный коммит своих путей, а
перед сдачей проверяет:

```bash
git log --oneline origin/$(git branch --show-current)..HEAD   # пусто
```

Без push работа существует в одном каталоге на одном диске — это не работа.

### Правило D. Общие файлы — только через merge, никогда через Write

`app.py`, `deploy_oracle_objects.py`, `CLAUDE.md`, `README.md`, `templates/*`
(старых модулей), `controllers/*`, `models/*` (общие) — редактируются
**только точечным `Edit`** и только после `git log --oneline -3 -- <файл>`.
Если там свежие коммиты другой сессии — сначала `git pull`, потом правка.
Полная перезапись (`Write`) общего файла запрещена.

## 3. Жизненный цикл ветки

```
new_module <ключ>  →  feat/<ключ> в Artgranit-<ключ>  →  работа (hook пушит)
      →  тесты изоляции зелёные  →  merge в main (fast-forward или PR)
      →  деплой из main  →  git worktree remove Artgranit-<ключ>
```

1. **Старт:** `python scripts/new_module.py <ключ> "<Название>"` (раздел 4).
2. **Работа:** только в `Artgranit-<ключ>/`. Подтягивать `main` в ветку —
   `git merge main` (не rebase: rebase переписывает то, что уже запушено).
3. **Готово:** `pytest tests/test_<ключ>.py` зелёный, изоляция подтверждена.
4. **Merge:** в общем каталоге `git checkout main && git pull --ff-only &&
   git merge --no-ff feat/<ключ> && git push`. Конфликтов быть не должно —
   если есть, значит нарушено правило B, чинить в ветке, не в main.
5. **Деплой** только из `main` (`deploy_to_remote.sh` / точечный патч).
6. **Уборка:** `git worktree remove ../Artgranit-<ключ>`; ветку не удалять
   до деплоя и проверки прода.

Долгоживущие ветки (`feat/autopark-module` с 15 чужими коммитами) — это
симптом: чем дольше ветка не влита, тем больше на ней чужого. Влить, как
только модуль работает.

## 4. Команда «новый проект-модуль» — одной строкой

Владелец говорит ИИ: *«создай модуль автомойки, ключ carwash»*. Агент выполняет:

```bash
python scripts/new_module.py carwash "Автомойка" --prefix CWS --icon 🚿
```

Скрипт (`scripts/new_module.py`) делает всё, что требует CLAUDE.md, и ничего
сверх:

| Шаг | Результат |
|---|---|
| worktree + ветка | `../Artgranit-carwash` на `feat/carwash` от свежего `main` |
| пакет модуля | `modules/carwash/{__init__,routes,controller,store,rules}.py`, `module.json`, `templates/carwash.html`, `sql/`, `scripts/carwash_deploy.py` |
| тесты | `tests/test_carwash.py` — два теста изоляции (app.py и общий установщик не тронуты) + заготовка |
| документация | `docs/Carwash/README.md`, `docs.json` — хаб подхватывает сам |
| git | первый коммит `carwash: каркас модуля` и push ветки |

После этого агент работает **только в `Artgranit-carwash/`**. Ядро
(`core/module_loader.py`) подключит модуль само — в `app.py` ничего не
вписывается, в меню он появится автоматически (`module.json`).

Слэш-команда для владельца: `/new-module carwash Автомойка`
(`.claude/commands/new-module.md`).

## 5. Если что-то всё-таки пропало

1. `git log --all --oneline -S"<уникальное имя из кода>"` — искать по всем
   веткам, включая `claude/*` и worktree-ветки.
2. `git reflog` в каталоге, где работала сессия.
3. Прод: `ssh ubuntu@92.5.3.187 'cd artgranit && grep -rn "<имя>" .'`.
4. Транскрипты: `grep -l "<имя>" ~/.claude/projects/*/*.jsonl`.
5. Документация `docs/<Модуль>/*.md` — по ней восстанавливать заново.
   Так восстанавливаются mTLS-источники TBControl (09.2026).

## 6. Что запрещено

- работать в `/Users/pt/Projects.AI/Artgranit` не на `main`;
- `git checkout <другая ветка>` / `git stash` / `git restore` в общем каталоге;
- `git push --force`, `rebase` запушенных веток;
- `Write` целиком общего файла;
- коммитить чужие незакоммиченные изменения «заодно» (только свои пути);
- откатывать или вырезать чужие коммиты из ветки.
