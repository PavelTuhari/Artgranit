## 1. Мультиязычность

Модуль спроектирован трёхъязычным с первого релиза. Схема хранения:

1. **Справочники и master-data** — три колонки на сущность:
   `NAME_RU` / `NAME_RO` / `NAME_EN` (для задач и документов — `TITLE_*`,
   для уведомлений — `TEXT_*`, для истории — `SUMMARY_*`, для настроек — `DESCR_*`).
2. **Строки интерфейса** — словарь `PLG_I18N` (`MSG_KEY`, `SCOPE`, `TEXT_RU`, `TEXT_RO`, `TEXT_EN`).
   Это единственный источник правды для подписей UI; в шаблоне нет захардкоженных переводов.
3. **Реестр языков** — `PLG_REF_LANGS` (`ru` / `ro` / `en`, флаг `IS_DEFAULT`).

Контроллер получает язык параметром `?lang=ru|ro|en` (неизвестный код → `ru`) и методом
`_localize()` добавляет к каждой строке сводный ключ без суффикса: `name_ru/name_ro/name_en`
→ `name` на выбранном языке (fallback на русский, если перевод пуст). Исходные языковые
колонки **сохраняются в ответе** — они нужны формам, где оператор правит все три языка сразу.

Во избежание коллизий представления отдают локализуемые названия справочников под
именами `*_NAME_RU/RO/EN` (`STATUS_NAME_*`, `ZONE_TYPE_NAME_*`, `FIXTURE_TYPE_NAME_*`,
`PROMO_TYPE_NAME_*`, `TASK_TYPE_NAME_*`, `DOC_TYPE_NAME_*`), чтобы не затирать колонку-код
(`STATUS`, `ZONE_TYPE`, …).

**Как добавить четвёртый язык:**
1. `ALTER TABLE` — добавить `NAME_XX` / `TEXT_XX` / `TITLE_XX` / `SUMMARY_XX` / `DESCR_XX`.
2. Добавить колонку в представления `V_PLG_*`.
3. `INSERT INTO PLG_REF_LANGS`.
4. В контроллере расширить `PlanogramController.LANGS`.
Шаблон подхватит новый язык автоматически: переключатель строится из `PLG_REF_LANGS`.

### Демо-режим (доступ без входа)

Страница отдаётся и неаутентифицированному посетителю — иначе живые ссылки из
презентации и документации упирались бы в форму входа. В этом случае шаблон
получает `plg_demo=True`, показывает полосу «Демо» и гасит действия записи.

Ограничение держится **на сервере**, а не на кнопках. `before_request`-хук
`_plg_block_anonymous_writes` в `app.py` отклоняет любой запрос к `/api/plg/*`
с методом, отличным от `GET`/`HEAD`/`OPTIONS`, если сессия не аутентифицирована:

```json
HTTP 403 {"success": false, "demo": true, "error": "Демо-режим: изменение данных…"}
```

Хук выбран вместо декоратора на каждом маршруте сознательно: маршрутов записи
больше шестидесяти, и любой новый, добавленный позже, автоматически попадёт
под то же правило — забыть повесить декоратор невозможно.

В шаблоне за это отвечают три вещи: константа `DEMO`, регулярное выражение
`WRITE_RE` (по имени inline-обработчика отличает изменяющие действия от
просмотровых) и `MutationObserver`, который гасит кнопки в разделах,
дорисованных асинхронно. Просмотровые действия — навигация, смена языка
и периода, карточка планограммы, карточка поставщика, просмотр BPMN-схемы —
остаются рабочими.

Данные модуля — синтетический тестовый набор, поэтому открытый просмотр
не раскрывает коммерческой информации. Контур эксплуатации (`TBC_*`) под это
правило **не** попадает: там реальные адреса, серийные номера и IP-адреса
оборудования, и он остаётся закрытым входом.

## 4. API

Все методы принимают `?lang=ru|ro|en`. Ответ: `{"success": bool, "data": …, "lang": "…"}`
или `{"success": false, "error": "…"}`.

GET  /api/plg/langs
GET  /api/plg/i18n                     → {msg_key: text}
GET  /api/plg/refs                     → langs, zone_types, fixture_types, plg_statuses,
                                          task_types, promo_types, doc_types, categories
GET  /api/plg/stores
```

### Дашборд, карта, аналитика
```
GET  /api/plg/dashboard?store_id=&days=      → stats, metrics, categories, promos, notifications
GET  /api/plg/map?store_id=                  → store, zones, fixtures
GET  /api/plg/analytics?store_id=&days=      → zones, categories, metrics
```

### Зоны, оборудование, товары
```
GET|POST          /api/plg/zones
PUT|DELETE        /api/plg/zones/<id>
GET|POST          /api/plg/fixtures            (GET: ?store_id=&zone_id=)
PUT|DELETE        /api/plg/fixtures/<id>
GET|POST          /api/plg/products            (GET: ?category_id=&q=)
PUT|DELETE        /api/plg/products/<id>

### Планограммы
```
GET               /api/plg/planograms?store_id=&status=&zone_id=
GET               /api/plg/planograms/<id>            → заголовок + items + history
POST              /api/plg/planograms
PUT|DELETE        /api/plg/planograms/<id>

### Акции, задачи, документы, уведомления
```
GET|POST          /api/plg/promos                (GET: ?store_id=&active=1)

GET|POST          /api/plg/tasks                 (GET: ?store_id=&status=open|new|…)

# Часть II. Тестовое окружение и прогноз заказов

Вторая очередь модуля: генератор тестовых данных сети магазинов и
прогнозирование заказов с админкой конфигурирования.

## 9. Изоляция тестовых данных: наборы (PLG_DATASETS)

Oracle общая с боевыми контурами, поэтому тестовые данные живут в **именованных
наборах**. Набор проставляется только на корневых сущностях —
`PLG_STORES.DATASET_ID` и `PLG_PRODUCTS.DATASET_ID`; всё остальное (зоны,
оборудование, планограммы, акции, задачи, метрики, продажи) достижимо через
магазин и удаляется каскадом вместе с ним.

* Набор `DEMO` содержит исходные демо-данные и помечен `IS_PROTECTED = 1` —
  генератор и кнопка удаления его не трогают.
* Один и тот же `SEED` при одинаковых параметрах даёт **идентичные** данные:
  весь случайный поток идёт из `random.Random(seed)`.
* Удаление набора идёт в жёстком порядке: планограммы → магазины → товары →
  сам набор. Планограммы не каскадируются от магазина (обычный FK), а позиции
  выкладки ссылаются на товар без каскада.

Раздел админки: **Генератор данных** (`/UNA.md/orasldev/planograms`).

## 10. Алгоритмы генерации (PLG_GEN_ALGORITHMS)

Пять этапов, каждый достраивает свой слой поверх предыдущего. Порядок важен:
акции создаются до спроса (иначе не на что накладывать promo-аплифт),
метрики — после продаж (иначе не из чего считать).

| # | Код | Что делает |
|---|---|---|
| 1 | `network` | Магазины четырёх форматов (гипермаркет / супермаркет / дискаунтер / у дома) с торговым залом: зоны по формату, стеллажи и холодильное оборудование, координаты карты |
| 2 | `assortment` | Ассортиментная матрица: SKU по категориям с ценами, габаритами, кратностью заказа, сроком поставки и ABC-классом |
| 3 | `events` | Промо-кампании с привязкой к товарам и зонам, планограммы с позициями выкладки, задачи мерчандайзинга, уведомления |
| 4 | `demand` | **Ядро**: суточные продажи по каждому SKU в каждом магазине |
| 5 | `traffic` | Проходимость зон и дневные показатели магазина |

### Модель спроса

```
qty = base × yearly(t) × weekday(t) × trend(t) × promo(t) × noise
```

* `base` — от ABC-класса SKU и формата магазина (нормировка по трафику формата);
* `yearly` — синусоида с амплитудой и фазой пика **своей для каждой категории**
  (алкоголь пикует в декабре, напитки — летом, здоровое питание — в январе);
* `weekday` — недельный профиль торговли (пт-сб пик, вт провал);
* `promo` — аплифт `1.35 + скидка × 2.6`, применяется только в дни действия акции;
* `noise` — гауссов множитель;
* поверх — события **out-of-stock** и простая (s,S) политика запаса: при падении
  остатка ниже точки заказа приходит партия, кратная коробу.

Ассортимент магазина зависит от формата (гипермаркет — вся матрица, «у дома» —
30 %), поэтому сеть выглядит неоднородно, как настоящая.

Метрики этапа `traffic` **выводятся из продаж**, а не генерируются независимым
шумом: выручка = сумма продаж дня, покупатели = выручка / средний чек,
трафик = покупатели / конверсия. Поэтому дашборд и аналитика согласованы
с историей спроса.

Реализация: [models/plg_datagen.py](../../models/plg_datagen.py).
Прогон идёт в фоновом потоке, прогресс пишется в `PLG_GEN_RUNS` и опрашивается
админкой раз в 2.5 с; прогон можно остановить кнопкой.

## 11. Алгоритмы прогноза заказов (PLG_FCT_ALGORITHMS)

| Код | Алгоритм | Параметры | Мин. история |
|---|---|---|---|
| `sma` | Скользящее / взвешенное скользящее среднее | `window`, `weighted`, `exclude_oos` | 21 дн. |
| `ses` | Простое экспоненциальное сглаживание | `alpha`, `exclude_oos` | 28 дн. |
| `holt_winters` | Тройное сглаживание: уровень + тренд + сезонность | `alpha`, `beta`, `gamma`, `season`, `damped`, `exclude_oos` | 42 дн. |
| `promo_reg` | Базовая линия по дням без акций × promo-uplift × индекс трафика | `baseline_window`, `use_promo`, `use_traffic`, `uplift_cap`, `exclude_oos` | 35 дн. |

Всё считается чистым Python/SQL — новых зависимостей не добавлено.

Два инженерных решения, которые стоит знать:

1. **`exclude_oos`**: дни out-of-stock — это не спрос, а его отсутствие. Если их
   не обработать, модель систематически занижает уровень. Такие дни заменяются
   медианой положительных продаж.
2. **Индекс трафика в `promo_reg`** — это *изменение* трафика зоны (последняя
   неделя против всего окна), а не его абсолютный уровень. Абсолютный уровень
   уже зашит в базовую линию SKU; умножение на него double-count'ит, и поскольку
   категории с высоким трафиком держат больше SKU, средний по товарам индекс
   уезжает выше единицы. На первой реализации это давало +35 % систематического
   завышения прогноза.

### Модель = алгоритм + конфигурация

`PLG_FCT_MODELS` хранит именованные конфигурации: параметры алгоритма плюс
настройки заказа (горизонт, уровень сервиса, срок поставки, округление до короба).
Одному алгоритму может соответствовать несколько моделей — они сравниваются
на backtest. Форма конфигуратора в админке **строится автоматически** из
`PLG_FCT_ALGORITHMS.PARAMS_SCHEMA` (тип поля, границы, подписи на трёх языках),
поэтому новый параметр алгоритма появляется в UI без правки шаблона.

### Из прогноза в заказ

```
safety_stock = z(service_level) × sigma × sqrt(lead_time)
order_qty    = max(0, спрос_за(horizon + lead_time) + safety_stock − остаток)
```
с округлением вверх до `PLG_PRODUCTS.ORDER_MULTIPLE`. Квантиль `z` берётся
линейной интерполяцией по таблице — без scipy.

### Режимы прогона

* `forecast` — прогноз вперёд от последней даты истории, `QTY_ACTUAL` пуст;
* `backtest` — origin отодвигается на горизонт назад, прогноз сравнивается
  с фактом. Так считаются MAPE / MAE / RMSE / bias и модели сравниваются
  между собой на одних данных (кнопка «Сравнить модели на backtest»).

Реализация: [models/plg_forecast.py](../../models/plg_forecast.py).

## 15. Что нашёл тест-прогон (2026-08-15)

Полный тест (схема, 72 GET-ответа × 3 языка, CRUD-roundtrip, свойства алгоритмов,
граничные случаи, воспроизводимость, UI в трёх языках) выявил и закрыл пять дефектов.

**1. Четыре представления оставались `INVALID`.** `ALTER TABLE` над `PLG_STORES` /
`PLG_PRODUCTS` в `84_plg_testdata.sql` инвалидирует зависимые вьюхи. Oracle
перекомпилирует их лениво, поэтому запросы работали — но статус `INVALID` мог
всплыть как `ORA-04063`. В конец `84_plg_testdata.sql` добавлен блок рекомпиляции.

**2. Одинаковый `SEED` давал разные данные.** Три независимые причины:

* per-SKU генератор случайных чисел засевался от `PLG_PRODUCTS.ID` и
  `PLG_STORES.ID` — а это значения последовательности Oracle, у второго набора
  они другие. Теперь seed берётся от **порядкового номера** внутри набора;
* запросы, чей порядок строк питает `rnd.sample()` / `rnd.choice()`, шли **без
  `ORDER BY`**. Oracle не обязан сохранять порядок, поэтому в акцию попадали
  разные SKU, а за ними уезжал весь спрос. `ORDER BY` добавлен в выборки зон,
  оборудования, товаров и промо-календаря;
* при перекрытии двух акций на одном SKU в один день выигрывала «последняя
  прочитанная» — теперь порядок задан явно (`ORDER BY pr.ID`).

> Правило для будущих правок генератора: **любой `SELECT`, чей порядок строк
> влияет на поток случайных чисел, обязан иметь `ORDER BY`**, а seed никогда
> не должен зависеть от суррогатных ключей БД.

**3. Прогноз на пустом наборе рапортовал `done`.** Если в срезе нет магазинов,
прогон завершался «успешно» с нулём рядов — оператор видел зелёный статус без
объяснения. Теперь это явная ошибка с текстом причины.

**4. Прогон, где все ряды отброшены по нехватке истории, выглядел как пустой
успех.** Сообщение теперь называет порог: «алгоритму holt_winters нужно минимум
42 дней продаж».

**5. В словаре не хватало трёх статусов** (`st.draft`, `st.approved`,
`st.rejected`) — добавлены в `86_plg_i18n_gen.sql`.

Итог после исправлений: **PASS 87 / FAIL 0**, ни одной ошибки в консоли браузера
при обходе всех 14 разделов в трёх языках, backtest воспроизводит те же метрики,
что и до правок (промах в генераторе не влиял на прогноз).

## 16. Логистика завоза (`PLG_DC`, `PLG_VEHICLES`, `PLG_SHIPMENTS`)

Схема сети — **РЦ + прямые поставки**, три плеча доставки:

| Тип рейса | Плечо | Кто везёт |
|---|---|---|
| `inbound` | поставщик → РЦ | фуры и рефрижераторы, паллетный завоз |
| `transfer` | РЦ → магазин | развозка по дням маршрута (`PLG_DC_STORES.DELIVERY_DOW`) |
| `direct` | поставщик → магазин | фреш минуя РЦ: хлеб, молоко, мясо, локальные фермы |
| `return` | обратный рейс | тара, брак, просрочка |

Ключевые таблицы: `PLG_DC` (РЦ с доками и часами работы), `PLG_DC_STORES`
(зона обслуживания с расстоянием и днями развозки), `PLG_VEHICLES` (парк пяти
типов с грузоподъёмностью и паллетовместимостью), `PLG_SHIPMENTS` (рейс с
плановым и фактическим окном, доком, температурным режимом, опозданием),
`PLG_SHIPMENT_LINES` (состав рейса).

### Диаграмма Ганта

`GET /api/plg/gantt?dataset_id=&days=&group_by=vehicle|store|dock|supplier`
возвращает уже посчитанные строки-ресурсы и полосы-рейсы — шаблон только рисует
прямоугольники. Строка = машина / магазин / док / поставщик, полоса = плановое
окно, тонкая линия под ней = фактическое (зелёная — в окно, красная — с
опозданием), красная засечка слева = срыв окна > 30 мин, пунктирный контур =
отменённый рейс. Шкала — сутки с трёхчасовыми делениями.

Генератор раскладывает рейсы так, чтобы **на одном доке и на одной машине окна
не пересекались**: занятость проверяется до вставки, иначе Гант превращается в
кашу наложенных полос и перестаёт что-либо показывать.

> Даты в JSON приходят в формате RFC-822 (`Fri, 08 Aug 2026 09:13:00 GMT`).
> Искать по ним минимум/максимум сравнением строк нельзя — сначала `new Date()`,
> потом сравнение миллисекунд. На первой реализации шкала времени из-за этого
> разъезжалась на десятки тысяч пикселей.

## 18. Анализ конкурентов (`PLG_COMPETITORS`)

| Таблица | Назначение |
|---|---|
| `PLG_COMPETITORS` | Сеть-конкурент: позиционирование (`discount` / `mid` / `premium`), число магазинов, доля рынка, СТМ |
| `PLG_COMPETITOR_PRICES` | Мониторинг цен по нашим SKU: цена конкурента, наша цена на дату, промо-флаг, наличие, источник |

**Ценовой индекс** = цена конкурента / наша цена × 100. Ниже 100 — конкурент
дешевле. Визуализация: тепловая матрица «конкурент × товарная группа»,
цвет от красного (мы заметно дороже) до зелёного (мы дешевле). Под ней —
таблица SKU с наибольшим расхождением и список поставщиков конкурента
с пометкой пересечения с нашей базой.

**Импорт замеров**: `POST /api/plg/competitors/prices/import`, CSV
`код_конкурента;код_товара;дата;цена;промо`. Разделитель `;` или `,`
определяется автоматически, заголовок опционален, повторный замер за ту же
дату перезаписывается (`MERGE`).

## 19. Рынки других стран (`PLG_MARKETS`, `PLG_MARKET_CHAINS`)

Справочник рынков (Молдова, Румыния, Украина, Польша, Болгария, Грузия)
с макропоказателями: население, ВВП на душу, объём продуктового ритейла,
доля современной торговли, концентрация топ-5, средний чек в евро,
магазинов на 100 тыс. жителей, доля СТМ. К каждому рынку — схожие торговые
сети с выручкой, числом магазинов, средней площадью, долей рынка и онлайна.

Представление считает производные: выручка на магазин и **выручка с м²** —
именно они сопоставимы между сетями разного размера.

**Пузырьковая диаграмма**: ось X — число магазинов (логарифмическая, сети
различаются на три порядка), ось Y — средний чек в евро, радиус — выручка,
цвет — страна. Точка «наша сеть» считается из фактических магазинов и метрик
набора и подсвечена отдельно — видно, где сеть стоит относительно рынка.

> Средний чек генератора приведён к реальному диапазону (~7-9 € по курсу
> 19.4 MDL/EUR). До правки он считался как «средняя цена × 6.5» и давал ~660 MDL:
> на бенчмарке наша точка улетала за пределы облака и сравнение теряло смысл.

## 20. Новые этапы генератора

К пяти прежним добавлены четыре; полный прогон идёт в порядке `STAGE_ORDER`:

| # | Этап | Что создаёт |
|---|---|---|
| 2 | `suppliers` | Поставщиков, контакты, контракты, товарные группы (до ассортимента — SKU получают поставщика) |
| 7 | `logistics` | РЦ с доками, парк машин, расписание рейсов на трёх плечах |
| 8 | `competitors` | Сети-конкуренты, раунды замеров цен, их поставщиков |
| 9 | `markets` | Рынки шести стран и схожие сети |

Цена конкурента строится от **нашей** цены: `наша × позиционирование × сдвиг
SKU × промо`. Сдвиг по SKU постоянен между раундами — это «ценовая политика»
конкурента, поэтому индекс по категориям выходит неоднородным, как в жизни.

`delete_dataset()` обязателен: планограммы → транспорт → РЦ → магазины →
конкуренты → рынки → поставщики → товары → набор.

## 23. Что нашла перегенерация главного набора (2026-08-15)

При пересборке `NET-10-400` со всеми девятью этапами вскрылись два дефекта
генератора логистики — оба исправлены.

**1. Рейсы вставали на одну машину внахлёст (3 пары из 538).** Бронь ресурса
считалась по «дробному часу» (`7.0004`), а в timestamp минуты округлялись
отдельно, причём при округлении до 60 минут час не переносился — время уезжало
на час назад. Забронированный интервал и записанный расходились, проверка
занятости пропускала конфликт. Теперь `datetime_at()` считает через `timedelta`
от полуночи, а все три плеча **сначала округляют время до минут и только потом
бронируют** — интервал в карте занятости совпадает с тем, что попадёт в базу.

**2. Запуск подмножества этапов падал на `ORA-12899`.** Список кодов этапов
пишется в `PLG_GEN_RUNS.ALGORITHM`; девять кодов через запятую не влезали
в `VARCHAR2(30)`. Колонка расширена до 200, значение дополнительно усечено
в коде — прогон должен стартовать в любом случае.

> Проверка на пересечение окон вошла в регрессионный набор:
> ```sql
> SELECT COUNT(*) FROM PLG_SHIPMENTS a JOIN PLG_SHIPMENTS b ON a.ID < b.ID
>  AND a.VEHICLE_ID = b.VEHICLE_ID
>  AND a.PLANNED_START < b.PLANNED_END AND b.PLANNED_START < a.PLANNED_END;
> ```
> Должно быть 0. То же по паре `DC_ID + DOCK_NO`.

# Часть IV. Бизнес-процессы и связь презентации с системой

## 24. Прямые ссылки на разделы (deep-linking)

Модуль — одностраничное приложение, разделы переключались только в JS,
поэтому ссылку «на конкретный экран» дать было нельзя: любая вела на «Обзор».
Добавлен хеш-роутинг:

```
/UNA.md/orasldev/planograms#logistics     — диаграмма Ганта
/UNA.md/orasldev/planograms#forecast      — модели прогноза
/UNA.md/orasldev/planograms#competitors   — ценовой индекс
```

* адрес обновляется при переключении раздела (`history.replaceState`);
* `hashchange` переключает раздел без перезагрузки;
* `SECTION_ALIASES` держит синонимы (`#map` → `storemap`, `#orders` → `forecast`),
  чтобы ссылки в презентации и переписке не ломались от переименования раздела.

Всего адресуемо 18 разделов.

> При правке `boot()` легко промахнуться: `setLang()` заканчивается теми же
> четырьмя строками. Замена «по первому совпадению» уходит в `setLang`,
> и deep-linking молча не работает — проверять по имени функции.

## 25. Бизнес-процессы (`PLG_PROCESSES`)

Пять процессов модуля описаны в нотации BPMN и хранятся **в формате draw.io**
(mxGraph XML) в колонке `DIAGRAM_XML`:

| Код | Процесс |
|---|---|
| `planogram-change` | Изменение выкладки: от инициативы до внедрения с фотоотчётом |
| `order-forecast` | Формирование заказа: история → модель → backtest → заказ |
| `inbound-delivery` | Завоз товара: РЦ и прямые поставки, окна разгрузки |
| `supplier-management` | Работа с поставщиком: договор, группы, OTIF, перезаключение |
| `price-monitoring` | Ценовой мониторинг: замеры → индекс → реакция |

Гиперссылки узлов записаны штатным для draw.io способом —
`<UserObject label="…" link="/UNA.md/orasldev/planograms#analytics">`.
Поэтому клик по квадрату или ромбу работает **и** в бэк-офисе, **и** после
открытия файла в diagrams.net.

### Раздел «Бизнес-процессы» в бэк-офисе

`/UNA.md/orasldev/planograms#processes`

* переключатель процессов, описание, схема с кликабельными фигурами;
* **Скачать .drawio** — выгрузка файлом (`/api/plg/processes/<code>/drawio`);
* **Открыть в draw.io** — передача схемы в diagrams.net через `#R<url-encoded xml>`;
* **Импорт .drawio** — вставка XML или выбор файла; при сохранении XML
  проверяется на разбор и наличие `mxGraphModel`, иначе просмотрщик получил бы
  мусор и раздел «сломался» бы без объяснения.

Просмотрщик — собственный: разбирает mxGraph XML через `DOMParser`, читает
стиль draw.io (`rhombus`, `ellipse`, `rounded`, `fillColor`, `strokeColor`),
строит ортогональную трассировку связей с упором стрелок в границу фигуры.
Внешних библиотек не добавлено.

Схемы генерируются из компактной спецификации: `scripts/gen_plg_processes.py`
собирает `sql/91_plg_processes.sql`. Правки вносить в скрипт, а не в SQL.

## 26. Презентация: живые ссылки и схемы
