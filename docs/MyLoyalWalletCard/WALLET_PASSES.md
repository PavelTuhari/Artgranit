# Кошелёк: удостоверение держателя и защищённый учёт выпущенных пропусков

Один механизм на карту лояльности, билет автовокзала, посадочный талон и
пропуск. Пропуск лежит на телефоне, предъявляется там, где сети может не быть,
и не повторяется чужим скриншотом.

Сделано 12.09.2026. Серверная часть — в платформе (`loyalty-platform`),
клиентская — в приложении UNA Market (`mobile-app/mobile`).

---

## 1. Что это решает

| Задача | Как закрыта |
|---|---|
| Опознать держателя | Вход по номеру телефона с кодом; держатель связывается с картой лояльности по тому же номеру |
| Привязать пропуск к телефону | Устройство регистрируется, секрет привязки хранится в Keychain / Android Keystore, на сервере — только его хеш |
| Доказать подлинность без сети | Пропуск — подписанный Ed25519 токен; контролёр проверяет подпись открытым ключом офлайн |
| Отсечь скриншот чужого экрана | Рядом со штрихкодом — восьмизначный код, меняется каждые 30 с (HMAC от секрета и окна времени) |
| Не пустить один билет дважды | Одноразовые пропуска гасятся при проходе, повтор отклоняется |
| Ответить «кто выпустил и кто погасил» | Журнал событий с цепочкой хешей: переписать строку задним числом нельзя |
| Утерян телефон | Отзыв устройства гасит и его пропуска |

## 2. Устройство пропуска

```
base64url({"alg":"Ed25519","typ":"MLWC-PASS","kid":"…"})
  . base64url({"ser":"TKT-…","typ":"TRANSIT_TICKET","sub":"42","iss":"…","iat":…,"nbf":…,"exp":…,"bar":"…","one":true,"dat":{…}})
  . base64url(подпись)
```

- **Подпись** — Ed25519, ключи в `PassSigningKey`, ротация через
  `rotateSigningKey()`: старый ключ помечается отслужившим, но остаётся в
  наборе, поэтому ранее выпущенные пропуска продолжают проходить.
- **Открытые ключи** — `GET /api/wallet/v1/keys`; контролёр забирает их один раз.
- **Динамический код** — HMAC-SHA256(секрет, номер 30-секундного окна),
  усечение по RFC 4226, 8 цифр, допуск ±1 окно на расхождение часов.
- **Секрет кода** отдаётся устройству ровно один раз при выпуске. На сервере
  лежит зашифрованным (AES-256-GCM, ключ `WALLET_SECRET_KEY`) — дамп базы без
  ключа окружения кодов не даёт; рядом хранится sha256 для сверки целостности.

Реализация: `src/lib/pass.ts` (криптография), `src/lib/secretbox.ts` (шифрование
секретов), `src/lib/wallet-service.ts` (правила и база).

## 3. Журнал: почему его нельзя переписать

Каждое событие хранит хеш предыдущего:

```
hash = sha256({prev, passId, type, actor, actorId, createdAt, meta})
```

`GET /api/wallet/v1/passes/<serial>/audit` пересчитывает цепочку и отвечает
`chain_intact: true|false`. Удалённая или изменённая строка разрывает цепь, и
это видно в ответе — включая то, на каком событии цепь разошлась.

Записываются: выпуск, выдача на устройство, показ на экране, успешная проверка,
отказ с причиной, отзыв.

## 4. API

Два вида удостоверения: **держатель** (личный токен после подтверждения
номера) и **оператор** (ключ `sk_…`, тот же, что у POS API). Выпускать и
проверять пропуска имеет право система, а не телефон.

| Метод | Кто | Назначение |
|---|---|---|
| `POST /api/wallet/v1/auth/request-code` | все | код подтверждения на номер |
| `POST /api/wallet/v1/auth/verify` | все | вход, привязка устройства, личный токен |
| `GET /api/wallet/v1/passes` | держатель | что лежит на телефоне |
| `POST /api/wallet/v1/passes` | оператор | выпуск пропуска |
| `GET /api/wallet/v1/passes/{serial}` | держатель / оператор | один пропуск |
| `POST /api/wallet/v1/passes/{serial}/revoke` | держатель / оператор | отзыв |
| `GET /api/wallet/v1/passes/{serial}/audit` | держатель / оператор | журнал и целостность цепочки |
| `POST /api/wallet/v1/validate` | оператор | контроль на входе |
| `GET /api/wallet/v1/devices` · `DELETE` | держатель | устройства, отзыв утерянного |
| `GET /api/wallet/v1/keys` | все | открытые ключи для офлайн-проверки |
| `GET /api/wallet/v1/transit/trips` | все | расписание рейсов |
| `POST /api/wallet/v1/transit/tickets` | держатель / оператор | покупка билета |

Чужой пропуск отвечает `404`, а не `403`: перебирать номера бессмысленно.
Отказ контроля — это `200` с `valid: false` и причиной, а не ошибка запроса:
контролёру нужен вердикт, а не код HTTP.

## 5. Билет автовокзала

Тип пропуска `TRANSIT_TICKET`, полезная нагрузка:

```json
{
  "carrier": "Nord-Trans", "station": "Autogara Chișinău",
  "route": { "from": "Chișinău", "to": "Bălți", "number": "101" },
  "departure_at": "2026-09-12T06:00:00.000Z", "platform": "6", "seat": "48",
  "passenger": { "name": "Ion Popescu" },
  "price": { "amount": 120, "currency": "MDL" },
  "order_id": "MOCK-MTXYS3SB", "source": "mock"
}
```

Окно действия: открывается за 60 минут до отправления, закрывается через 30
после. Пассажир, севший на пять минут позже расписания, пройдёт; вчерашний
билет — нет (`BOARDING_OPENS_MINUTES` / `BOARDING_CLOSES_MINUTES` в `src/lib/transit.ts`).

### Подключение системы автовокзала

`TRANSIT_SOURCE=mock` (по умолчанию) — демо-рейсы стенда.
`TRANSIT_SOURCE=iruta` — боевая система продаж autogara.md, её адрес и ключ
задаются `IRUTA_BASE_URL` и `IRUTA_API_KEY`.

Контракт адаптера (`TransitAdapter`), который должна закрыть сторона автовокзала:

| Вызов | Что ожидается |
|---|---|
| `GET {IRUTA_BASE_URL}/api/trips?from=&to=&date=` | `{ "trips": [ { id, carrier, station, route{from,to,number}, departure_at, arrival_at, platform, price{amount,currency}, seats_available } ] }` |
| `POST {IRUTA_BASE_URL}/api/orders` | тело `{ tripId, passenger{name,phone,document_last4} }` → `{ order_id, seat, price{amount,currency} }` |
| `POST {IRUTA_BASE_URL}/api/orders/{id}/refund` | тело `{ reason }` → `200` |

⚠️ **Доступа к боевому контуру пока нет.** На `autogara.md` работает WordPress
и подсистема `iRuta` (`/iRuta/gsaCabinet/login.php`, расписание на
`92.115.181.24/orar/`); на сервере разработки 92.5.3.187 её нет. Пока ключ не
выдан, `TRANSIT_SOURCE=iruta` честно отвечает `503 transit_unavailable` вместо
выдуманных рейсов. Нужно от автовокзала: адрес API, ключ и подтверждение
формата ответов выше — либо доступ к базе, тогда адаптер пишется под неё.

## 6. Рабочее место контролёра

`https://<платформа>/station` — вход общий с кассой (`/cashier/login`).
Ввод номера билета или QR со сканера, поле для кода с экрана пассажира,
переключатель «гасить билет при проходе», крупный зелёный/красный вердикт с
рейсом, местом, перроном и маскированным телефоном пассажира.

Ключ оператора в браузер контролёра не попадает: страница ходит в
`/api/station/validate`, который проверяет сессию сотрудника.

## 7. Приложение

- **Профиль → Кошелёк** — вход по номеру, список карт и билетов, архив.
- **Пропуск** — штрихкод, динамический код с отсчётом, детали рейса, отзыв.
- **Рейсы** — расписание и покупка билета в два касания.
- Пропуска и их секреты переживают отсутствие сети: список хранится в базе
  приложения, секреты — в защищённом хранилище, код считается на устройстве
  (`src/wallet/code.ts`, SHA-256 и HMAC своей реализацией — `src/wallet/hmac.ts`,
  проверены векторами RFC 4231 и эталоном сервера).
- Адрес кошелькового сервера правится в настройках приложения — пересборка не нужна.

## 8. Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `WALLET_SECRET_KEY` | ключ шифрования секретов динамических кодов (≥32 символов) | выводится из `AUTH_SECRET` — **в проде задать явно** |
| `WALLET_HOLDER_SECRET` | подпись личных токенов держателей | `AUTH_SECRET` |
| `WALLET_ISSUER` | издатель в токене пропуска | `myloyalwalletcard.eminescu.md` |
| `WALLET_EXPOSE_OTP` | `1` — возвращать код подтверждения в ответе (стенд) | выключено в проде |
| `TRANSIT_SOURCE` | `mock` или `iruta` | `mock` |
| `IRUTA_BASE_URL`, `IRUTA_API_KEY` | доступ к системе продаж автовокзала | пусто |

## 9. Проверка

```bash
cd loyalty-platform
npm run dev          # в другом окне
npm run test:wallet  # 37 проверок
```

Покрыто: удостоверение (неверный код, кривой номер, повтор), привязка и отзыв
устройства, выпуск карты, право выпуска только у оператора, проверка подписи,
подделка подписи, неверный динамический код, окно посадки билета, журнал и
целостность цепочки, недоступность чужого пропуска, выдача только открытых
ключей, отзыв пропуска и устройства.

Отдельно проверено вживую на эмуляторе: вход в кошелёк из приложения, покупка
билета, показ динамического кода, проход контроля этим кодом (`consume`),
повторный проход тем же билетом — отказ `already_used`, журнал из трёх событий
с целой цепочкой.
