📌 1. Обзор

Интеграция с EasyCredit (EC Moldova) для оформления кредитов через SOAP API. Клиент реализован вручную на Python (integrations/easycredit_client.py), без WSDL-based библиотек (zeep, suds).

Технология Python + Flask + SOAP
Окружение Sandbox / Production

Две независимые точки применения, каждая со своим экземпляром EasyCreditProvider и своим набором настроек в Oracle (см. §4):

Biro26 — бэк-офис и витрина /UNA.md/orasldev/biro26-credit-admin (витрина: biro26-shop / biro26-site/cart) TMS_CREDITE_PROVIDER в Oracle 11g OfficePlus

📡 2. SOAP-операции

Реализованы в integrations/easycredit_client.py, каждая функция собирает SOAP-конверт вручную и парсит ответ через xml.etree.ElementTree.

ОперацияEndpoint (.svc)SOAPActionНазначениеКлючевые поля
Preapproved_v2.1 /Preapproved_v2.1.svc http://tempuri.org/IPreapproved_v2_1/Preapproved Проверка предодобренной суммы по IDNP Login, Password, UIN, Phone (опц.)
Request_v4_PJ /Request_v4_PJ.svc http://tempuri.org/Request_v4_PJ_I/InsertRequest Подача заявки, возвращает URN Login, Password, UIN, GUFirstName/LastName, GUMobile, GoodsName, GoodsPrice, CreditAmount, Product
URNStatus_v2 /URNStatus_v2.svc http://tempuri.org/URNStatus_v2_I/GetUrnStatus Статус заявки по URN Login, Password, URN
eShopClientInfo_v3 (ClientInfo) /eShopClientInfo_v3.svc http://tempuri.org/eShopClientInfo_v3_I/eShopClientInfo_v3 Данные клиента и его займы по IDNP Login, Password, UIN

Дополнительно доступны ECM_GetClientInfoByPhone (поиск по телефону) и ECM_GetUrnPerUin_V2 (список URN клиента) — используются служебными эндпоинтами основного проекта (/api/credit-easycredit/client-by-phone, /api/credit-easycredit/urns), не участвуют во флоу Biro26.

🏗️ 3. Архитектура интеграции

Слои

  • integrations/base_provider.py — абстрактный CreditProvider (единый интерфейс: preapproved/submit/check_status/check_auth, is_configured/get_settings) и ProviderRegistry.
  • integrations/easycredit_provider.py — EasyCreditProvider, обёртка над easycredit_client.py с единым интерфейсом.
  • integrations/__init__.py — глобальный registry (настройки читаются из Config, основной проект) и build_registry(settings_source) — новый реестр, читающий настройки из произвольного источника (см. §4).

Путь запроса на витрине Biro26

клиент витрины (shop.html / site_cart.html)
  → POST/GET /api/biro26/shop/credit/api/{preapproved,submit,status}
  → Biro26Controller.credit_api_*()               (controllers/biro26_controller.py)
  → Biro26Credit.api_preapproved/api_submit/api_status()   (models/biro26_credit.py)
  → Biro26Credit._registry() = build_registry(biro26_settings())
  → EasyCreditProvider(settings_source=biro26_settings())
  → integrations/easycredit_client.py               (SOAP)

biro26_settings() возвращает CrediteSettings поверх Biro26Backend (Oracle 11g); в основном проекте вместо неё используется глобальный registry, читающий Config.easycredit_* (те, в свою очередь, читают adb_settings() — Oracle ADB).

⚙️ 4. Хранение настроек

Настройки провайдеров хранятся в Oracle, в двух нормализованных таблицах (одна и та же схема развёрнута в обеих БД — см. §5):

  • TMS_CREDITE_PROVIDER — по одной строке на провайдера (CODE='easycredit'): ENABLED, ENV, BASE_URL, ICON, COLOR, ORD.
  • TMS_CREDITE_PROVIDER_PARAM — параметры и креды, ключ-значение на провайдера: для EasyCredit это api_user (обычный) и api_password (IS_SECRET='1').
⚠️ Правило «пустой секрет = не менять»: при сохранении настроек (CrediteSettings.save()) пустое значение секретного параметра НЕ затирает уже сохранённое — так UI может отправлять форму, не зная текущий пароль (только его маску, см. masked()).

Два независимых контура — у каждого свой CrediteSettings и своя запись в своей БД, значения не синхронизируются автоматически:

  • adb_settings() → AdbBackend → Oracle ADB основного проекта (через models/database.py).
  • biro26_settings() → Biro26Backend → Oracle 11g OfficePlus (через thick subprocess-воркер, models/biro26_db.py).

Фолбэк на .env: если источник настроек недоступен (БД не отвечает) или в нём вовсе нет записи для провайдера, значение берётся из переменных окружения (EASYCREDIT_BASE_URL/API_USER/API_PASSWORD). Но если запись в Oracle ЕСТЬ, она авторитетна целиком — пустое значение в ней НЕ подменяется значением из .env (см. CreditProvider._setting()).

🚫 data/easycredit_settings.json — больше не хранилище. Файл используется только как одноразовый seed-источник при первом деплое (deploy_credite_oracle.py читает его вместе с .env и заполняет TMS_CREDITE_PROVIDER, если строки для провайдера ещё нет). В рантайме файл не читается — save_easycredit_settings() пишет прямо в Oracle ADB.
⚠️ Демо-креды после первого деплоя. Если в .env (или файле-seed) не заданы реальные EASYCREDIT_API_USER/API_PASSWORD, действуют дефолты кода — demo/demo (см. Config.EASYCREDIT_API_USER/PASSWORD). Seed создаёт провайдера с ENABLED='0', но api_user/api_password при этом заполнены этими демо-значениями — в бэк-офисе провайдер покажется «configurat», хотя реальный вызов к EasyCredit вернёт ошибку авторизации (Invalid User Name / Password). Оператор обязан ввести настоящие креды через бэк-офис (§6) — «configurat» здесь означает «заполнены поля», а не «проверено на реальном API».

🗄️ 5. Схема TMS_CREDITE_*

Один и тот же DDL развёрнут в обеих БД: sql/50_credite_tables.sql (Oracle ADB) и sql/biro26/12_tms_credite.sql (Oracle 11g OfficePlus, копия того же текста). Без identity-колонок — последовательность + триггер BEFORE INSERT.

ТаблицаНазначениеКлючевые колонки
TMS_CREDITE_PROVIDER Реестр API-провайдеров (easycredit, iute) CODE, NAME, ENABLED, ENV, BASE_URL, ICON, COLOR, INFO, ORD, UPDATED
TMS_CREDITE_PROVIDER_PARAM Параметры и креды провайдера (PK: PROVIDER_ID+PARAM_NAME) PROVIDER_ID (FK), PARAM_NAME, PARAM_VALUE, IS_SECRET
TMS_CREDITE_ORG Организации кредитования (магазинные условия рассрочки) NAME, ENABLED, ORG_MODE (manual/api), PROVIDER_ID (FK, NULL=ручной режим), API_URL, LOGO_URL, INFO, ORD
TMS_CREDITE_PLAN Пакеты рассрочки организации (формула расчёта не менялась) ORG_ID (FK), NAME, MONTHS_MIN/MAX, AMOUNT_MIN/MAX, MARKUP_PCT, ANNUAL_PCT, MONTHLY_FEE_PCT, ISSUE_FEE, AVANS_MIN_PCT, ENABLED, INFO
TMS_CREDITE_REQ Заявки на кредит/рассрочку (журнал + API-статус) ORG_ID, PLAN_ID, MONTHS, PRODUCT_COD/NAME, QTY, AMOUNT, CREDIT_PRICE, MONTHLY, CLIENT_NAME, PHONE, STATUS, PROVIDER_CODE, EXT_REF, API_STATUS, PREAPPROVED_AMOUNT, IDNP_MASKED, LAST_CHECK, CREATED
TMS_CREDITE_REQ_EVENT Append-only лог вызовов API (без PII) REQ_ID, PROVIDER_CODE, OP, HTTP_CODE, DURATION_MS, PAYLOAD, RESULT, IS_ERROR, CREATED
PII в логе: перед записью в TMS_CREDITE_REQ_EVENT IDNP маскируется (_mask_idnp, видны первые/последние 2 символа), телефон обрезается, а длинные числовые последовательности (13+ цифр, включая с разделителями) вычищаются регэкспом (_scrub). Разрешённые поля результата — allowlist (_EVENT_SAFE_KEYS): success, preapproved, max_amount, status, state, urn, order_id, message, http_code, error.
ID без RETURNING ... INTO: subprocess-воркер (models/biro26_worker.py) не поддерживает OUT-бинды, поэтому api_submit() резервирует ID заявки через SELECT TMS_CREDITE_REQ_SEQ.NEXTVAL FROM dual до INSERT. request_create() (старый флоу без API) пока использует SELECT MAX(ID) — менять не требовалось в рамках этой работы.

Данные из YBIRO_CREDIT_ORG/PLAN/REQ (старые таблицы Biro26) перенесены скриптом деплоя; сами старые таблицы пока не переименованы — переименование в *_OLD выполняется отдельным флагом деплоя на сервере (см. §9).

🛠️ 6. Настройка в бэк-офисе Biro26

Страница /UNA.md/orasldev/biro26-credit-admin, вкладка/секция «Provideri API» (вверху страницы, до таблиц организаций и пакетов).

  1. Отметить чекбокс activ / включён для EasyCredit.
  2. Выбрать env: sandbox или production.
  3. Проверить/поправить base_url (по умолчанию подставляется URL по выбранному env).
  4. Ввести api_user и api_password (секретное поле, пустое при сохранении = не менять текущее значение).
  5. Нажать «Salvează» — PUT /api/biro26/credit/providers.
  6. Нажать «Test conexiune» — POST /api/biro26/credit/providers/easycredit/test; для EasyCredit нет отдельного check_auth, поэтому тест выполняет пробный preapproved на тестовом IDNP 2000000000001 и пишет результат в TMS_CREDITE_REQ_EVENT (OP='provider_test').
  7. В таблице «Organizații de creditare» у нужной организации выбрать EasyCredit в колонке «Provider API» и сохранить строку — только после этого у организации появляется кнопка оформления заявки через API на витрине.

Карточка провайдера показывает статус configurat/neconfigurat — это CrediteSettings.is_configured(): заполнены ли обязательные секретные поля (для EasyCredit — api_user и api_password). Статус не подтверждает, что креды рабочие — см. предупреждение в §4; для проверки реальной работоспособности используйте «Test conexiune».

🛒 7. Флоу на витрине

В корзине магазина Biro26 (shop.html — модалка корзины, site_cart.html — новая витрина) при выборе оплаты «в кредит» блок #ec-flow появляется, только если у выбранной организации привязан включённый провайдер (org.provider.configured). Иначе показывается прежняя форма «Cerere de credit» (журналируется в TMS_CREDITE_REQ без обращения к API — request_create()).

  1. Форма — ФИО, телефон, IDNP (ровно 13 цифр).
  2. Preapproved — POST /credit/api/preapproved; если preapproved=true, показывается предодобренная сумма, кнопка отправки активируется. Если провайдер вернул отказ, форма всё равно позволяет отправить заявку — решение принимает кредитор.
  3. Submit — POST /credit/api/submit: создаёт запись в TMS_CREDITE_REQ (API_STATUS='SENDING'), затем вызывает prov.submit(); при успехе сохраняет EXT_REF (URN) и API_STATUS='SENT'.
  4. Опрос статуса — GET /credit/api/status каждые 5 секунд, до 24 попыток (2 минуты), пока статус не станет финальным (APPROV|REJECT|APROB|RESPINS|DECLIN|CANCEL по регэкспу) или не истечёт лимит попыток — тогда UI предлагает «менеджер свяжется позже».
Дисклеймер об оценочности: расчёт рассрочки (наценка, ставка, комиссии, взнос — см. Biro26Credit.calc()) — ЕСТИМАТИВНЫЙ; окончательное решение о сумме и условиях принимает кредитор через Preapproved/ Request_v4_PJ.

Бэк-офис Biro26 (auth required)

РоутТело / параметрыОтвет

Витрина (public, rate-limited по IP)

РоутЛимитТело / параметрыОтвет
POST /api/biro26/shop/credit/api/preapproved 10/мин {org_id, idnp, amount, phone?} {success, data:{preapproved, max_amount, message}}
POST /api/biro26/shop/credit/api/submit 5/мин {org_id, plan_id, months, amount, qty, client_name, phone, idnp, product_name?, product_cod?} {success, data:{req_id, ext_ref, status, monthly, months, org}}
GET /api/biro26/shop/credit/api/status?req_id=N&ref=<ext_ref> 60/мин req_id, ref — оба обязательны {success, data:{status, ext_ref, saved?}} — saved есть только если провайдер реально был опрошен (не если заявка ещё не привязана к провайдеру/референсу)
Параметр ref обязателен. Публичный GET .../status подтверждает владение заявкой сравнением переданного ref с сохранённым EXT_REF — без него запрос отклоняется («cerere inexistentă»), заявку нельзя опросить по одному только req_id.

🚀 9. Деплой

./venv/bin/python deploy_credite_oracle.py --target both

Для каждой БД (adb, biro26) скрипт идемпотентно:

  1. создаёт объекты из соответствующего DDL, если их ещё нет (по имени в USER_OBJECTS);
  2. переносит данные из YBIRO_CREDIT_ORG/PLAN/REQ в TMS_CREDITE_*, если старые таблицы есть и целевые ещё пустые;
  3. сеет TMS_CREDITE_PROVIDER значениями из data/*.json + .env, только если строки для провайдера ещё нет (создаётся с ENABLED='0' — см. предупреждение в §4).

Переименование YBIRO_CREDIT_* → *_OLD — отдельный флаг --rename-legacy, выполняется на сервере ПОСЛЕ того, как новый код уже развёрнут и перестал обращаться к старым таблицам:

./venv/bin/python deploy_credite_oracle.py --target both --rename-legacy
deploy_to_remote.sh не создаёт Oracle-объекты. Он переносит только код. Если релиз меняет схему Oracle, DDL нужно применить отдельно — deploy_credite_oracle.py локально или на сервере (см. общее правило в корневом CLAUDE.md).
