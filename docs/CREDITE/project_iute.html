📡 API Endpoints

Check Auth

Проверка авторизации и получение информации о партнёре.

GET /api/v1/physical-api-partners/me
Headers: Authorization: {API_KEY}

Ответ: partnerId, posId, products[]

Create Order

Создание заказа (заявки на кредит).

POST /api/v1/physical-api-partners/orders
Headers: Authorization: {API_KEY}
Content-Type: application/json

{
  "posIdentifier": "...",
  "salesmanIdentifier": "...",
  "phoneNumber": "+373...",
  "orderAmount": 15000,
  "currency": "MDL",
  "items": [{ "name": "...", "quantity": 1, "price": 15000 }]
}

Get Order Status

Проверка статуса заказа.

GET /api/v1/physical-api-partners/orders/{orderId}
Headers: Authorization: {API_KEY}

Статусы: PENDING, IN_PROGRESS, PAID, CANCELLED, CUSTOMER_NOT_EXISTS

⚙️ Конфигурация

Настройки больше не хранятся в data/iute_settings.json — этот файл используется только как одноразовый seed при первом деплое (deploy_credite_oracle.py). Авторитетное хранилище — Oracle, таблицы TMS_CREDITE_PROVIDER (CODE='iute': ENABLED, ENV, BASE_URL) и TMS_CREDITE_PROVIDER_PARAM с параметрами:

ПараметрСекретныйНазначение
api_keyдаключ авторизации, заголовок Authorization
pos_identifierнетидентификатор точки продаж
salesman_identifierнетидентификатор продавца

Как и для EasyCredit, у Iute — два независимых контура: TMS_CREDITE_PROVIDER в Oracle ADB основного проекта (/UNA.md/orasldev/credit-admin) и та же схема в Oracle 11g OfficePlus (/UNA.md/orasldev/biro26-credit-admin, вкладка «Provideri API»). Пустое значение api_key при сохранении — «не менять». Подробности архитектуры (CrediteSettings, build_registry, правило «пустой секрет = не менять», фолбэк на .env, демо-креды после деплоя) — общие для всех провайдеров, см. документацию EasyCredit, §4.

⚠️ Безопасность: API ключи скрыты в интерфейсе бэк-офиса (маска xxx***), реальные значения НЕ передаются в frontend (CrediteSettings.masked()).

🛒 Витрина Biro26

Iute доступен в корзине магазина Biro26 (shop.html, site_cart.html) наравне с EasyCredit — тот же UI, те же маршруты /api/biro26/shop/credit/api/{preapproved,submit,status}, тот же реестр build_registry(biro26_settings()). Условие показа то же: провайдер включён И привязан к организации (TMS_CREDITE_ORG.PROVIDER_ID) в бэк-офисе.

⚠️ Известное ограничение: IuteProvider (integrations/iute_provider.py) реализует только check_auth / create_order / order_status (замаппленные на submit() / check_status()). Метод preapproved() не переопределён и наследуется от базового класса, который возвращает {"success": false, "error": "Not supported"}. Витрина всегда начинает флоу с шага «Preapproved» (см. §7 EasyCredit), поэтому для организации, привязанной к Iute, первый шаг сейчас завершится этой ошибкой и кнопка отправки заявки останется заблокированной — заявку через API отправить нельзя, пока в IuteProvider не появится preapproved() (например, как заглушка «всегда допустить к подаче», раз у Iute нет отдельного эндпоинта предодобрения) или пока флоу на витрине не научится пропускать этот шаг для провайдеров без capability preapproved. Тестовое подключение в бэк-офисе («Test conexiune») этой проблемы не имеет — оно использует check_auth, который у Iute реализован.
