# Разработка документа в UNA.md — полный пример

Как устроен документ в учётной системе UNA и как завести свой. Всё ниже
проверено в боевой схеме `OFFICEPLUS` (`orange.una.md`, Oracle 11.2.0.4)
25.08.2026: и разбор существующих документов, и создание собственных.

Сквозной пример — документы маркетинга модуля SEOForge: «Закупка рекламных
услуг» (`60001`) и «Акт о размещении рекламы» (`60002`).

---

## 1. Из чего состоит документ

Документ живёт в трёх местах сразу, и пропустить любое — значит получить
документ, который не работает.

| Слой | Где | Что задаёт |
|---|---|---|
| **Данные** | таблицы `TMDB_*` и вьюшки `VMDB_*` | что хранится |
| **Конфигурация** | дерево `A$ADM$V` / `A$ADP$V` | что это за документ, в каком журнале, каким модулем исполняется |
| **Интерфейс** | гриды в `A$LOB` | какие колонки видит пользователь и каким запросом они читаются |

Ошибка новичка — сделать только первый слой. Тогда таблицы есть, а в клиенте
документа нет.

## 2. Слой данных

### 2.1. Шапка — всегда `TMDB_DOCS`

Своей таблицы шапки у документа нет: шапка у всех одна.

| Колонка | Смысл |
|---|---|
| `COD` | номер документа, PK |
| `SYSFID` | **тип документа** |
| `TIP` | вид записи, у документов `'H'` |
| `DATAMANUAL` | дата документа, `NOT NULL` |
| `NRMANUAL` | номер, который видит человек |
| `VALUTA`, `NRSET`, `DIV` | валюта, набор, подразделение |
| `USERID` | автор |
| `ISGFC` | признак проведения |
| `DOCCOLOR` | цвет строки в реестре, ставится триггером |

`COD` **никогда не считается как `MAX(COD)+1`.** Его выдаёт триггер
`TRIG_BFINS_TMDB_DOCS`:

```sql
IF :NEW.COD IS NULL THEN
  SELECT ID_TMDB_DOCS.NEXTVAL INTO :NEW.COD FROM DUAL;
END IF;
IF :NEW.ISGFC IS NULL THEN :NEW.ISGFC := 0; END IF;
IF :NEW.USERID IS NULL THEN :NEW.USERID := ATOI(GET_ENV('PARAM_USERID')); END IF;
```

Отсюда два правила: вставлять с `COD = NULL`, а перед вставкой выставлять
сессионный `PARAM_USERID` через `SET_ENV` — иначе документ уйдёт в учёт без
автора.

Дополнительные реквизиты шапки лежат в `TMDB_DOCS_ADD` (`TXTCOMMENT`,
`PARENT_NRDOC`, `RECALC_*`), история изменений — в `TMDB_DOCS_LOG`, её
ведёт триггер `TMDB_DOCS_TRLOG`, руками туда писать не нужно.

### 2.2. Строки — универсальная таблица со слотами

Общей таблицы строк нет, есть **семейства**. Самое распространённое —
`TMDB_CST3A`:

```
NRDOC, NRDOC1                      -- документ и номер строки, вместе PK
CONT, DEP, SC, SC1                 -- счёт, контрагент, позиция, аналитика
CANT1..CANT9                       -- количества
SUMA1..SUMA9                       -- суммы
PRET1..PRET3                       -- цены
PRM1..PRM9                         -- числовые параметры
DATA1..DATA3                       -- даты
STR1..STR9                         -- строки
```

Это **пул типизированных слотов**. Каждый тип документа раскладывает по ним
свои поля, а бизнес-имена даёт вьюшка. Так одна таблица обслуживает десятки
типов документов, не разрастаясь колонками.

Ограничения `TMDB_CST3A` — образец для любой своей таблицы строк:

```sql
CONSTRAINT TMDB_CST3A_PK PRIMARY KEY (NRDOC, NRDOC1)
CONSTRAINT TMDB_CST3A_FK FOREIGN KEY (NRDOC)
    REFERENCES TMDB_DOCS (COD) ON DELETE CASCADE
    DEFERRABLE INITIALLY DEFERRED ENABLE NOVALIDATE
```

`ON DELETE CASCADE` — строки уходят вместе с документом. `DEFERRABLE
INITIALLY DEFERRED` — шапку и строки можно вставлять в любом порядке внутри
транзакции. `NOVALIDATE` — ограничение не проверяет исторические данные.

Номер строки выдаёт триггер, из общей для схемы последовательности:

```sql
CREATE OR REPLACE TRIGGER TMDB_CST3A_TRG
BEFORE INSERT ON TMDB_CST3A FOR EACH ROW
BEGIN
  IF :NEW.NRDOC1 IS NULL THEN
    SELECT ID_TMDB_CM.NEXTVAL INTO :NEW.NRDOC1 FROM DUAL;
  END IF;
END;
```

Свой параллельный нумератор заводить не нужно — берите `ID_TMDB_CM`.

### 2.3. Вьюшка — бизнес-имена и расшифровки

`VMDB_CST3A` — это таблица плюс колонки-расшифровки с приставкой `CLC`:

```sql
CREATE OR REPLACE FORCE VIEW VMDB_CST3A AS
SELECT A.NRDOC, A.NRDOC1, A.CONT, A.DEP, A.SC, ... ,
  (SELECT DENUMIREA FROM TMS_UNIVERS WHERE COD = A.DEP) CLCDEPT,
  (SELECT DENUMIREA FROM TMS_UNIVERS WHERE COD = A.SC)  CLCSCT,
  (SELECT DENUMIREA FROM TMS_UNIVERS WHERE COD = A.SC1) CLCSC1T
FROM TMDB_CST3A A;
```

Соглашение: `CLC<поле>T` — текстовая расшифровка кода. Благодаря им
интерфейсу не нужны соединения: он читает одну вьюшку и сразу показывает
названия.

Такая вьюшка key-preserved и обновляется напрямую. Если вьюшка становится
не обновляемой — появился фильтр, соединение, агрегат — пишется триггер
`INSTEAD OF` (пример в схеме: `TRIG_VMDB_CST_PRET`).

### 2.4. Проводки

`TMDB_CM` — общая таблица движений для любого типа: `NRDOC`, `DT`/`CT` со
своими аналитиками (`DTSC`, `DTDEP`, `DTSC1`, …), `CANT`, `SUMA`, `FUNCT`.

**Суммой документа она не является.** Проводки двойной записи
взаимопогашаются: у документа 386 двадцать проводок и `SUM(SUMA) = 0`, при
этом строки дают 5100. Сумму берите из строк.

Проводки не вставляются вручную. Их генерирует `UN$GFC` по настройкам
документа — так делают штатные пакеты схемы (`PKG_SALES`,
`PKG_ORDERS_DOCS`, `PKG_EDI`):

```sql
un$gfc.setDoc_GFC(v_nrdoc);
un$gfc.setDoc_Correct(v_nrdoc);
```

## 3. Слой конфигурации: uniConf

Клиент UNA строит меню, журналы и формы не из кода, а из дерева
конфигурации в самой базе.

| Таблица | Что хранит |
|---|---|
| `A$ADM$V` | узлы: `OBJ_ID`, `OBJ_TYPE`, `OBJ_SUBTYPE`, `PARENT_ID`, `SECTION`, `NAME` |
| `A$ADP$V` | свойства узла: `NAME` (ключ), `VTYPE`, `VALUE`, `LVALUE` (memo) |
| `A$ABC$V` | справочник типов и подтипов, правила вложенности |
| `A$ADS$V` | какие свойства допустимы для каждого типа узла |
| `A$LOB` | двоичные приложения узла: гриды, языки, отчёты |

Типы узлов: `1` — документы, `2` — журналы, `3` — отчёты, `4` — формы,
`5` — универсум, `6` — настройки, `7` — пользователи.

### 3.1. Узел документа

`OBJ_TYPE = 1`, `OBJ_SUBTYPE = 0`. Ключевые свойства:

| Свойство | Смысл |
|---|---|
| **`DB ID`** | **равно `TMDB_DOCS.SYSFID`** — этим документ и опознаётся |
| `DLL ID` | какой модуль исполняет документ |
| `DOCNAME` | идентификатор документа внутри модуля |

Связь `DB ID = SYSFID` проверена сопоставлением: каждый `SYSFID`,
встречающийся в данных, ложится ровно на один узел конфигурации.
`TIPDOC` в `TMDB_DOCS` при этом пуст у всех документов и типом **не
является** — распространённое заблуждение.

Под документом живут дочерние узлы: `2` — Actions, `3` — печатные формы,
`4` — Sold (подбор сальдо), `5` — итоги.

### 3.2. Узел журнала

`OBJ_TYPE = 2`, `OBJ_SUBTYPE = 0`:

| Свойство | Смысл |
|---|---|
| `SQLFILTER` | условие по `SYSFID` — какие документы попадают в журнал |
| `DOCTYPESFILTER` | какие типы разрешено создавать |
| `DOCTYPESDEFAULT` | тип по умолчанию для кнопки «новый» |
| `CAPTION`, `ACTIVE`, `DLL ID` | заголовок, доступность, модуль |

Пример реального фильтра:

```
sysfid=1208 or sysfid=1212 or sysfid=1213 or (sysfid>=1217 and sysfid<=1221)
```

Это сырой SQL, попадающий в `WHERE`. В вебе он берётся **по номеру журнала
из конфигурации** и проверяется по белому списку — испорченная запись в
конфигурации иначе стала бы инъекцией.

### 3.3. Как завести свой документ

Свойств у рабочего документа 47–52, дочерних узлов 7–9, LOB 3–6. Собрать
такой набор с нуля и не промахнуться нельзя, а промах виден пользователю
как сломанная форма. Поэтому **копируйте ближайший работающий документ**:

1. выберите донора по смыслу (для закупки услуг — `2:1:FS_48101`
   «Покупка услуг от фирм РМ», DLL `20`, DOCNAME `201`);
2. заведите новый узел `A$ADM$V` с `A$ADM$SQ.NEXTVAL`;
3. скопируйте все свойства, LOB и дочерние узлы;
4. поменяйте только `SECTION`, `NAME` и `DB ID`;
5. секциям дочерних узлов дайте префикс новой секции — `SECTION` уникален
   по всему дереву;
6. заведите журнал с фильтром на свой диапазон `SYSFID`.

Готовый установщик: `modules/seoforge/scripts/seoforge_erp_config.py`.
Он делает всё это одной транзакцией и проверяет, что диапазон свободен.
Проверка после установки показала ноль расхождений свойств с донором и
полный перенос LOB (3/3 и 6/6).

**Возьмите себе диапазон `DB ID`.** У маркетинга это `60000..60099`. Чужие
номера занимать нельзя: тип документа — это и настройки проводок, и форма,
и ответственность.

## 4. Слой интерфейса: дизайны гридов

Самая неочевидная часть. Колонки, которые видит пользователь, и запрос,
которым они читаются, лежат **в конфигурации**, а не в коде.

Гриды хранятся в `A$LOB`:

| Колонка | Смысл |
|---|---|
| `OBJ_ID` | узел, которому принадлежит грид |
| `LOB_TYPE` | `0` — Grid, `1` — Cust, `2` — Lang, `3` — List, `4` — Sys, `5` — Rep, `6` — File |
| `LOB_NAME` | `:<форма>:<грид>`, например `:fRegistru:grCST3a` |
| `LOB_VALUE` | двоичный поток Delphi |

Формат потока — `TPF0` (обычный Delphi-поток компонента) или `SDBG`
(составной, с блоками). У `SDBG` флаги блоков: `1` — Columns, `2` —
GridProps, `16` — SmartQuery. Декодировать умеет
`SL/Cnf/python/uniconf/tpf0.py`.

### 4.1. Что внутри — на реальном примере

Грид `:fRegistru:grCST3a` документа «Закупка рекламных услуг» (2348 байт,
формат `SDBG`, блоки `Columns` и `SmartQuery`) содержит:

- колонки `CONT`, `CLCSCT`, `SUMA1`, `SUMA2`, `SUMA3` — со свойствами
  `FieldName`, `Title.Caption`, `Width`, `Alignment`, `Font.Style`,
  `ButtonStyle = cbsEllipsis`, `PickList`;
- **SmartQuery** с прямым запросом строк:

```sql
SELECT ... FROM VMDB_CST3A WHERE NRDOC = :COD ORDER BY NRDOC1
```

### 4.2. Практический вывод

**Грид отвечает на вопрос «где лежат строки этого документа».** Не нужно
угадывать таблицу — она написана в `SmartQuery` грида.

Это важно, потому что угадывание не работает. Поиск «в какой таблице есть
такой `NRDOC`» даёт ложные срабатывания: у документа 86 («Акт изменения
цен») так «находится» `TMDB_SALAR_ABSD1` с 28 строками зарплаты, где
`NRDOC` означает совсем другой документ.

И второй вывод: если вы скопировали документ-донор, вы унаследовали его
грид, а вместе с ним — **его таблицу строк**. Класть строки в свою таблицу
после этого нельзя: родной клиент будет читать донорскую, и один и тот же
документ станет выглядеть по-разному в клиенте и в вебе.

## 5. Собственный контур: как сделано у маркетинга

`modules/seoforge/sql/117_tmdb_yseo_docs.sql`.

### 5.1. Строки — в общей таблице, под своим именем

Документы `60001`/`60002` скопированы с закупки услуг и унаследовали грид
`grCST3a`. Значит строки обязаны лежать в `TMDB_CST3A`. Своей таблицы строк
у них нет — и это осознанный отказ, а не упрощение.

Бизнес-имена даёт своя вьюшка над общей таблицей:

```sql
CREATE OR REPLACE VIEW VMDB_YSEO1D AS
SELECT a.NRDOC, a.NRDOC1,
       a.CONT  AS CONT,        a.DEP   AS PARTNER_COD,
       a.SC    AS SC,          a.SC1   AS PLATFORM_COD,
       a.PRM1  AS CHANNEL_COD1,
       a.CANT1 AS CANT,        a.PRET1 AS PRET,
       a.SUMA1 AS SUMA,        a.SUMA2 AS SUMA_TVA,
       a.SUMA3 AS SUMA_TOTAL,
       a.DATA1 AS DATE_START,  a.DATA2 AS DATE_END,
       a.STR1  AS NOTE,
       (SELECT u.DENUMIREA FROM TMS_UNIVERS u WHERE u.COD = a.SC) CLCSCT,
       ...
FROM   TMDB_CST3A a
WHERE  EXISTS (SELECT 1 FROM TMDB_DOCS d
               WHERE d.COD = a.NRDOC AND d.SYSFID BETWEEN 60000 AND 60099);
```

Фильтр по типу документа обязателен: таблица общая, без него вьюшка
показывала бы чужие строки.

Из-за фильтра вьюшка перестаёт быть обновляемой — поэтому у неё есть
`INSTEAD OF` триггер. Он же делает две вещи по существу задачи: не пускает
строку в чужой документ и считает итог, если его не передали.

```sql
IF v_sysfid IS NULL OR v_sysfid NOT BETWEEN 60000 AND 60099 THEN
  RAISE_APPLICATION_ERROR(-20110,
    'RO: Randurile de marketing pot fi legate doar de documentele proprii '
    || 'ale modulului. / EN: Marketing rows may only be attached to the '
    || 'module own documents.');
END IF;
```

Проверено: `INSERT INTO VMDB_YSEO1D (NRDOC, …) VALUES (386, …)` — где 386
чужой документ — отклоняется.

### 5.2. Шапка — собственное расширение

`TMDB_YSEO1M` хранит то, чему негде лежать в `TMDB_DOCS`: кампания, сайт,
статья бюджета, канал, площадка, период. Подчинение и ограничения — по
образцу CST3:

```sql
CONSTRAINT TMDB_YSEO1M_PK PRIMARY KEY (NRDOC),
CONSTRAINT TMDB_YSEO1M_FK FOREIGN KEY (NRDOC)
    REFERENCES TMDB_DOCS (COD) ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED,
CONSTRAINT TMDB_YSEO1M_CK_PERIOD CHECK (
    PERIOD IS NULL OR REGEXP_LIKE(PERIOD, '^[0-9]{4}-[0-9]{2}$'))
```

Плюс триггер владения — тот же, что у строк. Плюс вьюшка `VMDB_YSEO1M`
с расшифровками `CLC*`.

Родной клиент про эту шапку не знает — она нужна веб-модулю. Если
понадобится в клиенте, ей надо будет дописать грид в конфигурации.

## 6. Порядок разработки — чеклист

1. **Определить хранение строк.** Копируете документ — декодируйте грид
   донора и посмотрите `SmartQuery`. Делаете с нуля — выберите семейство
   (`CST3`, `CST4`, `ST201`) или заведите свою таблицу по их образцу.
2. **Занять диапазон `DB ID`.** Проверить, что он свободен и в
   конфигурации, и в данных.
3. **Таблицы:** PK, FK на `TMDB_DOCS` с `ON DELETE CASCADE DEFERRABLE`,
   индексы по каждой FK-колонке, `CHECK` по существу задачи.
4. **Триггеры таблиц:** нумерация из `ID_TMDB_CM`, проверка владения.
5. **Вьюшки:** бизнес-имена, расшифровки `CLC*`, фильтр по своим типам.
6. **Триггер `INSTEAD OF`,** если вьюшка не обновляемая.
7. **Конфигурация:** документ (копией), журнал с `SQLFILTER`, группа.
8. **Гриды:** унаследованы при копировании либо дописываются отдельно.
9. **Проведение:** через `un$gfc.setDoc_GFC` + `setDoc_Correct`.
10. **Проверить в клиенте и в вебе** — они должны показывать одно и то же.

## 7. Грабли, на которые я наступил

Каждая — реальная, с проверкой.

| Грабли | Чем кончилось |
|---|---|
| `SUM(TMDB_CM.SUMA)` как сумма документа | ноль вместо 5100: проводки взаимопогашаются |
| Поиск таблицы строк по `NRDOC` | у документа изменения цен «нашлись» зарплатные строки |
| Своя таблица строк после копирования документа | второй склад строк, невидимый родному клиенту |
| `MAX(COD)+1` для номера документа | дубль ключа при двух сессиях, обход триггера |
| Bind-переменная `:uid` | `ORA-01745`: `UID` — встроенная функция Oracle |
| `RETURN` внутри compound trigger | `PLS-00678` |
| Построчный триггер, читающий свою же таблицу | `ORA-04091`, нужен compound |
| `;` внутри `--` комментария в SQL-файле | сплиттер деплоя рвёт команду пополам |
| Вьюшка до пакета в порядке установки | `ORA-00904` на функции пакета |

И отдельно: документ нельзя создать, пока в учёте не открыт **рабочий
период**. Система отвечает `ORA-20101: Data documentului … inafara
perioadei de lucru`. Это не ошибка кода — это бухгалтерская настройка.

## Доступ к базе: пул долгоживущих воркеров (требование)

Правило для каждого модуля, который ходит в ERP, — и для каждой новой задачи,
где такая система проектируется:

1. **Никаких процессов на запрос.** Обращения к Oracle идут через
   `models/biro26_db.py` — пул долгоживущих воркеров (`--serve`). Запуск
   процесса на каждую интерогацию стоил ~1,7 с и был главной причиной
   медленного ответа сайта (замер 26.08.2026).
2. **Чтения** переиспользуют удержанное соединение: они не трогают
   состояние сессии. **Записи** (dml/plsql/script) всегда получают свежее
   соединение — они выставляют контекст сессии (`SET_ENV`: период,
   пользователь), и он не имеет права утекать в следующие запросы.
3. **Один `execute_script` — одна транзакция.** На это опирается запись
   документов в ERP; ломать нельзя.
4. **Таймаут убивает процесс** — сессия Oracle падает и откатывается.
   Это страховка от чужих блокировок, её нельзя заменять «мягким» ожиданием.
5. Выключатель на случай беды: `BIRO26_WORKER_POOL=0` возвращает старый
   транспорт (процесс на запрос). `BIRO26_WORKER_POOL_SIZE` — размер пула.

Ориентиры скорости после перехода: чтение ~0,16 с, запись ~1,1 с,
тестовый прогон 4,6 с. Если новый код снова показывает секунды на чтение —
что-то пошло мимо пула.
