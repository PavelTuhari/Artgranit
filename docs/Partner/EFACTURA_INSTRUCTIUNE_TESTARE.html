e-Factura — instrucțiune de testare

Facturile fiscale primite de la parteneri (rolul de cumpărător), pe contul real al OfficePlus la SFS. Versiunea 13.09.2026. Actul de testare executat după această instrucțiune: EFACTURA_ACT_TESTARE_2026-09-13.html.

Ce NU se face în test fără decizia contabilului: «Acceptă în SFS» și «Respinge în SFS…». Ambele trimit decizia firmei la SFS și la furnizor și nu se pot retrage. Tot restul (preluare, potrivire, import în una.md) se poate repeta și șterge.

2. Pregătire

  • Intrare în back-office-ul web cu contul de operator (pagina /login).
  • În pagina de administrare e-Factura sînt completate: contul API real, vat_payer = 0, creation_motiv = 1, setările contabile in_nrset 201, in_dt 2171, in_ct 5211, in_dtdep 1, in_dt_row 2171, in_userid 1.
  • Butonul «Testează conexiunea» din administrare dă verde (mesajul rămîne pe ecran, nu dispare).
  • Un furnizor v-a transmis cel puțin o factură fiscală prin e-Factura (ea apare în cabinetul sfs.md la «Facturi primite → de semnat»).

3. Pașii de test (web)

1Deschideți pagina de test și în blocul «Contul API» scrieți utilizatorul și parola contului real; apăsați «mediu real» (adresa devine https://efactura-api.sfs.md/Service.svc).
Așteptat: nimic nu se trimite încă; pagina nu salvează contul nicăieri.
2Cardul «📥 Facturi primite de la parteneri» → «Preia din e-Factura».
Așteptat: mesaj «găsite N, adăugate A, actualizate U»; în tabel apar facturile în care firma e cumpărător: seria/nr, furnizor, IDNO, data, total, TVA, statutul SFS (7 așteaptă cumpărătorul sau 3 acceptată), statutul nostru (NEW), coloana «În una.md» (✓ furnizorul găsit sau «lipsește»), «Poziții» (potrivite / total).
3Click pe factură → se deschide detaliul cu pozițiile.
Așteptat: pentru fiecare poziție: denumirea, UM, cantitatea, prețul fără TVA, TVA %, total, codul de bare și «Potrivire în una.md»: cod de bare (card găsit în TMS_MPT_BARCODE), regulă (TMS_IMPORT_EFACTURA) sau nepotrivit.
4«XML» — se deschide XML-ul facturii așa cum l-a dat SFS (fără semnătura XAdES).
Așteptat: <Document><SupplierInfo>… cu Supplier/Buyer/Merchandises.
5«Repotrivește» — reia potrivirea furnizorului și a pozițiilor.
Așteptat: «potrivire: {barcode: n, rule: m, none: k}»; furnizorul după IDNO în TMS_UNIVERS.CODVECHI / TMS_ORG.CODFISCAL.
6Dacă furnizorul lipsește → «Adaugă furnizorul în una.md» (puntea Contragenti).
Așteptat: firma apare în nomenclator cu COD nou, CODVECHI = IDNO, GR1 = E, rînd în TMS_ORG cu CODFISCAL; coloana «În una.md» devine ✓. Dacă firma există fără cod fiscal, se repară (nu se dublează).
7«Import în una.md (pachet 12103 → document 1209)».
Așteptat: mesaj cu numărul pachetului (COD al documentului 12103) și statutul din TMDB_XML_PACKAGE: valida → documentul 1209 creat (numărul lui apare în rînd, statutul nostru IMPORTED). Alte statute posibile și ce înseamnă:

10Decizia în SFS — doar contabilul: «Acceptă în SFS» (factura trece în «acceptate», statut SFS 3) sau «Respinge în SFS…» cu motiv (ajunge la furnizor). În test se sare peste acest pas.

4. Pașii de test (back-office nativ, Delphi)

N1 «Intrări» → 12103 «Pachet XML e-Factura» → document nou → acțiunea «Preia din e-Factura (API)».
Așteptat: Oracle cheamă EFA_INBOX.fetch_api_pr → serverul web (officeplus.md/api/biro26/efactura/inbox/package/<nrdoc>) aduce facturile noi din SFS și le pune în pachet; mesaj «facturi noi: N; valide: V; cu probleme: …». Fără cheie API adresa răspunde 401.
N2 Acțiunea «Загрузить XML» (a vendorului) — reface validările; «Сформировать документы 1209» — creează documentele pentru pozițiile valide. Rezultatul e același ca la pasul 7 din web.

5. Verificări în bază (pentru IT)

-- facturile primite si soarta lor
SELECT ID, ENV, SERIA, NUMBER_, SUPPLIER_NAME, TOTAL, SFS_STATUS, STATUS, PKG_NRDOC, PKG_STATUS, DEST_NRDOC
FROM EFA_IN ORDER BY ID;
-- pachetul si statutele vendorului
SELECT NRDOC, NRDOC1, FACTURA_SERIA, FACTURA_NR, STATUS_DOC, NRDOC_DEST, COMMENTS FROM TMDB_XML_PACKAGE WHERE NRDOC = :pachet;
-- documentul 1209
SELECT COD, NRMANUAL, DATAMANUAL, USERID FROM TMDB_DOCS WHERE COD = :doc;
SELECT DT, CT, DTDEP, CTDEP, CLCCTDEPT FROM VMDB_ST201M WHERE NRDOC = :doc;
SELECT RROWID, DTSC, CANT, PRET, SUMA, SUMAGAAP, SUMAVALCT FROM VMDB_ST201D WHERE NRDOC = :doc ORDER BY RROWID;
-- toate comunicarile cu SFS (cerere + raspuns, si cele reusite)
SELECT ID, SRC, OP, STATUS, CREATED FROM EFA_CALL ORDER BY ID DESC;

Jurnalul comunicărilor cu SFS e și în web: …/efactura/admin/calls.

6. Curățenie după test

Documentele create în test (12103 și 1209) se șterg din back-office-ul nativ sau, dacă data lor e în afara perioadei de lucru, de către IT cu ocolirea de sistem (envun4.dont_fire_trigger). Rîndurile din EFA_IN se pot lăsa — la următoarea preluare se actualizează, nu se dublează.
