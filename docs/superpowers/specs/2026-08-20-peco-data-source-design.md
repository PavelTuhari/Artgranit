# Дизайн: источник данных UNA.md/PECO в модуле «Планограммы» + визуализация автозаказа в planogram3d

*20.08.2026 · утверждено владельцем (brainstorming-сессия).*

## Контекст

Модуль «Планограммы» Artgranit (`PLG_*`, `controllers/planogram_controller.py`,
`templates/planograms.html`) сегодня поддерживает один источник данных —
демо-набор `PLG_DEMO` (обычные магазины, `docs/Planograms/PLANOGRAMS_MODULE.md`).

Раздел «Автозаказ топлива» (`#fuel`, §35 того же документа) уже читает и пишет
напрямую в `PECO_*` без демо-дублирования — сознательное архитектурное решение
против второго источника правды (см. «Почему данные лежат в PECO_*, а не в
PLG_*» в модульной документации).

Задача — распространить тот же принцип на **основной** (не только `#fuel`)
модуль планограмм: добавить список поддерживаемых источников данных, где
второй пункт — `UNA.md/PECO` (46 реальных АЗС сети), и при его выборе модуль
работает на объектах PECO напрямую: общие справочники товаров (сорта топлива)
и точек (АЗС), без копирования в `PLG_*`.

Отдельно — визуализация факта инициации автозаказа в другом проекте,
**planogram3d** (`/Users/pt/Projects.AI/.../gourmet/planogram3d`, отдельный
Python/Flask/Plotly репозиторий, не Artgranit).

Проект разбит на два независимых поддпроекта.

## Проект A — источник данных UNA.md/PECO (Artgranit)

### Область

Read-only визуализация. PECO уже имеет собственные рабочие интерфейсы
(`peco-admin`, `peco-shift`, `peco-pump`) для цен, смен, приёмки цистерн —
модуль планограмм их не дублирует и не подменяет, а показывает сеть АЗС в
своей витрине, читая напрямую `PECO_*`/`V_PECO_*`. Запись
(изменение цен, приёмки) из витрины планограмм при источнике PECO — вне
первой итерации.

Новых Oracle-объектов не требуется — используются существующие таблицы и
представления. Деплой DDL на этом этапе не нужен, что заметно снижает риск
для `https://nufarul.eminescu.md/` (критический production-инвариант,
`CLAUDE.md`): изменения — только в Python и шаблонах.

### Архитектура

```
models/plg_datasource.py
├── class PlanogramDataSource(ABC)
│   ├── list_stores() -> List[dict]
│   ├── list_products(store_id) -> List[dict]
│   └── store_layout(store_id) -> dict   # «стеллаж → полки → товары»
├── class DemoDataSource(PlanogramDataSource)
│   └── тонкая обёртка над текущими PLG_*-запросами (поведение не меняется)
└── class PecoDataSource(PlanogramDataSource)
    ├── list_stores()   -> PECO_STATIONS (46 АЗС как "магазины")
    ├── list_products() -> PECO_REF_FUEL_GRADES + действующая цена
    │                      из PECO_PRICES (VALID_TO IS NULL)
    └── store_layout()  -> резервуар (PECO_TANKS) + сорт топлива = "товар
                           на полке"; наполненность (V_PECO_TANK_LEVELS) —
                           аналог остатка на полке
```

Соответствие понятий (для UI и внутренних структур, без переименования
Oracle-объектов):

| Планограммы (demo) | PECO |
|---|---|
| Магазин | АЗС (`PECO_STATIONS`) |
| Товар | Сорт топлива (`PECO_REF_FUEL_GRADES`) |
| Остаток на полке | Наполненность резервуара (`V_PECO_TANK_LEVELS`) |
| Цена | Действующая цена (`PECO_PRICES`, `VALID_TO IS NULL`) |

`controllers/planogram_controller.py` получает параметр источника
(`?source=demo|peco`, аналогично уже существующему `?lang=`) и выбирает
backend через фабрику. JSON-контракт ответов контроллера не меняется —
`templates/planograms.html` не переписывает логику рендера, только точку
выбора источника плюс сам селектор в UI.

### UI и документация

* Селектор источника на странице планограмм; список «поддерживаемые
  источники данных: Demo (демо-сеть) · UNA.md/PECO (46 АЗС, реальные
  данные)».
* `docs/Planograms/PLANOGRAMS_MODULE.md` — новый раздел «Источники данных»
  (по образцу §35, со ссылкой на этот дизайн-документ).
* `README.md` — по чек-листу `CLAUDE.md` (§4 «UI и маршруты», §5
  «Документация»), т.к. это функциональное изменение модуля, даже без
  новых Oracle-объектов.

### Критерии приёмки

1. `/UNA.md/orasldev/planograms?source=peco` отдаёт реальные 46 АЗС из
   `PECO_STATIONS` вместо демо-магазинов.
2. Переключение обратно на `source=demo` не меняет прежнее поведение —
   регрессия исключена смоук-тестом до и после.
3. Товары в `store_layout()` при `source=peco` — сорта топлива с
   действующей ценой станции, не выдуманные SKU.
4. Ни один новый Oracle DDL не задействован (грепом по коммиту:
   изменения только в `models/`, `controllers/`, `templates/`, `docs/`).
5. После любого прогона на remote:
   `curl -I https://nufarul.eminescu.md/login` → `HTTP/2 200`.

## Проект B — визуализация инициации автозаказа в planogram3d

### Контекст

planogram3d — независимый Python/Flask/Plotly-проект («цифровой двойник
сети», см. его `docs/HANDOFF.md`). В нём уже есть работающий паттерн для
именно такой интеграции: `webapp/network.py` (логистический центр,
грузовики по дорогам города) и `webapp/eta_ai.py` (онлайн-обучаемое
ИИ-табло прибытия, добавленное в этом же цикле работы). Тот же паттерн
переиспользуется для сети АЗС и рейсов бензовозов.

Artgranit уже отдаёт всё нужное API без изменений на своей стороне:
`GET /api/plg/fuel/runs`, `GET /api/plg/fuel/trips`,
`GET /api/plg/fuel/trips/<id>/track`, `POST /api/plg/fuel/autoorder`
(раздел `#fuel`, см. §35 `PLANOGRAMS_MODULE.md`). Единственное, что может
понадобиться со стороны Artgranit, — токен для чтения с внешнего хоста
(по аналогии с токен-авторизацией `PECO_GPS_PROVIDERS`), а не новый
эндпоинт.

### Архитектура

```
planogram3d/webapp/peco_fuel.py     (новый, по образцу network.py)
├── эмулятор сети АЗС + автозаказов по умолчанию
│   (свой сценарий: рейсы бензовозов, как сейчас демо-сеть магазинов)
└── реальный поток: опрос Artgranit
    GET /api/plg/fuel/trips
    GET /api/plg/fuel/trips/<id>/track
    интервал опроса; глушит эмулятор по таймауту — тот же паттерн,
    что уже применяется к Zabbix и GPS доставки (webapp/delivery.py)
```

Визуализация на карте: бензовозы едут по дорогам к АЗС, переиспользуя
`webapp/roadnet.py` (тот же граф/маршрутизация, что для грузовиков РЦ) и
`webapp/eta_ai.py` (то же онлайн-табло прибытия — АЗС получает такое же
табло, как магазины сети «Гурман» сейчас получают для грузовиков РЦ).

### Триггер и данные

Нажатие «Инициировать автозаказ» в Artgranit
(`POST /api/plg/fuel/autoorder`) создаёт `PECO_ORDER_RUNS` →
`PECO_FUEL_ORDERS` → (после планирования рейсов) `PECO_TRIPS`.
planogram3d видит это при следующем опросе `/api/plg/fuel/trips` и рисует
рейс на карте — без явного webhook/pub-sub (в Artgranit его нет, см.
исследование архитектуры PECO, раздел 3 отчёта), работает тем же
pull-опросом, что и остальные внешние контуры planogram3d.

### Критерии приёмки

1. Эмулятор рейсов бензовозов работает по умолчанию, без обращения к
   Artgranit (принцип planogram3d: «каждый внешний контур имеет
   эмулятор»).
2. При доступности `/api/plg/fuel/trips` Artgranit реальные рейсы
   вытесняют эмулятор по таймауту, как уже сделано для GPS доставки.
3. Инициация автозаказа в Artgranit приводит к появлению бензовоза на
   карте planogram3d в течение одного цикла опроса.
4. ИИ-табло прибытия для АЗС работает по тому же контракту API
   (`/api/eta/...`), что уже есть для магазинов сети «Гурман».

## Порядок работы

Проекты независимы: A трогает только Artgranit (без DDL), B — только
planogram3d плюс контракт на чтение существующего API Artgranit. Сначала
A (самодостаточен и разблокирует данные для B), затем B.

## Явно вне рамок (на сейчас)

* Запись (цены, приёмки цистерн) из витрины планограмм при источнике
  PECO.
* Новые Oracle DDL/миграции — оба сценария используют существующую схему.
* Push/webhook со стороны Artgranit — вместо этого пуллинг существующего
  REST API, по аналогии с остальными внешними контурами planogram3d.
