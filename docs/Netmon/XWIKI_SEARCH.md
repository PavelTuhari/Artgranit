## 1. Что такое xwiki.una.md

| | |
|---|---|
| Сервер | 192.168.0.15, Windows Server 2003 SP2, в Zabbix — хост «xwiki» (техническое имя `amd64`) |
| Приложение | XWiki на GlassFish 3.1.1 (Java 1.7), порт 8080; админка GlassFish — 4848 |
| Снаружи | https://xwiki.una.md → nginx 1.20.1 на 192.168.0.148 → 192.168.0.15:8080 |
| База | схема `XWIKI` в Oracle cloudbd (192.168.0.24, SID CLOUDBD) — та же база, что у OTRS |
| Содержимое | 3499 страниц (`XWIKIDOC`), из них 2536 в разделе UNA; 7356 вложений; языки ru, ro, en |

**Диски сервера вики заполнены.** На 18.10.2026 в Zabbix горят триггеры:
D: — свободно 0 байт (все три порога: 10 %, 5 %, 1 %), C: — свободно 6,6 %
(2,5 ГБ из 38 ГБ). Когда закончится место на C:, GlassFish не сможет писать
журналы и временные файлы — вики встанет. Это надо разобрать на самом сервере
(что лежит на D:, журналы GlassFish на C:); удалённо отсюда ничего не чистилось.

## 2. Мониторинг

Скрипт `modules/netmon/scripts/netmon_zabbix_xwiki.py` (повторный запуск ничего не
дублирует, `--dry-run` — только показать). Заведено 18.10.2026:

| Где в Zabbix | Что | Триггер |
|---|---|---|
| хост `xwiki.una.md`, группа Domains | Template Web — сайт отвечает 200; Template SSL Check — срок сертификата | общие триггеры шаблонов |
| там же, веб-сценарий «XWiki» | шаг «Главная» — `/bin/view/UNA/WebHome`, в ответе обязана быть метка `name="wiki" content="xwiki"` (заглушка nginx за вики не сойдёт); шаг «Поиск» — встроенный поиск вики, он ходит в базу | «Вики xwiki.una.md не открывается» (высокий, 3 мин подряд); «…отвечает медленно» (> 5 с в среднем за 5 мин) |
| хост `xwiki` (192.168.0.15) | простая проверка `net.tcp.service[tcp,,8080]` — GlassFish принимает соединения | «GlassFish с вики не отвечает на порту 8080» (высокий) |
| хост `xwiki` | описание хоста заполнено: что за сервер и где база | — |

Веб-сценарии выполняет сам сервер Zabbix, cron не нужен. Если упала машина —
сработает агент; если машина жива, а вики нет — порт 8080; если GlassFish жив,
а страница отдаёт ошибку — веб-сценарий.

## 3. Умный поиск по вики и заявкам

### Как устроен

Вся логика — в базе cloudbd, на PL/SQL: пакет `NMON_SRCH`
(`modules/netmon/sql/cloudbd/301_nmon_srch_pkg.sql`). Тексты не уходят из
офиса: индекс лежит в той же базе, где OTRS и вики.

| Возможность | Как |
|---|---|
| Номер заявки | 8–20 цифр в запросе — заявка находится сразу, первой в списке |
| Все слова | каждое слово ищется точно (вес ×3), по основе (`принтера` → `принтер%`) и с опечаткой (`fuzzy`) |
| Не та раскладка | ничего не нашлось — запрос переводится в другую раскладку: `ghbynth` → `принтер`, `щкфсду` → `oracle`; показывается «результаты для …» |
| Часть слов | нет документа со всеми словами — ищутся документы с частью слов, больше совпадений — выше |
| Вес | совпадение в заголовке ×2, фраза целиком ×2; свежие документы, страницы вики и открытые заявки чуть выше |
| Регистр, ё, диакритика | не важны: `BASE_LETTER`, ё = е; румынские ă ș ț снимает приложение (в кодировке базы их нет) |
| Служебные слова | ru/ro/en стоп-слова не мешают (`и`, `на`, `pentru`, `the`…) |
| Фрагмент | `CTX_DOC.SNIPPET` с подсветкой найденного |
| Ссылки | оригинальные: заявка — `https://otrs.una.md/otrs/index.pl?Action=AgentTicketZoom;TicketID=…`, страница — `https://xwiki.una.md/bin/view/<раздел>/<страница>` (+ `?language=ro` для перевода) |
| Пароли | в текстах писем пароли заменяются на `[скрыто]` ещё при индексации |
| Журнал | каждый запрос — в `NMON_SRCH_LOG`: что ищут и что не находится |

### Объекты Oracle (база cloudbd, схема OTRS, префикс `NMON_SRCH_`)

| Объект | Что |
|---|---|
| `NMON_SRCH_DOC` | документ поиска: заявка (все письма подряд) или страница вики (каждый язык отдельно); реквизиты для показа и ссылка |
| `NMON_SRCH_DOC_CTX` | полнотекстовый индекс Oracle Text на `NMON_SRCH_DOC.BODY`; разделы T (заголовок), M (реквизиты), B (текст) |
| `NMON_SRCH_SYNC` | состояние обновления по источнику; строка служит замком от двух обновлений сразу |
| `NMON_SRCH_LOG` | журнал запросов, только добавление |
| `NMON_SRCH_HIT`, `NMON_SRCH_HITS` | типы строки результата |
| `NMON_SRCH` | пакет: `search`, `refresh`, `optimize`, разбор запроса |
| `NMON_SRCH_LEXER`, `_WL`, `_STOP`, `_SG` | настройки Oracle Text |

Почему так:

* **Индекс — на своей копии текстов, не на `OTRS.ARTICLE`.** Сломанный
  доменный индекс запрещает вставку в таблицу: OTRS перестал бы принимать
  письма. Копия весит ~200 МБ в табличном пространстве USERS (свободно 44 ГБ).
* **Таблицы OTRS и XWIKI только читаются** — это проверяет тест
  `test_search_sql_never_writes_otrs_or_xwiki_and_grants_nothing`.
* **Новых учёток и прав нет.** Отдельная схема потребовала бы выдать права в
  боевой базе; объекты лежат в схеме OTRS под своим префиксом и удаляются
  одним скриптом `399_nmon_srch_drop.sql`.

### Обновление индекса

* Заявка попадает в обновление, если изменилась сама или в ней появилось
  письмо (по номеру письма — индекс `ARTICLE_PK`, без полного просмотра).
  Страницы вики — по дате изменения; удалённые и переименованные уходят.
* Поиск сам запускает догрузку фоном, если индекс старше 10 минут, — не
  чаще раза в 2 минуты. Кнопка «Обновить индекс» — то же вручную.
* Постоянного задания в базе (`DBMS_SCHEDULER`) не заводилось: если поиском
  долго не пользоваться, индекс просто догрузится при первом запросе.

### API

| Метод | Адрес | Что |
|---|---|---|
| GET | `/UNA.md/orasldev/netmon/api/search?q=&src=OTRS\|XWIKI&open=1\|0&off=&order=rank\|date` | результаты (по 20) и состояние индекса; пустой `q` — только состояние |
| POST | `/UNA.md/orasldev/netmon/api/search/refresh` (`?full=1` — с нуля) | догрузить индекс фоном |

Под входом и только из внутренней сети (как весь модуль). Если пакет ещё не
установлен, API отвечает 503 с подсказкой, чем его поставить.
