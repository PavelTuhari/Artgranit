Пошаговый порядок работ для исполнителя. Каждый шаг содержит команды и проверку результата. Простоя мониторинга нет: старый сервер работает до последнего шага, откат возможен на любом этапе.

Куда

Подготовка

Ничего не меняется, простоя нет. Задача — получить страховку: дамп, файлы и независимую выгрузку конфигурации.
0.1

Снять полный дамп базы

Дамп — единственная страховка на весь проект. Снимается на работающей системе, простоя не требует.

ssh root@192.168.0.110
mysqldump -uroot --single-transaction --quick --default-character-set=utf8 \
          --routines --triggers zabbix | gzip > /root/zabbix34-$(date +%F).sql.gz
ls -lh /root/zabbix34-*.sql.gz
gunzip -t /root/zabbix34-*.sql.gz && echo 'архив цел'
Проверка: Файл 300–400 МБ, проверка целостности без ошибок.
0.2

Сохранить скрипты и конфигурацию

Внешние скрипты и alert-скрипт Telegram в базе не лежат — только файлами. Токен бота находится внутри telegram_bot.sh.

ssh root@192.168.0.110
tar czf /root/zabbix34-files-$(date +%F).tar.gz \
    /etc/zabbix /usr/lib/zabbix/externalscripts /usr/lib/zabbix/alertscripts
ls -lh /root/zabbix34-files-*.tar.gz
Проверка: Архив создан, внутри 8 внешних скриптов и telegram_bot.sh.
0.3

Выгрузить конфигурацию через API

Вторая, независимая от дампа копия конфигурации — на случай, если апгрейд схемы не удастся и придётся собирать систему заново.

cd /Users/pt/Projects.AI/Artgranit-netmon
python modules/netmon/scripts/netmon_zabbix_export.py --out ~/zbx-export
Проверка: 53 шаблона и 75 хостов в XML, файл inventory.json со списком.
0.4

Освободить память на гипервизоре

Кэш ZFS занимает 78,7 ГБ из 157 ГБ. Он отдаёт память сам, но при старте новой ВМ возможна просадка ввода-вывода — лучше ограничить заранее.

ssh root@192.168.0.149
echo 68719476736 > /sys/module/zfs/parameters/zfs_arc_max
echo 'options zfs zfs_arc_max=68719476736' >> /etc/modprobe.d/zfs.conf
update-initramfs -u
Проверка: cat /sys/module/zfs/parameters/zfs_arc_max → 68719476736

Развёртывание

Создаётся новая машина рядом с работающей системой. Старый сервер не затрагивается.
1.1

Создать виртуальную машину

KVM, а не контейнер: на Proxmox 4.4-1 ядро 4.4, и контейнер с Ubuntu 22.04 не запустится. У виртуальной машины собственное ядро.

ssh root@192.168.0.149
qm create 141 --name zabbix8 --memory 8192 --cores 4 --sockets 1 \
  --net0 virtio,bridge=vmbr0 --ostype l26 --machine pc-i440fx-2.7 \
  --scsihw virtio-scsi-pci --scsi0 local-zfs:100,discard=on \
  --ide2 local:iso/ubuntu-22.04.3-live-server-amd64.iso,media=cdrom \
  --boot order='ide2;scsi0' --onboot 1 --agent 1
qm start 141
Проверка: qm status 141 → running; консоль открывается в веб-интерфейсе Proxmox.
1.2

Установить Ubuntu и задать сеть

Адрес 192.168.0.111 свободен: он закреплён за контейнером 130 «zabbixt», который остановлен и помечен как неиспользуемый.

# в установщике Ubuntu:
#   IP       192.168.0.111/24
#   шлюз     192.168.0.101
#   DNS      192.168.0.103, 192.168.0.102
#   имя      zabbix8
# после установки:
apt update && apt -y upgrade && apt -y install qemu-guest-agent
systemctl enable --now qemu-guest-agent
Проверка: ping 192.168.0.111 проходит; в Proxmox у ВМ отображается IP.
1.3

Поставить СУБД и создать базу

Кодировка сразу utf8mb4: Zabbix 8.0 LTS корректно работает только с ней, а старая база в utf8. Пароль — случайный, не «zabbix», как сейчас.

apt -y install mariadb-server
PW=$(openssl rand -base64 24)
echo "пароль БД: $PW"   # записать в Keychain, в файлы не класть
mysql -uroot <<SQL
CREATE DATABASE zabbix CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;
CREATE USER zabbix@localhost IDENTIFIED BY '$PW';
GRANT ALL ON zabbix.* TO zabbix@localhost;
SET GLOBAL log_bin_trust_function_creators = 1;
SQL
Проверка: SHOW CREATE DATABASE zabbix содержит utf8mb4.
1.4

Поднять лимиты СУБД под импорт

На старом сервере max_allowed_packet = 1 МБ. С таким значением импорт истории оборвётся на первой же крупной строке.

cat >> /etc/mysql/mariadb.conf.d/99-zabbix.cnf <<CNF
[mysqld]
max_allowed_packet = 64M
innodb_buffer_pool_size = 4G
innodb_file_per_table = ON
CNF
systemctl restart mariadb
mysql -uroot -e "SHOW VARIABLES LIKE 'max_allowed_packet'"
Проверка: max_allowed_packet = 67108864.
1.5

Установить Zabbix 8.0 LTS

Ubuntu 22.04 входит в матрицу поддержки Zabbix 8.0 — проверено в репозитории.

wget https://repo.zabbix.com/zabbix/8.0/release/ubuntu/pool/main/z/zabbix-release/\
zabbix-release_8.0-0.2+ubuntu22.04_all.deb
dpkg -i zabbix-release_8.0-*.deb && apt update
apt -y install zabbix-server-mysql zabbix-frontend-php zabbix-nginx-conf \
               zabbix-sql-scripts zabbix-agent2 fping snmp unixodbc
zabbix_server -V
Проверка: zabbix_server -V показывает 8.0.x.

Перенос базы

Переносится вся база целиком, с историей за 90 дней и трендами за год. Шаг 2.4 необратим — перед ним снимок ВМ.
2.1

Перенести дамп на новую машину

Передаётся 300–400 МБ по локальной сети.

scp root@192.168.0.110:/root/zabbix34-*.sql.gz /root/
scp root@192.168.0.110:/root/zabbix34-files-*.tar.gz /root/
ls -lh /root/zabbix34-*
Проверка: Оба архива на месте, размеры совпадают с исходными.
2.2

Импортировать базу с конвертацией кодировки

Дамп снят в utf8, а база создана в utf8mb4 — объявления кодировки заменяются на лету, иначе таблицы вернутся к старой кодировке.

zcat /root/zabbix34-*.sql.gz \
  | sed -e 's/CHARSET=utf8 /CHARSET=utf8mb4 /g' \
        -e 's/CHARSET=utf8;/CHARSET=utf8mb4;/g' \
        -e 's/COLLATE=utf8_bin/COLLATE=utf8mb4_bin/g' \
  | mysql -uroot zabbix
mysql -uroot zabbix -e "SELECT COUNT(*) FROM history; SELECT COUNT(*) FROM hosts;"
Проверка: 140 таблиц; число строк history совпадает со старым сервером; SHOW TABLE STATUS показывает utf8mb4_bin.
2.3

Прописать базу в конфигурации сервера

Переносим параметры, отличающиеся от стандартных: они подобраны под текущую нагрузку и на новом сервере нужны те же.

cat >> /etc/zabbix/zabbix_server.conf <<CFG
DBPassword=<пароль из шага 1.3>
StartPollers=20
StartPollersUnreachable=10
StartPingers=5
StartDiscoverers=5
StartHTTPPollers=5
CacheSize=256M
Timeout=30
CFG
Проверка: Файл без опечаток; пароль совпадает с созданным.
2.4

Запустить сервер — пойдёт апгрейд схемы 3.4 → 8.0

необратимо

Ключевой шаг. Zabbix 8.0 поддерживает прямой апгрейд начиная с версии 2.0, поэтому промежуточные версии не нужны. На 11 млн строк истории займёт от 30 до 90 минут. Старый сервер в это время продолжает работать.

ssh root@192.168.0.149 'qm snapshot 141 before-db-upgrade'   # снимок ДО запуска
systemctl start zabbix-server
tail -f /var/log/zabbix/zabbix_server.log | grep -i 'database upgrade'
Проверка: В логе «database upgrade fully completed»; SELECT mandatory FROM dbversion показывает версию 8.0, а не 3040000.
2.5

Вернуть внешние скрипты

Скрипты в базе не хранятся. Пять из восьми обращаются к Oracle через sqlplus или cx_Oracle, им нужен клиент либо переписывание.

tar xzf /root/zabbix34-files-*.tar.gz -C /
chown -R zabbix:zabbix /usr/lib/zabbix/externalscripts
chmod 750 /usr/lib/zabbix/externalscripts/*
ls -l /usr/lib/zabbix/externalscripts/
Проверка: 8 скриптов на месте, владелец zabbix, права на запуск.
2.6

Портировать pyora.py на Python 3

Единственная работа, требующая написания кода: скрипт написан на Python 2.7 с cx_Oracle, а в Ubuntu 22.04 интерпретатора python2 нет. Библиотека oracledb в тонком режиме не требует Oracle Instant Client.

apt -y install python3-pip
pip3 install oracledb
# в скрипте: import cx_Oracle  →  import oracledb as cx_Oracle
#            print "x"        →  print("x")
#            cx_Oracle.connect(...) работает без клиента в тонком режиме
sudo -u zabbix /usr/lib/zabbix/externalscripts/pyora.py --help
Проверка: Скрипт запускается и возвращает значение, а не трассировку.
2.7

Вернуть отправку в Telegram

Alert-скрипт содержит токен бота. Канал и действие уже перенеслись вместе с базой — их создавать заново не нужно.

chmod 750 /usr/lib/zabbix/alertscripts/telegram_bot.sh
chown zabbix:zabbix /usr/lib/zabbix/alertscripts/telegram_bot.sh
sudo -u zabbix /usr/lib/zabbix/alertscripts/telegram_bot.sh \
     -1001544437696 'Проверка' 'Тест с нового сервера Zabbix 8.0'
Проверка: Сообщение появилось в канале «Zabbix Alert: Unisim-Soft&Coninfo».
2.8

Включить веб-интерфейс

Фронтенд на nginx + PHP-FPM 8.1 из репозитория Ubuntu.

sed -i 's/# listen 8080;/listen 80;/; s/# server_name example.com;/server_name 192.168.0.111;/' \
    /etc/zabbix/nginx.conf
systemctl restart nginx php8.1-fpm
systemctl enable zabbix-server zabbix-agent2 nginx php8.1-fpm
curl -I http://192.168.0.111/
Проверка: Открывается веб-интерфейс; вход существующими учётными записями работает — пароли перенеслись вместе с базой.

Параллельная работа

Две недели оба сервера работают одновременно. Это и проверка, и путь отката.
3.1

Направить агенты на оба сервера

Пассивные проверки заработают сразу, активным (282 элемента) нужен ServerActive. Пока указаны оба сервера, данные собирают обе системы.

# на каждом наблюдаемом хосте, в /etc/zabbix/zabbix_agentd.conf:
#   Server=192.168.0.110,192.168.0.111
#   ServerActive=192.168.0.110,192.168.0.111
systemctl restart zabbix-agent
Проверка: На новом сервере элементы получают значения; в «Последних данных» идут числа.
3.2

Сверить полноту сбора

Расхождение больше 5 % означает, что часть проверок на новом сервере не работает — искать причину до переключения.

# на обоих серверах:
mysql -uroot zabbix -e "SELECT COUNT(*) FROM items WHERE status=0 AND state=0"
# и сравнить значения
Проверка: Число работающих элементов отличается не более чем на 5 %.
3.3

Проверить приёмочными тестами

Готовый прогон проверяет покрытие, доставку уведомлений и безопасность.

cd /Users/pt/Projects.AI/Artgranit-netmon
# в modules/netmon/sources.py заменить ZBX_URL на новый сервер
python modules/netmon/scripts/netmon_selftest.py --json /tmp/after.json
Проверка: 0 отказов. Замечание SEC-07 про устаревшую версию должно исчезнуть.

Переключение

Старый сервер выводится из работы, но не удаляется.
4.1

Остановить отправку уведомлений со старого сервера

Иначе два сервера будут слать в один канал дубли.

# на СТАРОМ сервере, в веб-интерфейсе:
#   Administration → Actions → Telegram → Disabled
# либо через API
Проверка: В канал приходит по одному сообщению на событие, а не по два.
4.2

Убрать старый сервер из агентов

После этого мониторинг полностью работает на новом сервере.

# в /etc/zabbix/zabbix_agentd.conf оставить только новый:
#   Server=192.168.0.111
#   ServerActive=192.168.0.111
systemctl restart zabbix-agent
Проверка: На новом сервере данные продолжают поступать, на старом — прекратились.
4.3

Остановить старый сервер, контейнер не удалять

необратимо

Контейнер остаётся выключенным как страховка. Удалять — не раньше чем через 90 дней и только после архивации.

ssh root@192.168.0.110 'systemctl stop zabbix-server && systemctl disable zabbix-server'
ssh root@192.168.0.149 'pct stop 101'
Проверка: Новый сервер собирает данные, уведомления приходят, старый выключен.

Если что-то пошло не так

Старый сервер работает до шага 4.3, поэтому откат почти всегда бесплатный.

СитуацияЧто делатьВремя
Новый сервер не собирает данныеПродолжаем на старом, разбираемся без спешки0 мин
Импорт базы упалУдалить базу, создать заново, повторить шаг 2.2 — дамп не пострадал40 мин
Апгрейд схемы (2.4) прервалсяВосстановить снимок before-db-upgrade и повторить; при повторной неудаче — собирать систему из выгрузки шага 0.320 мин
Уведомления не уходятВключить обратно действие на старом сервере5 мин
Нужно вернуть всёЗапустить zabbix-server на CT 101, вернуть агентам старый адрес30 мин
Чего не делать. Не удалять контейнер 101 и его дамп раньше чем через 90 дней. Не запускать оба сервера с включённым действием «Telegram» дольше необходимого — пойдут дубли. Не копировать файлы базы напрямую: на старом сервере innodb_file_per_table = OFF, все данные в общем ibdata1, перенос возможен только логическим дампом.

После миграции

Работы, которые логично сделать сразу, пока система в фокусе:

  • Вычистить мусор. Вместе с базой перенеслись 72 неработающих элемента, 87 неопрашиваемых JMX и 13 выключенных хостов. По каждому — решение: чиним или удаляем.
  • Настроить резервное копирование. Регулярного бэкапа базы Zabbix сейчас нет; достаточно ежедневного дампа конфигурации (21 МБ) с хранением 30 копий.
  • Java gateway. Поставить и вернуть JMX-мониторинг либо осознанно отказаться.
  • Шифрование агентов. Zabbix 8.0 поддерживает PSK; сейчас трафик открыт.
  • Вынести мониторинг с PROXMOX3. Сейчас падение гипервизора лишает и сервисов, и наблюдения за ними.
