## Как устроен этот OTRS — то, на чём построены списки

OTRS 2.x, база — схема `OTRS` в Oracle cloudbd (`192.168.0.24`, SID `CLOUDBD`).

* **«Ответственный» не используется** — работа идёт через владельца.
  Передача исполнителю — смена владельца: `ticket_history`, тип
  `OwnerUpdate` (23), `name = '%%логин%%id'`, `create_by` — кто передал.
* **Журнал работ `XUSERWORK`** — самописный; связь с заявкой по номеру
  (`ticket.tn`), а не по `id`.
* Пользователи — `system_user` (в этой версии нет таблицы `users`).
* Штатных статусов «на закрытие» и «вернули» нет — поэтому признак по
  журналу работ. Он не идеальный: исполнитель мог поработать и не записать.
  Поэтому рядом показан его последний комментарий из журнала.
* Отправитель письма: `article_sender_type` 1 — сотрудник, 3 — клиент.

## Как подключается

Cloudbd — Oracle 11g, тонкий режим python-oracledb к нему не подходит.
Запросы идут через толстый процесс `models/biro26_worker.py` (как у Biro26
и ServOuts26), все три — одним запуском, ~11 с. Результат держится минуту.
Кнопка «Обновить» — мимо кэша. Пароль базы — Keychain
`oracle-cloudbd-otrs` (учётка `otrs`) или переменная `NETMON_OTRS_DB_PASSWORD`.
Логин владельца — `NETMON_OTRS_LOGIN`, по умолчанию `ptuhari`.

Окна (константы в `modules/netmon/otrs_board.py`): вернувшиеся — 90 дней,
ответы клиентов и новые — 30 дней, «без движения» — 180 дней.
