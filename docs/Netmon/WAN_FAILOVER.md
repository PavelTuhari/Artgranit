# Два канала: если МТС лежит — всё работает через Orange

Задача владельца 03.11.2026, после аварии канала МТС
([INCIDENT_2026-11-03_WAN.md](INCIDENT_2026-11-03_WAN.md)): «сделай, чтобы всё
работало универсально и прозрачно: если МТС не работает, всё работает через Orange».

## Как было

| Что | МТС (93.115.136.18–22, пять адресов) | Orange (195.22.241.126, один адрес) |
|---|---|---|
| Выход офиса в интернет | основной | запасной, переключается сам (check-gateway) |
| Ответы на входящие | через тот же канал (mangle, уже было) | через тот же канал (mangle, уже было) |
| Пробросы портов (dst-nat) | почти все | только 80/443/8003 → nginx .148, 21, 22, почта другого домена |
| DNS una.md (`@`, `*`, `www`) | 93.115.136.18 | — |
| Профили OpenVPN | `remote 93.115.136.18 1194` | — |

Изнутри офиса авария незаметна, а снаружи пропадало всё, что смотрит на адрес
МТС. При этом 03.11.2026 снаружи `https://otrs.una.md` и `https://xwiki.una.md`
через адрес Orange отвечали **200**, недоставало только записи DNS.

## Что сделано

| Слой | Что | Где | Переключение |
|---|---|---|---|
| Маршрутизатор | Зеркальные пробросы на Orange для всех портов МТС, свободных на Orange: OpenVPN udp 1194, DNS 53 tcp/udp, WireGuard, 8080, 8083, 2626, 1521/1522, 47474, 2555 | `modules/netmon/scripts/netmon_wan_failover.py` | постоянно открыты на обоих адресах |
| DNS | Вторые записи A на Orange для `@`, `*`, `www` (закрывают otrs, xwiki, vpn и все имена под `*`); Orange добавлен в SPF | `modules/netmon/scripts/netmon_dns_failover.py`, зона `/etc/named/una.md` на 192.168.0.148 | браузер получает два адреса; если первый не отвечает, переходит на второй |
| OpenVPN | В каждом выдаваемом профиле две строки `remote` (МТС, затем Orange) и `server-poll-timeout 10` | `modules/netmon/openvpn.py` → `with_failover()` | клиент сам уходит на Orange через 10 секунд |
| L2TP/IPsec | Рядом с адресом сервера показывается запасной адрес Orange | `modules/netmon/mikrotik.py` → `server_backup`, панель «Выдать доступ» | вручную: Windows и Apple хранят один адрес |
| Мониторинг | GW MTC, «канал МТС не работает», «оба канала не работают», OTRS | `netmon_zabbix_wan.py` (уже заведено) | оповещение |

## Имена каналов: canal1 и canal2

Владелец 03.11.2026: «создай canal1.una.md для МТС и canal2.una.md для Orange,
чтобы всё снаружи настраивалось на эти два адреса».

| Имя | Адрес | Канал |
|---|---|---|
| `canal1.una.md` | 93.115.136.18 | МТС |
| `canal2.una.md` | 195.22.241.126 | Orange |

Профили OpenVPN: `remote canal1.una.md 1194`, `remote canal2.una.md 1194` и
третьей строкой `remote 195.22.241.126 1194`. Голый адрес Orange нужен, пока
ns2 (remsys) отвечает на любое имя адресом МТС (см. ниже). При выдаче L2TP
сервером указывается `canal1.una.md`, запасным `canal2.una.md`.

## Почта una.md через Orange

Порт 25 на Orange раньше вёл на почту garileauto.md (172.29.0.23). Владелец
03.11.2026: «не актуально, можно открыть для почты una.md». Пробросы 25/143/587
на 172.29.0.23 **выключены, а не удалены**, `--rollback` включает их обратно.
Теперь 25 на Orange ведёт на тот же фильтр ASSP 192.168.0.131:2525, что и mx2.
В зоне добавлены `mx4.una.md → 195.22.241.126` и `MX 40 mx4.una.md`. У ns2
`mx4` с адресом Orange уже был, поэтому в аварию МТС почта приходит через Orange.

## Что само не переключается и почему

1. **Порты, занятые на Orange другим сервисом.** У Orange один адрес, у МТС пять.
   80/443 на Orange ведут на nginx 192.168.0.148, поэтому сайты, которые на МТС
   живут на других серверах (bonus и его соседи → .146, linktickets → .147,
   mail.una.md → .104), через Orange по одному адресу не пройдут, пока nginx
   на .148 не начнёт проксировать их по имени (SNI). Входящая почта на 25 порту
   Orange занята почтой другого домена. Скрипт печатает весь такой список (`!`).
2. **Вторичный DNS ns2.una.md (178.175.140.131, remsys).** Его копия зоны своя
   (серийный номер 2014042244), с ns1 она не синхронизируется. Во время аварии МТС
   ns1 недоступен, отвечает только ns2, а он на любое неизвестное имя (в том числе
   `canal2`) отвечает адресом МТС 93.115.136.18. Поэтому записи Orange и `canal1`/`canal2` нужно добавить и там,
   либо попросить remsys брать зону с ns1 по обоим адресам (93.115.136.19 и
   195.22.241.126 после зеркального проброса 53). Это внешнее действие, оно за владельцем.
3. **Уже выданные профили OpenVPN** содержат один адрес. Новый профиль с двумя
   адресами выдаётся автоматически; уже выданным достаточно скачать файл заново
   (панель → OpenVPN → «Профиль»). Сертификат при этом не меняется.
4. **Обратная запись (PTR) адреса Orange** для почты задаётся у провайдера Orange.
   Без неё часть почтовых серверов хуже принимает письма, отправленные через Orange.

## Запуск и откат

Сначала пробный прогон: он ничего не меняет и показывает план.

```bash
cd /Users/pt/Projects.AI/Artgranit-netmon
../Artgranit/venv/bin/python modules/netmon/scripts/netmon_wan_failover.py --dry-run
../Artgranit/venv/bin/python modules/netmon/scripts/netmon_dns_failover.py --dry-run
```

Применение: маршрутизатор перед правкой сам сохраняет выгрузку
`netmon-before-failover-ДАТА.rsc`, зона сохраняется в `una.md.bak-ДАТА-failover`
и проверяется `named-checkzone`.

```bash
../Artgranit/venv/bin/python modules/netmon/scripts/netmon_wan_failover.py
../Artgranit/venv/bin/python modules/netmon/scripts/netmon_dns_failover.py
```

Откат: все правила маршрутизатора помечены `FAILOVER-ORANGE`, зона возвращается из копии.

```bash
../Artgranit/venv/bin/python modules/netmon/scripts/netmon_wan_failover.py --rollback
../Artgranit/venv/bin/python modules/netmon/scripts/netmon_dns_failover.py --rollback
```

## Проверка снаружи

С облачного сервера (не из офиса: изнутри ответы идут в обход NAT):

```bash
ssh -i ~/.ssh/artgranit-oci.key ubuntu@92.5.3.187 \
  'curl -sk -o /dev/null -w "%{http_code}\n" --resolve otrs.una.md:443:195.22.241.126 https://otrs.una.md/otrs/index.pl'
```

Ожидается `200`. Для OpenVPN: профиль с двумя `remote` подключается при
выключенном МТС (в журнале клиента видна попытка .18, затем успех на .126).
