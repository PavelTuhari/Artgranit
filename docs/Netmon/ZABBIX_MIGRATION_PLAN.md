# План миграции Zabbix 3.4.15 → Zabbix 8.0 LTS

Документ подготовлен 12.09.2026 по результатам обследования действующей
системы мониторинга. Все цифры получены с боевых систем, не оценочные.

Связанные документы: [MONITORING_SYSTEM.md](MONITORING_SYSTEM.md) — как устроена
система сейчас; [TEST_REPORT.html](TEST_REPORT.html) — акт испытаний, где
устаревшая версия зафиксирована как замечание SEC-07.

---

## 1. Резюме и рекомендация

**Обновление «на месте» невозможно.** Действующий Zabbix 3.4.15 работает на
CentOS 7.9 с MariaDB 5.5 и PHP 5.6 — все три компонента сняты с поддержки
(CentOS 7 — 30.06.2024, MariaDB 5.5 — 2020, PHP 5.6 — 2018). Zabbix 8.0
требует PHP 8.0+ и MariaDB 10.5+ / MySQL 8.0.30+; поднять их на CentOS 7
штатными средствами нельзя.

**Рекомендуемый вариант — новая виртуальная машина KVM на том же
гипервизоре PROXMOX3** с Ubuntu 22.04 LTS и Zabbix 8.0 LTS, с параллельной
работой старого и нового сервера в течение 2 недель.

Обоснование выбора именно KVM, а не контейнера LXC, — в разделе 4: на
PROXMOX3 стоит Proxmox 4.4 с ядром 4.4, и контейнер с современной ОС на нём
попросту не запустится, тогда как у виртуальной машины собственное ядро.
Совместимость подтверждена практикой: на этом же хосте уже работает
ВМ 120 `ubuntu22`.

| Параметр решения | Значение |
|---|---|
| Куда | KVM-ВМ на PROXMOX3 (`192.168.0.149`), хранилище `local-zfs` |
| ОС | Ubuntu 22.04.3 LTS (ISO уже загружен на гипервизор) |
| Zabbix | 8.0 LTS, пакеты из `repo.zabbix.com` (Ubuntu 22.04 поддерживается) |
| СУБД | MariaDB 10.6 из репозитория Ubuntu |
| Ресурсы ВМ | 4 vCPU, 8 ГБ RAM, 100 ГБ диск |
| Данные | **база переносится целиком**: вся история (90 дней) и тренды (365 дней) сохраняются |
| Простой мониторинга | **0 минут** (старый сервер работает до переключения) |
| Трудоёмкость | 3 рабочих дня работ + 2 недели параллельной работы |

## 3. Почему нельзя обновиться на месте

Три независимые блокировки, каждой достаточно:

1. **PHP.** Zabbix 8.0 frontend требует PHP ≥ 8.0. На CentOS 7 штатный
   PHP — 5.6; сборки 8.x есть только в сторонних репозиториях (Remi) и
   тянут за собой конфликт зависимостей с системным Apache.
2. **СУБД.** Zabbix 8.0 требует MariaDB ≥ 10.5 (или MySQL ≥ 8.0.30).
   Установленная MariaDB 5.5 отличается на 5 мажорных версий; апгрейд
   5.5 → 10.6 внутри CentOS 7 — отдельный рискованный проект.
3. **ОС.** CentOS 7 не получает обновлений с 30.06.2024. Строить новый
   сервер мониторинга на снятой с поддержки ОС — значит сразу закладывать
   следующую миграцию.

Дополнительно: контейнер LXC с CentOS 7 **нельзя** обновить «внутри» до
Ubuntu 22.04 — это смена дистрибутива, а не обновление.

## 4. Выбор площадки: три варианта

### Вариант A (рекомендуется). Новая KVM-ВМ на PROXMOX3

**Плюсы:** гипервизор уже есть; ресурсы есть (см. 5.2); собственное ядро ВМ
не зависит от старого ядра хоста; совместимость доказана работающей
ВМ 120 `ubuntu22`; старый сервер остаётся рядом для параллельной работы.

**Минусы:** PROXMOX3 сам устарел (PVE 4.4, 2016 г.) и является единой точкой
отказа — на нём же работает старый Zabbix. QEMU 2.7 не поддерживает
современные типы машин, ставить придётся с `machine=pc-i440fx-2.7`.

**Ограничение по ресурсам:** RAM хоста 157 ГБ, гостям выделено ≈ 82 ГБ,
кэш ZFS ARC занимает 78,7 ГБ. Свободно по `MemAvailable` — 17,2 ГБ.
ARC ужимается автоматически, но правильнее ограничить его явно
(см. 5.2), освободив запас под новую ВМ.

### Вариант B. LXC-контейнер с современной ОС — **невозможен**

На PROXMOX3 ядро 4.4 (2016 г.). Контейнер разделяет ядро с хостом, а
systemd версий 247+ (Ubuntu 22.04, Debian 12) требует унифицированной
иерархии cgroup v2, которой в ядре 4.4 нет. Такой контейнер не стартует.
Подтверждение: в хранилище шаблонов PROXMOX3 лежат только CentOS 6/7 и
Debian 8 — новее туда просто не ставили.

Вариант становится возможным только после обновления самого Proxmox, что
является отдельным проектом с остановкой всех 30+ гостей.

### Вариант C. Отдельный физический или облачный сервер

**Плюсы:** мониторинг перестаёт зависеть от наблюдаемой им же
инфраструктуры — правильная практика: сейчас Zabbix живёт на PROXMOX3 и
при падении этого хоста мы теряем и сервисы, и наблюдение за ними.

**Минусы:** требует закупки/выделения оборудования.

**Рекомендация:** выбрать вариант A сейчас, а вынос мониторинга на
независимую площадку заложить в план как отдельную задачу.

## 5. Технические требования к новой виртуальной машине

### 5.1 Конфигурация ВМ

| Параметр | Значение | Обоснование |
|---|---|---|
| VMID | `141` (свободен; занятые — до 140) | — |
| Имя | `zabbix8` | — |
| vCPU | **4** (`cores: 4`, `sockets: 1`) | текущая нагрузка ≈ 43 значения/сек при 2 561 элементе; 4 ядра дают трёхкратный запас под рост до 200+ хостов |
| Тип CPU | `kvm64` или `host` | QEMU 2.7; `host` быстрее, но мешает миграции между узлами — узел один, поэтому допустимо |

| Диск | **100 ГБ**, `local-zfs`, формат raw, `discard=on` | БД сейчас 1,5 ГБ; при удвоении числа хостов и той же глубине хранения — ~15 ГБ; 100 ГБ покрывают 5+ лет |
| Сеть | `virtio`, мост `vmbr0` | сеть офиса 192.168.0.0/24 |
| IP | **192.168.0.111/24**, шлюз `192.168.0.101` | адрес освобождается: закреплён за неиспользуемым CT 130 `zabbixt` (остановлен, в описании «not used») |
| DNS | `192.168.0.103`, `192.168.0.102` | как у действующего контейнера |
| Тип машины | `pc-i440fx-2.7` | QEMU 2.7 не знает более новых |
| Загрузка | ISO `ubuntu-22.04.3-live-server-amd64.iso` | уже лежит в `/var/lib/vz/template/iso/` |
| Автозапуск | `onboot: 1` | мониторинг должен подниматься сам |

Команда создания (выполняется на PROXMOX3):

```bash
qm create 141 --name zabbix8 --memory 8192 --cores 4 --sockets 1 \
  --net0 virtio,bridge=vmbr0 --ostype l26 --machine pc-i440fx-2.7 \
  --scsihw virtio-scsi-pci --scsi0 local-zfs:100,discard=on \
  --ide2 local:iso/ubuntu-22.04.3-live-server-amd64.iso,media=cdrom \
  --boot order='ide2;scsi0' --onboot 1 --agent 1
qm start 141
```

### 5.2 Подготовка гипервизора

Кэш ZFS ARC занимает 78,7 ГБ при лимите 78,7 ГБ. Он отдаёт память под
запросы гостей, но при старте ВМ на 8 ГБ возможна кратковременная
деградация ввода-вывода. Рекомендуется заранее ограничить ARC 64 ГБ:

```bash
echo "options zfs zfs_arc_max=68719476736" >> /etc/modprobe.d/zfs.conf
update-initramfs -u          # применится после перезагрузки хоста
echo 68719476736 > /sys/module/zfs/parameters/zfs_arc_max   # сразу, без перезагрузки
```

**Отдельно и срочно, вне рамок миграции:** хранилище `storage` заполнено
на **99,22 %**, `ctx` — на 98,93 %. Это уже висит в Zabbix как Disaster.
Новую ВМ размещаем на `local-zfs` (свободно 5,34 ТБ), но переполненные
пулы нужно разгружать независимо от миграции.

## 6. Стратегия переноса данных

### 6.1 Что переносим обязательно

1. **Конфигурация** (21,3 МБ): хосты, шаблоны, элементы, триггеры, графики,
   действия, пользователи, группы, веб-сценарии, карты.
2. **Внешние скрипты** (`/usr/lib/zabbix/externalscripts`, 8 файлов).
3. **Alert-скрипт Telegram** вместе с токеном бота — иначе уведомления
   не заработают.
4. **Настройки сервера** (`zabbix_server.conf`): `StartPollers=20`,
   `StartPingers=5`, `StartDiscoverers=5`, `StartHTTPPollers=5`,
   `CacheSize=256M`, `Timeout=30`.

### 6.2 Способ переноса — решение владельца от 12.09.2026

**Выбран перенос базы целиком с сохранением всей истории.** Вариант с
чистой установкой и переносом только конфигурации («быстрый путь») отклонён.

Хорошая новость, снимающая главный риск такого выбора: **Zabbix 8.0
поддерживает прямой апгрейд схемы начиная с версии 2.0** (проверено в
официальной документации 12.09.2026). Цепочка 3.4 → 5.0 → 6.0 → 7.0 → 8.0
**не нужна** — сервер 8.0 обновляет схему 3.4 за один проход при первом
запуске. Это превращает самый опасный этап в один управляемый шаг.

Порядок переноса:

1. Дамп базы на старом сервере (MariaDB 5.5).
2. Восстановление на новой ВМ в MariaDB 10.6 — с конвертацией кодировки.
3. Первый запуск `zabbix_server` 8.0 — он сам обновляет схему
   `dbversion` с `3040000` до версии 8.0 и пишет ход работы в лог.
4. Проверка: история и тренды на месте, графики за прошлый год рисуются.

### 6.3 Технические препятствия при переносе базы и как их обойти

Обследование выявило четыре несовместимости. Все устранимы, но каждую
нужно обработать явно — иначе импорт упадёт или Zabbix не стартует.

| # | Что обнаружено | Почему мешает | Как обходим |
|---|---|---|---|
| 1 | Кодировка базы **`utf8` / `utf8_bin`** (все 140 таблиц) | Zabbix 8.0 работает корректно только с **`utf8mb4` / `utf8mb4_bin`** | создать базу сразу в `utf8mb4`, дамп пропустить через замену `utf8;`→`utf8mb4;` и `utf8_bin`→`utf8mb4_bin` |
| 2 | **`innodb_file_per_table = OFF`** — все данные в общем `ibdata1` | файлы таблиц скопировать нельзя, только логический дамп | перенос строго через `mysqldump`, не копированием каталога |
| 3 | **`max_allowed_packet = 1 МБ`** | импорт больших строк истории оборвётся | на новом сервере поставить `max_allowed_packet = 64M` до импорта |
| 4 | `innodb_file_format = Antelope` (устаревший) | новые версии используют Barracuda | решается само при логическом импорте в MariaDB 10.6 |

Команды переноса:

```bash
# на старом сервере (192.168.0.110)
mysqldump -uroot --single-transaction --quick --default-character-set=utf8 \
          --routines --triggers zabbix | gzip > /root/zabbix34-$(date +%F).sql.gz

# на новой ВМ: конвертация кодировки на лету и импорт
zcat zabbix34-*.sql.gz \
  | sed -e 's/CHARSET=utf8 /CHARSET=utf8mb4 /g' \
        -e 's/CHARSET=utf8;/CHARSET=utf8mb4;/g' \
        -e 's/COLLATE=utf8_bin/COLLATE=utf8mb4_bin/g' \
  | mysql -uroot zabbix
```

Ожидаемое время: дамп 5–10 минут, передача по сети ≈ 300–400 МБ,
импорт 20–40 минут, автоматический апгрейд схемы 3.4 → 8.0 на 11 млн строк
истории — **от 30 до 90 минут**. На это время новый сервер недоступен, но
старый продолжает работать: простоя мониторинга по-прежнему нет.
