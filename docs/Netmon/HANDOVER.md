## 2. Доступы: где лежат пароли

**Пароли не хранятся в репозитории и не передаются в переписке.**
Первоисточник — macOS Keychain на рабочей машине владельца, бумажная
копия — `~/Documents/infra-passwords.md` (права 600).

Полный реестр доступов виден в панели:
https://nufarul.eminescu.md/UNA.md/orasldev/netmon — вкладка «Доступы».
Там сгруппировано по типам объектов и показано, **как достать** каждый
пароль, без самих значений.

| Что | Запись в Keychain | Команда |
|---|---|---|
| Zabbix (веб и API) | `zabbix-web` | `security find-generic-password -a Admin -s zabbix-web -w` |
| Гипервизор PROXMOX3 | `proxmox3-ssh` | `security find-generic-password -a root -s proxmox3-ssh -w` |
| Сервер Oracle | `192.168.0.24` | `security find-internet-password -a root -s 192.168.0.24 -w` |
| Контейнер Zabbix | `zabbix34-ct` | `security find-generic-password -a root -s zabbix34-ct -w` |
| Схемы Oracle | `oracle-cloudbd-<схема>` | `security find-generic-password -a <схема> -s oracle-cloudbd-<схема> -w` |
| Гости Proxmox | `pve-<имя машины>` | 30 записей, собраны из описаний ВМ |

### Что здесь не так и надо исправить

1. **В описаниях 18 виртуальных машин на гипервизоре записаны логины и
   пароли открытым текстом.** Их видит любой, у кого есть доступ к
   веб-интерфейсу Proxmox, и они попадают в резервные копии конфигурации.
   Пароли уже перенесены в Keychain; **из описаний их надо удалить, а сами
   пароли сменить** — считать скомпрометированными.
2. Пароль базы Zabbix — `zabbix`, словарный. Менять при миграции.
3. Доступ к базе `clouddev` **не найден ни под одной известной учёткой** —
   работаем через `sqlplus / as sysdba` на самом сервере. DBA должен завести
   себе учётную запись (раздел 7.2).

## 4. Сеть офиса

Подсеть **192.168.0.0/24**, шлюз и основной маршрутизатор —
**MikroTik 192.168.0.101**. Доступ снаружи только через **VPN93** (L2TP):
без туннеля ни один адрес `192.168.0.*` не откроется.

```bash
scutil --nc status "VPN93"   # проверить
scutil --nc start  "VPN93"   # поднять
```

Если в логе `/var/log/ppp.log` строка `incorrect user shared secret` —
общий ключ IPSec сбит; он лежит в системной связке ключей, из терминала не
читается, правится только вручную в настройках сети.

## 5. Виртуализация: PROXMOX3

| Параметр | Значение |
|---|---|
| Адрес | `192.168.0.149`, веб https://192.168.0.149:8006 |
| Версия | **Proxmox VE 4.4-1** (2016 г.), ядро 4.4.35 — снята с поддержки |
| Железо | 24 ядра, 157 ГБ ОЗУ, 2× Xeon E5-2620 v3 |
| Гостей | **51**: 35 виртуальных машин, 16 контейнеров; работают 20 |
| Хранилища | `local-zfs` 6,6 ТБ (занято 18 %), `storage` 3,6 ТБ (**99,2 %**), `ssd1` 430 ГБ (79 %), `ctx` (**98,9 %**) |

Паспорт каждой машины — в панели, вкладка «Proxmox: машины», клик по
строке. Там: процессор, память, диски, сеть, дата последней резервной
копии, роль из описания и **предлагаемое решение** (переносить, пересоздать
на новой ОС, списать).

### Важные ограничения

1. **Ядро 4.4 не поднимет современный контейнер LXC.** Debian 12 и
   Ubuntu 22.04 требуют cgroup v2. Новую систему ставить только
   виртуальной машиной (KVM) — у неё своё ядро. Подтверждено практикой:
   на этом же узле работает ВМ 120 `ubuntu22`.
2. Кэш ZFS ARC ограничен 64 ГБ (`/etc/modprobe.d/zfs.conf`). При нехватке
   памяти гостям он ужимается сам.
3. Температура процессоров: **норма до 73 °C**, троттлинг около 85 °C.
   Наблюдаемые 44–50 °C — обычный режим. Максимум за два года — 58 °C.

## 6. Резервное копирование — самое слабое место

**Регулярного резервного копирования фактически нет.**

| Что | Состояние |
|---|---|
| Виртуальные машины | 30 из 51 **без единой копии**; самая свежая — март 2024 |
| База Zabbix | копий нет |
| Базы Oracle | см. раздел 7.4 — уточнить у DBA |

Это первое, что надо поставить на поток. Место есть: на `local-zfs`
свободно 5,3 ТБ. Минимальный вариант — еженедельный `vzdump` работающих
гостей в режиме snapshot с уведомлением об ошибках.

## 7. Oracle — раздел для DBA

### 7.1 Что где стоит

Один сервер, **две базы**:

| Параметр | Значение |
|---|---|
| Сервер | `cloudbd.internal.uniacc.md` = **192.168.0.24**, снаружи `orange.una.md:4024` |
| Железо | 2× Intel Xeon E5-2623 v3 @ 3,00 ГГц |
| Базы | **`cloudbd`** (боевая) и **`clouddev`** (разработка) |
| Версия | Oracle **11.2.0.4** |
| Сервисы | `cloudbd.world`, `clouddev.world`, `cloudbdXDB.world` |
| Время работы | 71 день на день передачи |

Обе базы — **11g**, без поддержки Oracle с 2020 года. Это отдельный
разговор об обновлении.

**Ловушки версии 11g**, на которые уже напарывались:

- нет синтаксиса `FETCH FIRST n ROWS` (12c+) — только `ROWNUM`;
- `BY`, `LEVEL`, `SIZE`, `DATE` и прочие зарезервированные слова **нельзя
  использовать как имена bind-переменных**: `ORA-01745`. Ошибка неочевидная,
  ловили дважды;
- кодировка базы `utf8` / `utf8_bin`; при переходе на новые версии
  потребуется `utf8mb4`.

### 7.2 Доступы к базам

| База | Как заходим | Замечание |
|---|---|---|
| `cloudbd` | схемы `otrs`, `tickets`, `haruzdar2018` и др. из Keychain (`oracle-cloudbd-<схема>`) | у `haruzdar2018` нет прав на `V$SESSION` и `V$INSTANCE` |
| `clouddev` | **пароля нет ни к одной схеме**; работаем `sqlplus / as sysdba` с сервера по SSH | **задача DBA: завести себе учётку и положить в Keychain** |

Подключение к боевой базе идёт через **толстый клиент в отдельном процессе**
(`models/unisim_cassa.py`), потому что тонкий режим `python-oracledb` не
работает с 11g в этой конфигурации. Это не временный костыль, а рабочая
схема — не ломать.

### 7.3 Фронт-офисы: 39 торговых точек

Фронт-офис — это схема Oracle, под которой работает торговая точка или
контора. Сервер может быть жив, а конкретный магазин уже час как не
подключается: обычный мониторинг такого не покажет.

| База | Фронт-офисов | Сессий |
|---|---|---|
| `cloudbd` | **34** | 261 |
| `clouddev` | **5** | 19 |

Самые нагруженные: `RETAILMARKETS` (31 сессия), `AURUM` (28), `DORIMAX` (24),
`OFFICEPLUS` (21), `VITAC` (18), `PGSANAVIT` (15), `EUROSHOP23` (14),
`MOLLTEX18` (14). В `clouddev`: `GLASS`, `BONUS2019_07`, `BONUSPOS_SELF24`,
`DATACONTROL2025`, `USM26`.

**Все 39 заведены в Zabbix** 12.09.2026, группа **Front Office**, хосты
`cloudbd-db` и `clouddev-db`. По каждому фронт-офису — элемент «сессий» и
триггер: если сессий ноль дольше 30 минут, приходит уведомление
«фронт-офис не подключается». Порог в 30 минут выбран, чтобы перезагрузка
кассы не поднимала ложную тревогу.

Обновить список (например, когда добавится новая точка):

```bash
cd /Users/pt/Projects.AI/Artgranit-netmon
venv/bin/python modules/netmon/scripts/netmon_zabbix_frontoffice.py
```

Данные снимаются на самом сервере через `sqlplus / as sysdba`: у внешних
учётных записей нет прав на `V$SESSION`, а к `clouddev` пароля нет вовсе.

### 7.4 Что проверить DBA в первую неделю

1. **Диск `/mnt/md3` — свободно менее 10 %.** При 3 % база встанет. Что там
   лежит и что можно чистить — первый вопрос.
2. **Резервное копирование баз** — выяснить, настроено ли вообще (RMAN,
   экспорт, копии на другой узел), и проверить восстановление.
3. **Завести учётную запись в `clouddev`** и положить в Keychain, чтобы не
   ходить через `sysdba` с сервера.
4. **Archive Logs на Standby** — в Zabbix отключён шумевший триггер
   «Archive Logs are not applied on Vetropack Standby». Проверить, работает
   ли Standby на самом деле, и вернуть контроль осознанно.
5. **Мониторинг Oracle в Zabbix сломан:** 38 элементов типа «Database
   monitor» по хосту `192.168.0.18` не работают **все** (шаблон
   «Custom - Service - Oracle»). Либо чинить, либо убрать.
6. Внешние скрипты мониторинга Oracle лежат на контейнере Zabbix в
   `/usr/lib/zabbix/externalscripts/`: `pyora.py` (Python 2 + `cx_Oracle`),
   `cloudbd_count_sessions.sh`, `stanby_status.sh`, `gcc_stanby_status.sh`,
   `avpmr_count_messages.sh`. При миграции Zabbix их придётся переписать:
   `pyora.py` — на Python 3 и `oracledb`.

### 7.5 Известная поломка в почтовой очереди

В схемах `OTRS` и `TICKETS` есть процедура `send_email_api_php`, рассылающая
почту через PHP-шлюз. В ней было три дефекта (переполнение буфера
`varchar2(4000)`, утечка HTTP-дескрипторов, отсутствие повторов) — из-за
них молча терялись письма, в очереди висело 6613 штук с 2024 года.
**Исправлено 25.08.2026**, но тот же код есть ещё в схемах `UNI` (713
застрявших писем), `DORIMAX`, `HELIOS24` — туда доступа не было.

Подробности и готовое исправление: [../OTRS/MAIL_QUEUE_DIAGNOSIS.md](../OTRS/MAIL_QUEUE_DIAGNOSIS.md).

## 9. Мониторинг

### 9.1 Как устроен

| Слой | Чем |
|---|---|
| Сбор | Zabbix 3.4.15 в контейнере CT 101 на PROXMOX3, `192.168.0.110` |
| Хранение | MariaDB внутри контейнера, база 1,5 ГБ |
| Оповещение | скрипт `telegram_bot.sh` в Telegram |
| Канал | «Zabbix Alert: Unisim-Soft&Coninfo», 5 участников |
| Витрина | модуль `netmon` портала |

Веб: http://192.168.0.110/zabbix/ (через VPN93).

**Важно про действие «Telegram»:** у него нет условий по хостам, только по
уровню — average, high, disaster. Поэтому **любой новый триггер нужного
уровня автоматически попадает в канал**, донастройка не требуется. И
наоборот: неаккуратный триггер сразу создаёт шум.

### 9.2 Что стоит на мониторинге — 79 хостов

| Группа | Что |
|---|---|
| Linux servers, Oracle | ключевые серверы: cloudbd, PROXMOX3, apache, otrs |
| Office Auto-Discovered | 38 устройств офиса, заведены сканом |
| **Front Office** | `cloudbd-db`, `clouddev-db` — 39 торговых точек |
| **Office Facility** | 4 розетки и `facility-metrics` (кондиционеры, котёл, СКУД, лифт) |
| Business | `business-metrics` — домены и перерасход электроэнергии |

### 9.3 Температура процессоров — не путать

Пороги выставлены **по спецификации Intel**, а не по ощущениям:
внимание при **>73 °C**, высокая при **≥80 °C**, перегрев при **≥85 °C**.

Отдельно есть Telegram-бот на Blynk, где уставка осталась около 52 °C —
он шумит по ночам, хотя перегрева нет. Это **другая система**, к Zabbix
отношения не имеет; уставку менять там.

### 9.4 Zabbix пора менять

Версия 3.4.15 на CentOS 7 с MariaDB 5.5 и PHP 5.6 — всё снято с поддержки.
Подробный план перехода на Zabbix 8.0 LTS, с проверенными цифрами и
пошаговыми командами: [ZABBIX_MIGRATION_PLAN.md](ZABBIX_MIGRATION_PLAN.md).
Простоя мониторинга не требуется: старый сервер работает до переключения.

## 12. Чего в этом хозяйстве нет

Честный список пробелов — чтобы новая группа не искала того, чего не существует:

1. Нет регулярного резервного копирования (раздел 6).
2. Нет плана восстановления после аварии: что поднимать первым и за какое время.
3. Нет схемы физического размещения — какое устройство в какой комнате и
   розетке; помещения умных розеток не уточнены.
4. Нет описания, что именно делает каждая из 51 виртуальной машины: роли
   восстановлены из описаний, но три машины без описания вовсе.
5. Мониторинг не независим: живёт на том же гипервизоре, за которым следит.
6. Нет учёта лицензий и сроков поддержки оборудования.
