# Нагрузка сервера баз данных

Вкладка «Нагрузка БД» панели мониторинга —
http://127.0.0.1:3013/UNA.md/orasldev/netmon (локально и во внутренней сети).
Сделано 08.10.2026. Код — `modules/netmon/dbload.py`.

## Что показывает

Хост `cloudbd.internal.uniacc.md` (16 ядер, 64 ГБ), экземпляры Oracle 11.2.0.4
`cloudbd` и `clouddev`.

**Linux:** нагрузка (load average) против числа ядер, занятость процессора и
доля ожидания диска (vmstat), доступная память и swap, по каждому диску —
загрузка, задержка, чтение и запись (iostat -x, с подписью, что на диске).

**Кто грузит процессор прямо сейчас:** замер `top` за 2 секунды, каждый
процесс сопоставлен с сессией Oracle по `v$process.spid` — база, схема,
откуда подключена, какой SQL выполняет.

**По каждой базе:**

* показатели `v$sysmetric`: средняя активность (Average Active Sessions),
  транзакции, выполнения, чтения и записи в секунду;
* сессии, которые работают сейчас, дольше всех сверху: сколько идёт текущий
  вызов, на процессоре или чего ждёт, SQL, кого блокирует;
* тяжелее всех с момента входа — по процессору и по чтениям с диска;
* длинные операции (`v$session_longops`).

## Три вещи, на которых легко ошибиться

1. **`ps` не показывает нагрузку «сейчас».** `ps -o pcpu` — процессорное
   время, усреднённое за всю жизнь процесса: сессия, которая час назад вошла и
   последние секунды жжёт ядро, выглядит тихой. Поэтому `top` с двумя
   замерами.
2. **ACTIVE в `v$session` — ещё не работа.** Исполнители заданий и очередей
   висят ACTIVE в ожидании класса `Idle` (`jobq slave wait`). Из десяти ACTIVE
   реально работала одна. Такие сессии в список не попадают.
3. **Сессии с короткими вызовами** успевают стать неактивными между замером
   `top` и запросом к базе. Поэтому база спрашивается ровно о тех процессах,
   что показал `top` (`p.spid in (&pids)`), а не о текущих ACTIVE.

## Только чтение

Сессии панель не убивает. Для блокировок показывает, кто кого ждёт; для
каждой работающей сессии собрана команда `ALTER SYSTEM KILL SESSION` —
выполнять её решает DBA.

## Zabbix

Хост `cloudbd-load` («Нагрузка сервера баз данных cloudbd»), группа
`Infrastructure Health`, 12 элементов: `host.load1`, `host.cpu.busy`,
`host.iowait`, `host.mem.avail`, `host.disk.util`, `db.cloudbd.active`,
`db.cloudbd.blocked`, `db.cloudbd.longest`, `db.cloudbd.aas`,
`db.cloudbd.preads`, `db.clouddev.active`, `db.clouddev.blocked`.
Триггеры: перегрузка по load, ожидание диска, блокировки, запрос дольше
30 минут, средняя активность выше числа ядер.

```bash
python modules/netmon/scripts/netmon_zabbix_storage.py --only dbload
```

Сбор занимает около 12 секунд. Первая отправка сразу после создания
элементов уходит в отказ — Zabbix подхватывает новые элементы при
обновлении кэша; повторить через пару минут.

Значения попадают в Zabbix при запуске этой команды. Чтобы график был
непрерывным, её нужно запускать по расписанию (например, раз в минуту) —
расписание на сервере пока не заведено.

## Серьёзное наблюдение — запись нагрузки и графики в реальном времени

Добавлено 08.10.2026. Кнопка «Серьёзное наблюдение» на вкладке «Нагрузка БД»
запускает фоновую запись всех показателей нагрузки раз в N секунд и рисует
графики, как в Диспетчере задач.

**Интервал** — 30 секунд по умолчанию, от 3 до 300. Меняется прямо на
вкладке («Сохранить»), сохраняется между запусками и действует сразу, без
перезапуска наблюдения. Там же: через сколько часов наблюдение остановится
само (по умолчанию 8 — чтобы забытое наблюдение не нагружало сервер
бесконечно) и сколько дней хранить замеры (по умолчанию 7).

**Что пишется в каждый замер:**

| Хост | По каждой базе |
|---|---|
| процессор: пользователь, система, ожидание диска | всего сессий, работают, на процессоре |
| load average, процессы в очереди и заблокированные | ждут блокировку, самый долгий текущий запрос |
| память, swap | процессор базы (доля всех ядер сервера) |
| сеть: приём и отдача | чтения с диска, логические чтения, выполнения, фиксации, redo — в секунду |
| по каждому диску: загрузка, задержка, операции, МБ/с | список работающих сессий: кто, откуда, SQL, чего ждёт |

**Графики** — 14 штук, окно 5 минут … сутки. Длинное окно сжимается до 600
точек: проценты и скорости — средним, **сессии и блокировки — максимумом**,
иначе короткий пик растворился бы в среднем. Щелчок по графику показывает,
какие сессии работали в тот момент. Пока вкладка открыта, графики
обновляются с шагом наблюдения; скрытая вкладка сервер не дёргает.

### Как устроено

* **Лёгкий сборщик** (`observe_sampler.py`). Полный сбор вкладки идёт ~12 с
  — для частых замеров не годится. Здесь одно постоянное SSH-соединение,
  хост читается из `/proc` одной командой, а к каждой базе открыт постоянный
  `sqlplus`, в который подаются запросы. Скорости — по разнице
  накопительных счётчиков (`/proc/stat`, `/proc/diskstats`, `/proc/net/dev`,
  `v$sysstat`) между замерами. **Один замер — около 1 секунды**, поэтому
  интервал 3 секунды реален. Первый замер после запуска — опорный, без
  скоростей.
* **Фоновый процесс** (`scripts/netmon_observe.py`), а не поток веб-сервера:
  локальный Flask в отладке перезапускается при каждой правке кода и убил
  бы наблюдение. Процесс отвязан — закрытая страница его не останавливает.
  Один экземпляр на машину (файловая блокировка): повторное нажатие или
  ручной запуск второго просто выходит. Сбой соединения — переподключение;
  20 сбоев подряд — остановка с записью причины.
* **Остановка**: кнопка (процесс замечает её на ближайшем замере), таймер
  `max_hours`, SIGTERM.
* **Кэш** — SQLite `~/.netmon/observe.sqlite`, вне репозитория. Это кэш
  измерений, а не хранилище данных (CLAUDE.md запрещает SQLite для
  основных данных — здесь их нет): потеря файла ничего не ломает. Почему не
  Oracle — запись каждые несколько секунд в базу, которая стоит на
  наблюдаемом сервере, сама давала бы нагрузку и искажала картину. Таблицы
  по сущностям: `samples`, `disk_samples`, `db_samples`, `session_samples`,
  `settings`, `control`. Журнал процесса — `~/.netmon/observe.log`.

Оговорка о «процессоре базы»: Oracle добавляет `CPU used by this session`
в `v$sysstat` по завершении вызова, поэтому очень длинный запрос даёт
процессор пиком в конце, а не ровно по ходу. Текущая загрузка процессора
сервера (график «Процессор сервера») такой оговорки не имеет.

### API

| Адрес | Что |
|---|---|
| `GET …/netmon/api/observe` | идёт ли, сколько замеров, пульс, настройки, размер кэша |
| `POST …/observe/start`, `POST …/observe/stop` | запустить, остановить |
| `GET/POST …/observe/settings` `{"interval_sec", "max_hours", "retention_days"}` | настройки |
| `GET …/observe/series?minutes=30` | ряды для графиков |
| `GET …/observe/sessions?ts=<unix>` | кто работал в момент `ts` |

### Проверено

Интервал 3 с: замеры ровно через 3,0 с, один замер ~1 с. Повторный запуск
отвечает «уже идёт», ручной запуск второго экземпляра выходит, после
остановки процессов наблюдения ноль. Все 14 графиков отрисованы на данных
кэша (Node, поддельный canvas). Тестов по модулю — 149.
