## Унификация: один клиент от заявки до бэка

Один клиент записан по-разному в пяти местах:

| Где | Как |
|---|---|
| заявки OTRS | `ticket.customer_id` — свободный текст, у одного клиента бывает несколько вариантов |
| логин клиента OTRS | `customer_user.login` и `COD_UNIV` — код контрагента |
| наша бухгалтерия | `UNI.TMS_UNIVERS` (контрагент) и `UNI.TMS_ORG` (фискальный код, адрес) |
| база | одна или несколько схем: основная, `_BK`, `_HR`, `_WEB`, `_SCALES`, базы прошлых лет |
| подключения | точки: база магазина (Oracle XE точки), касса, весы, сайт, рабочие места офиса |

Сведено в таблицы **в OTRS** (база cloudbd, схема OTRS, префикс `NMON_CLI_`):

| Таблица | Что |
|---|---|
| `NMON_CLI` | клиент: код, юрлицо, фискальный код, код контрагента, тип, статус, менеджер, договор |
| `NMON_CLI_OTRS` | варианты заказчика в заявках OTRS → клиент (как сопоставлено, уверенность) |
| `NMON_CLI_LOGIN` | логины клиента в OTRS и их коды контрагента |
| `NMON_CLI_SCHEMA` | схемы клиента и их роль (back, hr, web, scales, pos, bk, test, year…) |
| `NMON_CLI_POINT` | точки за 30 дней: магазин, касса, весы, сайт, рабочее место; входы и дни |
| `NMON_CLI_PRODUCT` | продукты и модули (UaMenu, весы, кассы, сайт, обмен с 1C, кадры…) и откуда это известно |
| `NMON_CLI_ISSUE` | несостыковки: что поправить в OTRS и в учёте |
| `NMON_CLI_V` | клиент одной строкой с заявками — для отчётов в самом OTRS |

DDL — `modules/netmon/sql/cloudbd/302_nmon_cli.sql` (установщик
`netmon_search_deploy.py`). Таблицы OTRS, UNI и схем клиентов только читаются.

### Как сопоставляется (`modules/netmon/unify_rules.py`, `unify.py`)

1. Схемы UniAcc (владельцы `TMS_UNIVERS`) → клиент по основе имени: без хвоста
   (`_BK`, `_HR`…), префикса `POS_` и года (`…18`, `…2025`).
2. Заказчик OTRS → клиент: совпало название без формы собственности (100), логин
   (95), юрлицо по коду контрагента (90), одно — начало другого, от 6 букв (70).
3. Один фискальный код или код контрагента — один клиент: отделы одной сети,
   отдельно заведённая бухгалтерия, подразделения министерства сливаются.
4. Точки — из истории входов: тип по пользователю Windows в аудите
   (`OracleService*` — база магазина, `pos` — касса, `apache`/хостинг — сайт),
   компьютер точки не считается рабочим местом, наши специалисты исключены.
5. Продукты — по словам в заявках и по типам точек.
6. Тип клиента: закреплённый вручную → наш (своя компания) → по точкам за 30 дней.
7. Заглушки OTRS («Fara manager», «Nu este contract valid») — пустое значение.

Несостыковки: код контрагента ведёт на юрлицо, которое в OTRS записано за
другим заказчиком; один клиент записан в заявках по-разному; схема работает,
а заказчик в OTRS не связан.

Строки с `ORIGIN = manual` (поправлено в карточке) автоматика не трогает.
Запуск — кнопка «Сопоставить заново» или
`modules/netmon/scripts/netmon_unify.py` (~40 с).

## Вкладка «Аналитика клиентов»

**Бизнес:** активные клиенты по типам, точки магазинов и рабочие места за
30 дней, клиенты только сопровождения (заявки есть, нашей базы нет), заявки
по стадиям, должники, входы людей неделя к неделе, затихшие клиенты
(работали в месяце, на этой неделе — нет), работающие без договора в
заявках, исполнители и менеджеры, поток заявок по неделям.

**Стадии заявок.** Служебные «исполнители» OTRS — это стадии, а не люди:
`ptclose` — сделано, ждёт закрытия; `stopped` — остановлено; `doljniki` —
работа стоит из-за долга; `forum_uniacc` — форум; `root` — без исполнителя.
Поэтому «открытая заявка» ≠ «в работе»: в работе — только заявки на людях.
Должник — клиент, у которого заявка на `doljniki` менялась за полгода.

**Техника:** всплески входов (программа подключается к базе на каждый
запрос), неудачные входы, схемы без входов за 30 дней (кандидаты в архив),
несостыковки данных.

**Таблица клиентов:** поиск, фильтры по типу и признаку, сортировка;
«Люди, 30 дн» — входы с рабочих мест офиса (без сайтов, баз магазинов и
наших), с графиком по дням.

**Карточка клиента:** юрлицо, фискальный код, код контрагента, тип и статус
(можно поправить), менеджер, договор, заявки по стадиям, варианты в OTRS и
логины, ручная привязка заказчика OTRS (поиск), схемы, точки по типам,
продукты, несостыковки, последние заявки со ссылками в OTRS
(`https://otrs.una.md/otrs/index.pl?Action=AgentTicketZoom;TicketID=…`).

## API

| Метод | Адрес | Что |
|---|---|---|
| GET | `/UNA.md/orasldev/netmon/api/analytics` (`?force=1`) | показатели, клиенты, менеджеры, исполнители, несостыковки (кэш 5 мин) |
| GET | `/UNA.md/orasldev/netmon/api/analytics/client?code=` | карточка клиента |
| POST | `/UNA.md/orasldev/netmon/api/analytics/action` | `{action: unify \| link \| client \| resolve \| find_otrs, …}` |

## Изменения во вкладке «Подключения клиентов» (тот же день)

* клиент берётся из унификации (схемы с хвостами и годами — один клиент, имя — юрлицо);
* клиент, видимый только в тестовой базе clouddev, — в «наших», с меткой «тестовая база»;
* если сейчас подключены только наши специалисты — тип из истории клиента;
* «За 30 дней» — без входов с компьютеров домена UNAMD.
