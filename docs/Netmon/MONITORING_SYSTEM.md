## 1. Из чего состоит система

| Слой | Чем реализован | Где живёт |
|---|---|---|
| **Сбор метрик** | Zabbix 3.4.15, агенты и ICMP-опрос | LXC-контейнер `zabbix34` (CT 101) на PROXMOX3, IP `192.168.0.110` |
| **Хранение истории** | MariaDB внутри контейнера, база `zabbix` (~1.4 ГБ) | там же |
| **Оповещение** | alert-скрипт `telegram_bot.sh` → Telegram Bot API | `/usr/lib/zabbix/alertscripts/` |
| **Канал уведомлений** | Telegram-канал «Zabbix Alert: Unisim-Soft&Coninfo» | бот `@Una_ZabbixBot` |
| **Витрина для человека** | модуль `netmon` портала Artgranit | `/UNA.md/orasldev/netmon` |
| **Инвентарь и покрытие** | таблицы `NMON_*` в Oracle ADB | схема портала |

Принцип разделения: **Zabbix решает, что считать проблемой**, Telegram —
канал доставки, `netmon` — витрина и инвентарь. Модуль ничего не решает за
Zabbix: он читает то, что Zabbix уже сделал, и показывает это связно.

```
устройства сети ──ICMP/агент──▶ Zabbix 3.4 ──action «Telegram»──▶ telegram_bot.sh
     192.168.0.0/24                 │                                    │
                                    │                                    ▼
                        alert.get / host.get                   канал Unisim-Soft&Coninfo
                                    │                                    (5 участников)
                                    ▼
                          модуль netmon ──▶ Oracle NMON_* ──▶ панель портала
```

## 3. Как устройство опознаётся

Классификация — в `modules/netmon/rules.py`, функция `classify()`. Три
признака, в порядке убывания надёжности:

1. **Порт-маркер роли.** `8006` → Proxmox; `554`+`8000` → видеонаблюдение;
   `1521` → Oracle; `9100`/`631` → печать; `3389` → рабочая станция Windows.
2. **Заголовок страницы или баннер.** «RouterOS router configuration page» →
   MikroTik, даже если по портам это был бы обычный Linux-веб. Заголовок
   перебивает догадку по портам.
3. **TTL.** 64 (в пути 63) — Linux/BSD, 128 (→127) — Windows,
   255 (→254) — сетевое железо. Грубо, но работает, когда портов не видно.

Важность (`criticality`) назначается по классу: гипервизор, Oracle, Zabbix и
маршрутизатор — `high`; серверы Linux и камеры — `medium`; рабочие станции,
принтеры и коммутаторы — `low`. Она не влияет на триггеры Zabbix, а нужна
глазу: в таблице сразу видно, где потеря узла болезненна.

| Канал | ID | Тип | Участников | Статус | Сообщений за 30 дней |
|---|---|---|---|---|---|
| **Zabbix Alert: Unisim-Soft&Coninfo** | `-1001544437696` | channel | 5 | **активен** | 1251 |
| TEMP: Zabbix Notifications: Unisim-Soft&Coninfo | `-621328357` | group | 1 | выключен | 0 |

Как устроена доставка:

1. Триггер сработал → действие **«Telegram»** (единственное включённое
   действие типа «триггеры»).
2. Условие действия — только уровень: **average, high, disaster**. Привязки к
   хосту или группе нет, поэтому любой новый триггер нужного уровня
   попадает в канал автоматически, без донастройки.
3. Операция шлёт пользователю `Telegram` (userid 9), у которого заведены оба
   адресата; включён только `-1001544437696`.
4. Скрипт `telegram_bot.sh` подставляет эмодзи по уровню
   (🔴🔴 disaster, 🔴 high, 🟠 average, 🟡 warning, 🟢 resolved) и шлёт
   `parse_mode=HTML`.

Токен бота хранится **только** внутри `telegram_bot.sh` на контейнере Zabbix.
В репозиторий он не копируется; модуль `netmon`, когда ему нужны названия
каналов, выполняет запрос к Telegram API по SSH на самом контейнере, чтобы
токен не покидал сервер. Это проверяется тестом
`test_no_bot_token_is_hardcoded_in_the_module`.

## 5. Модуль netmon: витрина

Адрес: **`/UNA.md/orasldev/netmon`**. Семь разделов.

| Раздел | Что показывает | Зачем |
|---|---|---|
| **Сводка** | плитки (устройств, покрытие, каналы, сообщений, ошибок доставки), состав сети по классам, топ хостов по числу уведомлений | ответ за 5 секунд: всё ли под контролем и кто шумит |
| **Устройства** | таблица всех найденных узлов: IP, класс, имя/заголовок, порты, важность, есть ли в Zabbix, онлайн ли | инвентарь и поиск дыр в покрытии (фильтр «только вне мониторинга») |
| **Telegram-каналы** | карточка на канал: статус, участники, сообщений всего и за сутки, ошибки доставки, гистограмма по дням | наглядно видно, какой канал живой и сколько в него льётся |
| **Лента сообщений** | то, что реально ушло в Telegram: время, уровень с эмодзи, текст, канал, статус доставки | разбор «что приходило ночью», с фильтром по каналу и уровню |
| **Обзор Zabbix** | все 75 хостов мониторинга: элементы, сломанные, активные проблемы, доступность агента | состояние самого мониторинга, читается напрямую из Zabbix |
| **Proxmox: машины** | все 51 гость гипервизора, включая 31 выключенный; паспорт по клику | инвентарь виртуализации и решения о миграции |
| **Домены и стойка** | сроки доменов, перерасход электроэнергии, регламент двух серверов стойки | то, что стоит денег и не видно в обычном мониторинге |
| **Доступы** | 15 учётных записей по пяти группам, откуда взять пароль | реестр доступов без раскрытия значений |

Кнопки в шапке: **↻ Telegram** (перечитать каналы и ленту), **↻ Скан сети**
(новый скан подсети), **Обновить** (перечитать данные из Oracle).

### Модель данных (Oracle, префикс `NMON_`)

| Таблица | Назначение |
|---|---|
| `NMON_SCANS` | прогон скана: подсеть, время, сколько найдено, сколько новых, сколько пропало |
| `NMON_DEVICES` | устройство: IP (уникален), DNS-имя, TTL, порты, класс, важность, заголовок, баннеры, есть ли в Zabbix, статус, первое и последнее появление |
| `NMON_TG_CHANNELS` | канал: chat_id (уникален), название, тип, участники, бот, media в Zabbix, включён ли |
| `NMON_TG_ALERTS` | отправленное сообщение: id алерта Zabbix (уникален — защита от двойной загрузки), канал, время, тема, уровень, хост, статус доставки, ошибка |

### API

| Метод | Адрес | Что делает |
|---|---|---|
| GET | `/api/overview` | сводка: устройства + каналы + статистика ленты |
| GET | `/api/devices?kind=&missing=1` | список устройств с фильтрами |
| GET | `/api/channels` | каналы со счётчиками сообщений |
| GET | `/api/alerts?limit=&channel=&severity=` | лента сообщений |
| POST | `/api/sync/channels` | перечитать каналы из Zabbix + названия из Telegram |
| POST | `/api/sync/alerts?days=30` | подтянуть ленту `alert.get` (идемпотентно) |
| POST | `/api/sync/devices` | скан подсети и обновление инвентаря |
| POST | `/api/sync/all` | всё перечисленное подряд |

Все маршруты требуют входа в портал; синхронизация — только POST.

## 6. Эксплуатация

### Поставить новое устройство на мониторинг

```bash
cd /Users/pt/Projects.AI/Artgranit-netmon
python modules/netmon/scripts/netmon_zabbix_sync.py --apply --dry-run  # план
python modules/netmon/scripts/netmon_zabbix_sync.py --apply            # завести
```

Скрипт **только добавляет** недостающие: существующие хосты он не трогает и
ничего не удаляет. Нужен поднятый туннель **VPN93**.

### Обновить витрину

Кнопками в шапке панели или из кода:

```bash
python -c "from modules.netmon.controller import NetmonController as C; print(C.sync_all()[0])"
```

### Когда уведомления перестали приходить

1. Панель → **Telegram-каналы**: смотрим «Ошибок» и «Последнее». Если
   последнее сообщение старое, а ошибок нет — Zabbix ничего не шлёт.
2. Проверяем действие: в Zabbix действие «Telegram» должно быть **Enabled**,
   тип media «Telegram» — **Enabled**, адресат `-1001544437696` — активен.
3. Проверяем сам бот с контейнера:
   `curl -s "https://api.telegram.org/bot<токен>/getMe"` — токен берём из
   `telegram_bot.sh`, наружу не копируем.
4. Если бота исключили из канала, `getChat` вернёт ошибку — вернуть бота в
   канал администратором канала.

### Пороги и шум

Действие шлёт всё от **average** и выше. Если канал зашумел, правильный
порядок — не отключать канал, а убрать источник шума: отключить конкретный
триггер в Zabbix (как это уже сделано для «Archive Logs … Standby», почты
`garileauto.md` и SSL `tnme.md`). Верхний хост по числу сообщений виден на
вкладке «Сводка» — начинать разбор стоит с него.

## 7. Известные ограничения

1. **Скан видит только включённые устройства.** Ноутбук в спящем режиме в
   инвентарь не попадёт; устройство, пропавшее между прогонами, помечается
   `down`, но из базы не удаляется.
2. **ICMP-шаблон не знает, что внутри.** Для новых 38 хостов контролируется
   доступность, потеря пакетов и время отклика. Диски, память и службы там
   не видны — для этого нужен агент или SNMP на самом устройстве.
3. **Классификация — эвристика.** `net-206` может оказаться как коммутатором,
   так и IP-телефоном: порты закрыты, остаётся только TTL. Поле класса можно
   поправить руками в `NMON_DEVICES.KIND`, скан его перезапишет только при
   следующем прогоне.
4. **Zabbix 3.4.15 снят с поддержки с 2018 года.** Обновлений безопасности
   нет. Это не мешает работе, но остаётся риском — отмечено и в паспорте
   Zabbix, и в акте тестирования.
5. **Модуль читает, но не правит Zabbix из панели.** Завести хост можно
   только скриптом; кнопки «удалить хост» в панели нет намеренно.

## 8. Температурные пороги: разбор ложной тревоги (12.09.2026)

**Что было.** При первой настройке контроля температуры я взял пороги
**52 °C** и **60 °C** — из эмодзи Telegram-бота на Blynk, где 🔔 загорается
около 52 °C. Это оказалось неверным основанием.

**Что выяснилось.** Инженер Kvazar (обслуживает серверы) привёл данные:
максимум за два года — **58 °C**, за сутки — **51 °C**, ни одного случая
троттлинга. Проверил модели процессоров:

| Сервер | Процессор | Tcase (предел Intel) | Троттлинг |
|---|---|---|---|
| PROXMOX3 | 2× Intel Xeon E5-2620 v3 @ 2,40 ГГц | **72,6 °C** | ~85 °C |
| cloudbd | 2× Intel Xeon E5-2623 v3 @ 3,00 ГГц | ~73 °C | ~85 °C |

Нормальный режим для этих процессоров: 35–55 °C в простое, до 75 °C под
нагрузкой. Наблюдаемые 44–50 °C — **обычная рабочая температура**, а не
перегрев.

**Что исправлено.** Старые 8 триггеров удалены, заведены 12 новых с порогами
по спецификации:

| Порог | Уровень | Смысл |
|---|---|---|
| > 73 °C | average | превышен Tcase — стоит посмотреть |
| ≥ 80 °C | high | заметно выше нормы под нагрузкой |
| ≥ 85 °C | disaster | близко к троттлингу |

**Важное уточнение о происхождении шума.** Проверка `alert.get` показала:
за сутки мои триггеры дали **ноль** сообщений. Ночной шум, на который
жаловались, идёт не из Zabbix, а из **Blynk-бота**, где уставка осталась
около 52 °C. Её нужно поднять там же — это отдельная система, доступа к ней
у модуля нет.

непрерывно **обоснованно** и в расчёт не входят.

## 10. Управление доступами

Вкладка **«Доступы»**: 15 учётных записей в пяти группах по типу объекта —
базы Oracle, виртуализация, мониторинг, серверы SSH, прочее. Панель
показывает, какой доступ существует, где он применяется и **как достать
пароль из Keychain**; сами значения через веб не отдаются.

Инструмент `modules/netmon/scripts/netmon_vault.py`:

```bash
python modules/netmon/scripts/netmon_vault.py --collect
python modules/netmon/scripts/netmon_vault.py --to-keychain \
       --to-file ~/Documents/infra-passwords.md
```

Собрано 12.09.2026: 15 записей уже были в Keychain, **30 пар логин/пароль
извлечено из описаний виртуальных машин** на гипервизоре и перенесено в
Keychain под именами `pve-<машина>`. Справочник записан в
`~/Documents/infra-passwords.md` с правами 600 — **вне репозитория**;
скрипт отказывается писать файл внутрь проекта.

**Требует внимания:** пароли в описаниях ВМ видит любой, у кого есть доступ
к веб-интерфейсу Proxmox, и они попадают в резервные копии конфигурации.
Их следует удалить из описаний и сменить как скомпрометированные.
