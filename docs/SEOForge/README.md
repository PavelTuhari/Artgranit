# SEOForge — модуль AI-SEO продвижения

Модуль ведёт продвижение произвольного числа собственных сайтов: профили
сайтов, кампании, план и факт маркетингового бюджета, эффективность по
каналам. Оракловый контур модуля — `YSEO_*`, маршруты — `/UNA.md/orasldev/seoforge`.

Источник требований — ТЗ платформы SEOForge (репозиторий `PavelTuhari/cursor25`,
ветка `claude/seo-web-platform-spec-hxdbtj`, каталог `seo-platform/`).
Проектное решение по этому модулю — `docs/superpowers/specs/2026-08-24-seoforge-backoffice-design.md`.

## Что вошло в эту версию

| Экран | Что делает |
|---|---|
| Портфель | плитки сайтов: план периода, израсходовано, остаток, активные кампании |
| Сайты | профиль сайта: домен, локали, гео, ниша, tone of voice, guardrails, KPI |
| Кампании | код кампании (он же `utm_campaign`), сроки, план бюджета, статус, план/факт/остаток |
| Бюджет | сетка «период × статья × канал × сайт»: план, факт, остаток, процент выполнения |
| Факты | ручной ввод и CSV-импорт расходов рекламы и метрик сайта |
| ROI | по каналам и периодам: расход, клики, конверсии, выручка, ROI, CPC, CPA, CTR |
| Стратегия | документы работы в Markdown: стратегия, планы, плейбуки — с версиями и отпечатком |
| Справочники | каналы, статьи, типы промо, форматы, единицы закупки, метрики, площадки, курсы валют, настройки, журнал |

## Документооборот: от стратегии до ROI

Работа ведётся документами, и цепочка замкнута — от решения до цифры:

1. **Стратегия** — Markdown в `YSEO_PLAYBOOK`, вид `STRATEGY`. Пример живой:
   [`STRATEGY_OFFICEPLUS.md`](STRATEGY_OFFICEPLUS.md), код
   `officeplus-strategy-2026`, составлен на данных ERP.
2. **Кампании** (`YSEO_CAMPAIGN`) — код кампании он же `utm_campaign`.
3. **План бюджета** (`YSEO_BUDGET_PLAN`) по периодам и статьям.
4. **Факт расхода** (`YSEO_SPEND_FACT`) — вручную или CSV.
5. **Документы ERP** типов `60001`/`60002`, строки — в `TMDB_CST3A`
   через `VMDB_YSEO1D`.
6. **План/факт и ROI** — на экранах модуля.

### Правила хранения документов стратегии

- **Опубликованная версия неизменяема.** Правка создаёт новую версию;
  держит это триггер `TRG_YSEO_PLAYBOOK_FROZEN`, а не договорённость.
  Проверено: `UPDATE ... SET BODY` по опубликованной версии отбивается
  с `ORA-20120`.
- **Версия назначается сама** — из максимума по тому же коду.
- **Повтор того же текста не создаёт версию** — сверка по отпечатку.
- **Отпечаток `BODY_SHA`** показывает, совпадает ли документ в контуре
  с файлом в репозитории. Расхождение означает правку мимо репозитория.

### Ограничение кодировки — важное

База учёта в `CL8MSWIN1251`. Символ, которого в этой кодировке нет,
Oracle заменяет на `?` **молча**: длина та же, содержимое другое.
Поймано на живом документе — знак `≥` превратился в `?` четыре раза,
и увидеть это можно было только по отпечатку.

Поэтому текст проверяется **до** записи: `unsupported_chars` возвращает
непригодные знаки с номерами строк, и запись отклоняется.

Сюда же попадает **румынская диакритика** (`ș`, `ț`, `ă`, `î`, `â`) —
её в CP1251 нет. По этой же причине и сама ERP хранит наименования без
знаков: «Rechizite scolare». Документы контура живут по тому же правилу.
Если понадобится полный Unicode, текст надо будет хранить BLOB-ом в UTF-8;
сознательно не сделано, потому что тогда документ перестанет читаться
обычными средствами SQL.

## Чего в этой версии нет

Платформа из ТЗ шире одного модуля. Отложено:

- **документооборот и согласование** (Approval Inbox, документы поверх `TMDB_DOCS`
  системы UNA) — заблокировано до сверки интерфейса с командой UNA;
- **генератор `.md`-плейбуков и реестр запусков** AI-сессий;
- **коннекторы**: Google Search Console, GA4, SERP, рекламные кабинеты, соцсети,
  локальные площадки Молдовы;
- экраны семантики, контент-плана, техаудита и ссылочного профиля.

Пока коннекторов нет, факт поступает вручную или через CSV — формат описан
в [`CSV_FORMAT.md`](CSV_FORMAT.md).

## Где живёт контур

Контур `YSEO_*` установлен в **боевую ERP OfficePlus/UNA**
(`orange.una.md:4024/cloudbd.world`, схема `OFFICEPLUS`, Oracle 11.2.0.4),
рядом с остальным учётом. В облачной базе бэкофиса контура нет: он был там
на время разработки и снят скриптом `scripts/seoforge_drop_cloud.py`.

Практическое следствие для кода: модуль ходит в базу **только** через
`models/biro26_db.py` — thick-режим в отдельном процессе. Включить thick
в основном процессе нельзя, это переключатель на весь процесс, и он сломал
бы облачные подключения остальных модулей портала. Постоянного соединения
нет, поэтому многокомандные операции идут одним `execute_script`.

## Установка контура

```bash
venv/bin/python modules/seoforge/scripts/seoforge_deploy_erp.py --dry-run
venv/bin/python modules/seoforge/scripts/seoforge_deploy_erp.py --yes
```

`deploy_oracle_objects.py` контур **не ставит** и вообще о модуле не знает:
весь DDL лежит в `modules/seoforge/sql/`. Общий код модуль не трогает —
см. [`docs/CORE_MODULES.md`](../CORE_MODULES.md).

Порядок файлов важен и зафиксирован в установщике:

| Файл | Содержимое |
|---|---|
| `modules/seoforge/sql/113_yseo_tables.sql` | таблицы, последовательности, триггеры |
| `modules/seoforge/sql/115_yseo_package.sql` | пакеты `PK_SEO_UTIL`, `PK_SEO_BUDGET` |
| `modules/seoforge/sql/114_yseo_views.sql` | вьюшки `VSEO_*` — вызывают `PK_SEO_UTIL.TO_MDL`, потому идут после пакетов |
| `modules/seoforge/sql/116_yseo_dict_seed.sql` | справочники, настройки, перекомпиляция триггера |

Триггер `TRG_YSEO_SPEND_BUDGET` из `113` обращается к пакетам из `115`,
поэтому при первой установке он создаётся невалидным. Файл `116`
заканчивается `ALTER TRIGGER TRG_YSEO_SPEND_BUDGET COMPILE` — после полной
установки схема валидна.

Обычный `deploy_to_remote.sh` переносит код, но DDL не выполняет. Это и не
нужно: контур стоит в ERP, а она одна и та же для локальной машины и для
сервера. Ставить его повторно с сервера не требуется.

Установщик проверяет `USER_ERRORS` после каждого файла: `CREATE PACKAGE`
с ошибкой компиляции не бросает исключение, объект просто остаётся
невалидным, и без этой проверки установка выглядела бы успешной.

## Проверка

```bash
venv/bin/python -m pytest tests/test_seoforge.py -q
```

Юнит-тесты работают без базы: проверяют инварианты DDL разбором файлов,
разбор CSV, хранилище на моках, валидацию контроллера.

Инварианты самой базы (лимит бюджета, дедуп, архив вместо удаления)
проверяет живой smoke. Он пишет в **боевую** базу на служебном сайте
`smoke.invalid` и требует явного согласия:

```bash
venv/bin/python modules/seoforge/scripts/seoforge_smoke.py --yes
```

## Режим контроля бюджета

Настройка `BUDGET_OVERRUN_MODE` в справочниках:

- `WARN` (по умолчанию при установке) — расход сверх плана записывается
  с флагом `IS_OVERBUDGET = 1` и уходит в разбор;
- `BLOCK` — расход сверх плана отклоняется исключением `ORA-20101`.

Начинать имеет смысл с `WARN`: пока план не заполнен по-настоящему, `BLOCK`
будет мешать заносить реальные расходы. Правило живёт в пакете
`PK_SEO_BUDGET`, а не в приложении, — ошибка в коде интерфейса не должна
приводить к бесконтрольным тратам.

## Доступ к базе: пул долгоживущих воркеров (требование)

Правило для каждого модуля, который ходит в ERP, — и для каждой новой задачи,
где такая система проектируется:

1. **Никаких процессов на запрос.** Обращения к Oracle идут через
   `models/biro26_db.py` — пул долгоживущих воркеров (`--serve`). Запуск
   процесса на каждую интерогацию стоил ~1,7 с и был главной причиной
   медленного ответа сайта (замер 26.08.2026).
2. **Чтения** переиспользуют удержанное соединение: они не трогают
   состояние сессии. **Записи** (dml/plsql/script) всегда получают свежее
   соединение — они выставляют контекст сессии (`SET_ENV`: период,
   пользователь), и он не имеет права утекать в следующие запросы.
3. **Один `execute_script` — одна транзакция.** На это опирается запись
   документов в ERP; ломать нельзя.
4. **Таймаут убивает процесс** — сессия Oracle падает и откатывается.
   Это страховка от чужих блокировок, её нельзя заменять «мягким» ожиданием.
5. Выключатель на случай беды: `BIRO26_WORKER_POOL=0` возвращает старый
   транспорт (процесс на запрос). `BIRO26_WORKER_POOL_SIZE` — размер пула.

Ориентиры скорости после перехода: чтение ~0,16 с, запись ~1,1 с,
тестовый прогон 4,6 с. Если новый код снова показывает секунды на чтение —
что-то пошло мимо пула.

## Проекты — папки, и никто никому ничего не затирает (требование)

Правило для всего, что добавляется в портал:

1. **Модуль — это папка `modules/<ключ>/`.** Ядро находит её само, ничего
   дописывать в общий код не нужно. Отсюда и главное свойство: выкладка
   одной ветки не может унести чужие маршруты — они лежат в чужой папке.
2. **Никаких маршрутов в общем `app.py`.** Проверено на своей шкуре:
   27.08.2026 контур переставили на другую ветку, где `robots.txt` и
   `sitemap.xml` в `app.py` не было, — публичный сайт остался с 404 по
   обоим адресам. Теперь они в `modules/seo/`.
3. **Адреса в корне сайта** (`/robots.txt`, `/sitemap.xml`) объявляются
   списком `root_paths` в `module.json`. Ядро подключает их без префикса и
   **отвергает** попытку занять адрес, который уже держит другой модуль:
   молча перекрыть чужое невозможно. Кто что занял — видно в манифесте.
4. **Общие файлы трогает только тот, кто обязан.** Если правка кажется
   неизбежной в `app.py` — сначала проверить, не решается ли она папкой.
5. **Слияние веток не должно решать, чьи маршруты выживут.** Если ответ на
   вопрос «а что будет при выкладке другой ветки» — «пропадёт», значит
   место выбрано неверно.

Проверить, что модуль подключился: `/api/biro26/health` и отчёт ядра —
там видно `loaded`, `skipped`, `failed` с причинами.
