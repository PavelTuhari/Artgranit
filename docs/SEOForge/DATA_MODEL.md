# SEOForge — модель данных

Контур `YSEO_*` в схеме `OFFICEPLUS` боевой ERP UNA (Oracle 11.2.0.4).
Имена колонок взяты из ТЗ платформы без изменений: когда кусок C
потребует связать контур с документами UNA, отображение окажется
механическим — таблицы уже лежат в одной схеме с `TMDB_DOCS`
и `TMS_UNIVERS`.

## Отличия от ТЗ

В ТЗ таблицы `YSEO_*` — расширения таблиц UNA: внешние ключи на `TMS_UNIVERS`,
табличные части `*_D` с ключом на `TMDB_DOCS`, справочники через разделы
`TMS_SYSS ('W', 1..7)`. Контур лежит в той же схеме, но связей с этими
таблицами пока не заводит: их состав и правила (выдача `TMDB_DOCS.COD`,
кодировка `DOCCOLOR`, сигнатура `UN$GFC`) не подтверждены командой UNA,
а внешний ключ на непонятую таблицу опаснее его отсутствия. Поэтому:

| В ТЗ | Здесь | Почему |
|---|---|---|
| разделы `TMS_SYSS ('W', n)` | таблица `YSEO_DICT` | раскладка разделов `'W'` не подтверждена |
| `YSEO_TMDB_CAMP_D` (часть документа) | `YSEO_CAMPAIGN` | документов в этой версии нет (кусок C) |
| `YSEO_TMDB_BUDG_D` | `YSEO_BUDGET_PLAN` | то же |
| `YSEO_TMDB_ADSPEND_D` | `YSEO_SPEND_FACT` | то же |
| `VALUE` в метриках | `METRIC_VALUE` | `VALUE` — ключевое слово, в PL/SQL и вьюшках путается |

Связь с документами ERP заложена таблицей `YSEO_XREF` и заполняется, когда
интерфейс UNA будет подтверждён.

## Таблицы

| Таблица | Назначение | Ключи |
|---|---|---|
| `YSEO_DICT` | справочник разделов `CHANNEL`, `ARTICLE`, `PROMO_TYPE`, `FORMAT`, `BUYUNIT`, `METRIC` | PK `(SECTION, COD1)`, UK `COD1`, UK `(SECTION, CODE)` |
| `YSEO_SITE` | профиль продвигаемого сайта | PK `COD`, UK `DOMAIN` |
| `YSEO_PLATFORM` | площадки размещения | PK `COD`, UK `PLATFORM_CODE`, FK на канал |
| `YSEO_CAMPAIGN` | кампания / акция | PK `COD`, UK `CAMP_CODE`, FK на сайт и тип промо |
| `YSEO_BUDGET_PLAN` | план бюджета | PK `COD`, уникальный функциональный индекс по `(PERIOD, ARTICLE_COD1, NVL(CHANNEL_COD1,-1), NVL(SITE_COD,-1))` |
| `YSEO_SPEND_FACT` | факт расхода рекламы | PK `COD`, UK `EXT_ID` |
| `YSEO_METRICS_FACT` | метрики сайта | PK `COD`, UK `EXT_ID` |
| `YSEO_IMPORT` | партии CSV-импорта | PK `COD` |
| `YSEO_FX_RATE` | курс валюты на дату | PK `(VALUTA, RATE_DATE)` |
| `YSEO_SETUP` | настройки контура | PK `PARAM_CODE` |
| `YSEO_XREF` | связь с документами UNA | PK `COD`, UK `(ENTITY_TYPE, ENTITY_COD)` |
| `YSEO_EVENT_LOG` | журнал модуля, только добавление | PK `COD` |

### Почему у плана функциональный индекс, а не обычный UK

`CHANNEL_COD1` и `SITE_COD` необязательны: строка плана может относиться ко
всем каналам или ко всем сайтам. В обычном уникальном ключе Oracle не считает
два `NULL` одинаковыми, и две строки «весь период, вся статья, все каналы»
прошли бы обе. Индекс по `NVL(..., -1)` закрывает эту дыру.

### Диапазоны кодов справочника

`101..999` — поставляются с модулем (`116_yseo_dict_seed.sql`) и одинаковы
в любой установке. Добавленные через интерфейс начинаются с `1001`:
последовательность `YSEO_DICT_SEQ` объявлена `START WITH 1001`.

## Вьюшки

| Вьюшка | Содержимое |
|---|---|
| `VSEO_SITE` | сайт + активные кампании + расход и план текущего периода |
| `VSEO_CAMPAIGN` | кампания + план, факт, остаток, клики, конверсии, выручка |
| `VSEO_BUDGET_PLANFACT` | период × статья × канал × сайт: план, факт, остаток, процент |
| `VSEO_CHANNEL_ROI` | канал × период: расход, клики, показы, конверсии, выручка, ROI, CPC, CPA, CTR |

`VSEO_BUDGET_PLANFACT` соединяет план и факт через `FULL OUTER JOIN`
намеренно: расход по статье, которую не планировали, обязан появиться
в сетке — иначе перерасход молча исчез бы из отчёта.

## Пакеты

### `PK_SEO_UTIL`

| Подпрограмма | Что делает |
|---|---|
| `PERIOD_OF(p_date)` | дата → `YYYY-MM` |
| `GET_SETUP(p_code, p_default)` | значение настройки из `YSEO_SETUP` |
| `TO_MDL(p_suma, p_valuta, p_date)` | приведение к базовой валюте по `YSEO_FX_RATE` |
| `LOG_EVENT(...)` | запись в журнал модуля |

`TO_MDL` при отсутствии курса **бросает** `ORA-20102`, а не подставляет
единицу: молчаливый курс 1 исказил бы каждую сумму в отчётах. Курс
проверяется в момент записи плана, поэтому строка, из-за которой вьюшка
позже упала бы, в таблицу не попадает.

### `PK_SEO_BUDGET`

| Подпрограмма | Что делает |
|---|---|
| `CHECK_LIMIT(period, article, channel, site, add)` | остаток плана; отрицательный = перерасход |
| `PLAN_UPSERT(...)` | `MERGE` строки плана по естественному ключу + журнал + пересчёт флагов |
| `ENFORCE_KEYS(keys)` | проверка лимита для ключей, затронутых командой |
| `RECALC_OVERBUDGET(period)` | пересчёт флагов после правки плана |
| `MAKE_KEY`, `IS_FLAGGING`, типы `T_KEY`, `T_KEYS` | служебные, нужны триггеру |

## Инварианты, которые держит база

Эти правила живут в пакетах и триггерах, а не в приложении: ошибка в коде
интерфейса не должна приводить к бесконтрольным деньгам.

1. Расход сверх плана отклоняется (`BUDGET_OVERRUN_MODE = BLOCK`,
   исключение `ORA-20101`) либо помечается `IS_OVERBUDGET = 1` (`WARN`).
2. `PERIOD` и `SUMA_MDL` у факта расхода вычисляются триггером из даты
   и валюты — приложение их не задаёт и не может исказить.
3. Повторный `EXT_ID` отвергается уникальным ключом: повторная заливка
   того же файла не создаёт дублей.
4. Отсутствие курса валюты — ошибка `ORA-20102`, а не молчаливая единица.
5. Период плана обязан быть в формате `YYYY-MM` (`ORA-20104`),
   сумма плана неотрицательна (`ORA-20105`).
6. Журнал `YSEO_EVENT_LOG` защищён от изменения и удаления (`ORA-20103`).
7. Удалений в контуре нет: справочные сущности архивируются `ISARHIV = 1`.

### Почему триггер бюджета — compound

`CHECK_LIMIT` читает `YSEO_SPEND_FACT`, то есть ту самую таблицу, на которую
навешен триггер. Построчный триггер упал бы с `ORA-04091` (mutating table).
Поэтому `TRG_YSEO_SPEND_BUDGET` объявлен `COMPOUND TRIGGER`: в
`BEFORE EACH ROW` он проставляет период и сумму в базовой валюте и собирает
затронутые ключи, а в `AFTER STATEMENT` — один раз проверяет лимиты.
Обратная запись флагов идёт под защёлкой `PK_SEO_BUDGET.IS_FLAGGING`,
иначе триггер вызвал бы сам себя.

## Слой приложения

| Файл | Ответственность |
|---|---|
| `modules/seoforge/csv_format.py` | чистый разбор CSV: период, `EXT_ID`, валидация. Ни Oracle, ни Flask |
| `modules/seoforge/store.py` | SQL через thick-воркер ERP: чтения из `VSEO_*`, записи одним `execute_script` — воркер коммитит скрипт целиком |
| `modules/seoforge/controller.py` | валидация ввода, двухшаговый импорт, перевод ошибок Oracle в HTTP-коды |
| `modules/seoforge/routes.py` | 22 маршрута на blueprint, адреса без префикса — его ставит ядро |
| `modules/seoforge/scripts/seoforge_deploy_erp.py` | установка контура в ERP с проверкой `USER_ERRORS` |
| `modules/seoforge/scripts/seoforge_drop_cloud.py` | снятие контура с облачной БД после переноса |
| `modules/seoforge/templates/seoforge.html` | SPA с семью панелями |

Коды ответов: `400` — ошибка ввода, `409` — нарушенный инвариант
(`ORA-20xxx`, `ORA-00001`), `500` — сбой инфраструктуры. Тексты вроде
`TNS:no listener at host …` наружу не отдаются.

## Доступ к базе: пул долгоживущих воркеров (требование)

Правило для каждого модуля, который ходит в ERP, — и для каждой новой задачи,
где такая система проектируется:

1. **Никаких процессов на запрос.** Обращения к Oracle идут через
   `models/biro26_db.py` — пул долгоживущих воркеров (`--serve`). Запуск
   процесса на каждую интерогацию стоил ~1,7 с и был главной причиной
   медленного ответа сайта (замер 26.08.2026).
2. **Чтения** переиспользуют удержанное соединение: они не трогают
   состояние сессии. **Записи** (dml/plsql/script) всегда получают свежее
   соединение — они выставляют контекст сессии (`SET_ENV`: период,
   пользователь), и он не имеет права утекать в следующие запросы.
3. **Один `execute_script` — одна транзакция.** На это опирается запись
   документов в ERP; ломать нельзя.
4. **Таймаут убивает процесс** — сессия Oracle падает и откатывается.
   Это страховка от чужих блокировок, её нельзя заменять «мягким» ожиданием.
5. Выключатель на случай беды: `BIRO26_WORKER_POOL=0` возвращает старый
   транспорт (процесс на запрос). `BIRO26_WORKER_POOL_SIZE` — размер пула.

Ориентиры скорости после перехода: чтение ~0,16 с, запись ~1,1 с,
тестовый прогон 4,6 с. Если новый код снова показывает секунды на чтение —
что-то пошло мимо пула.
