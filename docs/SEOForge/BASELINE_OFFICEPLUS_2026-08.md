## 2. Главный вывод

**Каталог из 165 164 позиций для поисковика не существует.**

Серверный HTML `/catalog` не содержит ни одной ссылки на товар — каталог
собирается в браузере. Обходчик видит 14 страниц: главную, доставку,
бренды, контакты и прочую обвязку. Всё остальное для него отсутствует.

Это меняет порядок работ. Стратегия исходила из того, что 165 тысяч
страниц проиндексированы и мешают друг другу, и предлагала выделить из них
ядро. На деле индексировать пока нечего, и первая задача другая: сделать
так, чтобы страницы ядра вообще отдавались сервером. Разделение на ядро и
хвост остаётся верным — но как второй шаг, а не первый.

## 3. Найденная ошибка: canonical уводит на внутренний адрес

Страница `/catalog` объявляет:

```html
<link rel="canonical" href="https://officeplus.md/UNA.md/orasldev/biro26-site/catalog">
<link rel="alternate" hreflang="ro" href="https://officeplus.md/UNA.md/orasldev/biro26-site/catalog">
<link rel="alternate" hreflang="ru" href="https://officeplus.md/UNA.md/orasldev/biro26-site/catalog?lang=ru">
```

Этот адрес отвечает 200. То есть сайт сам просит поисковик считать
основным адресом каталога внутренний путь бэк-офиса, а публичный
`/catalog` — дубликатом. Публичный адрес из индекса выпадет.

Причина в общем шаблоне `templates/biro26/site_base.html:23`: canonical
строится из `request.path`, а на officeplus.md запрос приходит по
внутреннему пути. Особый случай предусмотрен только для корня — поэтому
главная объявляет canonical правильно, а все остальные страницы нет.

**Шаблон общий, не модуля SEO — я его не трогал.** Исправление в одну
строку: строить canonical и `hreflang` от публичного адреса сайта, а не от
`request.path`.

До исправления любая работа по каталогу бессмысленна: что бы ни
оптимизировали, canonical отправит вес на другой адрес.

## 4. Чего измерить не удалось

Эти показатели требуют доступа, которого у меня нет. Ставить сюда
правдоподобные цифры нельзя: база отсчёта из выдуманных чисел хуже, чем её
отсутствие — по ней потом посчитают несуществующий рост.

| Показатель | Что нужно |
|---|---|
| `INDEXED_PAGES` | Google Search Console по officeplus.md |
| `IMPRESSIONS`, `CLICKS`, `CTR`, `POSITION_AVG` | Search Console, выгрузка за 3 месяца |
| `SESSIONS`, `USERS`, `CONVERSIONS`, `REVENUE` | Google Analytics 4 |
| `TOP10_KEYS` | съём позиций по списку ключей |
| `BACKLINKS` | Ahrefs / Semrush или Search Console |
| `CWV_LCP` | PageSpeed Insights или полевые данные CrUX |

Модуль принимает их CSV-выгрузкой — экран импорта, вид `METRICS`. Как
только доступы появятся, база отсчёта дополняется тем же числом от
25.08.2026, если выгрузка позволяет, либо ближайшей доступной датой с
пометкой в источнике.

## 5. Что делать в этом порядке

1. **Починить canonical и hreflang** в общем шаблоне — иначе всё остальное
   уходит в чужой адрес.
2. **Отдавать каталог сервером**: карточки и группы ядра должны быть в
   HTML, а не собираться в браузере.
3. **Сделать карту сайта** и объявить её в `robots.txt`.
4. **Ускорить ответ**: 3,6 с до первого байта — это втрое дороже разумного.
5. Добавить разметку `Product` + `Offer` на карточки ядра.
6. Открыть доступ к Search Console и Analytics, дозаполнить базу отсчёта.

Первые пять пунктов — работа по сайту, не по продвижению. Бюджет на
рекламу в августе-сентябре при этом не простаивает: платный трафик идёт на
существующие страницы и не зависит от индексации.
