# Бэк-офис UNA в вебе

Развитие бэк-офиса biro26: учётная система в браузере — журналы, документы
и проводки. Модуль **только читает**.

## Чем отличается от прежнего бэк-офиса

Прежний биро26-бэкофис работает со своим набором экранов (товары, клиенты,
кредиты, отчёты). Этот модуль показывает учёт так же, как дельфийский
клиент UNA, и берёт структуру **из самой конфигурации**:

| Что | Откуда |
|---|---|
| Журналы и их группы | `A$ADM$V`, `OBJ_TYPE=2` (`CAPTION`, `SQLFILTER`) |
| Типы документов | `A$ADM$V`, `OBJ_TYPE=1/0`, свойство `DB ID` = `TMDB_DOCS.SYSFID` |
| Документы | `TMDB_DOCS` по фильтру журнала |
| Строки | реестр проверенных источников (см. ниже) |
| Проводки | `TMDB_CM` — общая для любого типа |

Захардкоженный список журналов разошёлся бы с клиентом в первый же день,
когда администратор заведёт новый тип документа. Здесь этого не случится:
источник тот же.

## Экраны

**Журналы**

1. дерево слева: группы и журналы с их заголовками;
2. документы журнала — отбор по `SQLFILTER` из конфигурации, фильтр по датам,
   тип документа расшифрован по `SYSFID`;
3. карточка документа — шапка, строки, проводки с корреспонденцией счетов.

**Товары**

4. дерево групп из `TMS_SYSGR` / `TMS_SYSGRPH` с раскрытием подгрупп;
5. номенклатура группы и поиск по названию или артикулу;
6. карточка позиции — реквизиты и группы, в которых она состоит.

Выборка товаров всегда фильтруется по `TIP = 'P'`: в `TMS_UNIVERS` рядом
лежат и строки-категории (`T`), и контрагенты (`O`), и без фильтра они
попали бы в список номенклатуры.

## Откуда берутся строки документа

Общего хранилища строк в UNA нет: строки кладёт DLL, исполняющая документ.
Причём `DOCNAME` семейство не задаёт — под одним `DG1p21` сидят 223 типа
документов с совершенно разным хранением.

Автоопределение «найти таблицу, где есть такой `NRDOC`» проверено и
**отвергнуто**: оно даёт ложные срабатывания. У документа 86 («Акт изменения
цен») так «находится» `TMDB_SALAR_ABSD1` с 28 строками зарплаты — там
`NRDOC` означает совсем другой документ. Показать это пользователю как
строки его документа хуже, чем не показать ничего.

Поэтому реестр составлен по проверенным данным:

| Тип / семейство | Источник строк | Как проверено |
|---|---|---|
| `DOCNAME 201` | `VMDB_ST201D` | документ 386: 2 строки, сходятся с проводками |
| `DOCNAME 202` | `VMDB_CMN202D` | та же схема именования витрин |
| `SYSFID 49398` «Регистрация товаров» | `TMDB_EDL_PLDRAFTD` | документ 13: 17 строк с наименованиями и ценами |

Для остальных типов модуль честно пишет, что строки не подключены, и
называет тип. `TMDB_DOCS_PRICE_ADD` рассматривался и отклонён: это не
строки, а один реквизит документа (`SITEPRICE`). `TMDB_CST3A` отклонён:
строки есть, но все поля пустые.

## Запись документов

Вынесена в отдельный файл `writer.py`, чтобы `store.py` оставался
доказуемо read-only — это закреплено тестом.

Разрешена **только для собственных типов** контура SEOForge, диапазон
`DB ID` 60000..60099. Любой другой `SYSFID` отклоняется до обращения
к базе: чужие типы имеют свои настройки проводок, свои обязательные
реквизиты и свою ответственность.

Номер документа берётся из `ID_TMDB_DOCS.NEXTVAL`, документ и его
примечание пишутся одной транзакцией. Проведение — через
`un$gfc.setDoc_GFC` + `setDoc_Correct`, прямых `INSERT` в `TMDB_CM` нет.

**Авторство.** `TMDB_DOCS.USERID` штатно берётся из сессионного
`PARAM_USERID`. Соответствия «пользователь портала → пользователь UNA»
нет, поэтому: если задан `BIRO26WEB_UNA_USERID`, он выставляется через
`SET_ENV`; если нет — автор остаётся пустым, а имя пользователя портала
пишется в примечание. Подставить чужой идентификатор было бы хуже:
документ числился бы за человеком, который его не делал.

**Состояние на 25.08.2026: создать документ в этой базе нельзя.** Учётная
система отбивает запись собственным правилом:

```
ORA-20101: Redactarea documentului este interzisa: 391.
Data documentului (25-AUG-26) inafara perioadei de lucru (-)
```

Рабочий период не задан вообще — в скобках пусто. Это защита самой ERP, и
обходить её нельзя: открытие периода — решение бухгалтерии. Модуль
доводит этот текст до пользователя целиком (код 409), а не прячет за
«ошибкой базы»: причина в нём названа и человек знает, что поправить.

Пока период закрыт, кнопки создания в интерфейсе нет — она бы только
показывала ошибку. API готов и покрыт тестами.

## Почему в списке нет суммы документа

Напрашивающееся `SUM(TMDB_CM.SUMA)` даёт ноль: проводки двойной записи
взаимопогашаются. Проверено на документе 386 — двадцать проводок, сумма 0,
при этом строки документа дают 5100. Общей суммы документа в UNA нет,
а витрина строк у каждого семейства своя, и в списке журнала её не собрать.

Поэтому в списке показывается **число проводок**, а итог по строкам
считается в карточке из тех строк, которые показаны. Неверная сумма на
экране хуже, чем её отсутствие.

## Безопасность фильтра

`SQLFILTER` — сырой SQL из конфигурации, он попадает в `WHERE`. Два правила:

1. фильтр берётся **по номеру журнала из конфигурации**, из запроса приходит
   только число;
2. перед подстановкой фильтр проверяется по белому списку: сравнения
   `SYSFID`/`ID` с числами, скобки, `and`/`or`/`not`/`in`/`between`.
   Всё остальное отклоняется.

Второе правило — на случай испорченной записи в конфигурации: без него она
стала бы инъекцией в бэк-офис. Тесты проверяют оба направления — реальные
фильтры проходят, `union select` и `; drop` отклоняются.

  документов в интерфейсе;
- сопоставление пользователей портала с пользователями UNA, чтобы

## Доступ к базе: пул долгоживущих воркеров (требование)

Правило для каждого модуля, который ходит в ERP, — и для каждой новой задачи,
где такая система проектируется:

1. **Никаких процессов на запрос.** Обращения к Oracle идут через
   `models/biro26_db.py` — пул долгоживущих воркеров (`--serve`). Запуск
   процесса на каждую интерогацию стоил ~1,7 с и был главной причиной
   медленного ответа сайта (замер 26.08.2026).
2. **Чтения** переиспользуют удержанное соединение: они не трогают
   состояние сессии. **Записи** (dml/plsql/script) всегда получают свежее
   соединение — они выставляют контекст сессии (`SET_ENV`: период,
   пользователь), и он не имеет права утекать в следующие запросы.
3. **Один `execute_script` — одна транзакция.** На это опирается запись
   документов в ERP; ломать нельзя.
4. **Таймаут убивает процесс** — сессия Oracle падает и откатывается.
   Это страховка от чужих блокировок, её нельзя заменять «мягким» ожиданием.
5. Выключатель на случай беды: `BIRO26_WORKER_POOL=0` возвращает старый
   транспорт (процесс на запрос). `BIRO26_WORKER_POOL_SIZE` — размер пула.

Ориентиры скорости после перехода: чтение ~0,16 с, запись ~1,1 с,
тестовый прогон 4,6 с. Если новый код снова показывает секунды на чтение —
что-то пошло мимо пула.

## Проекты — папки, и никто никому ничего не затирает (требование)

Правило для всего, что добавляется в портал:

1. **Модуль — это папка `modules/<ключ>/`.** Ядро находит её само, ничего
   дописывать в общий код не нужно. Отсюда и главное свойство: выкладка
   одной ветки не может унести чужие маршруты — они лежат в чужой папке.
2. **Никаких маршрутов в общем `app.py`.** Проверено на своей шкуре:
   27.08.2026 контур переставили на другую ветку, где `robots.txt` и
   `sitemap.xml` в `app.py` не было, — публичный сайт остался с 404 по
   обоим адресам. Теперь они в `modules/seo/`.
3. **Адреса в корне сайта** (`/robots.txt`, `/sitemap.xml`) объявляются
   списком `root_paths` в `module.json`. Ядро подключает их без префикса и
   **отвергает** попытку занять адрес, который уже держит другой модуль:
   молча перекрыть чужое невозможно. Кто что занял — видно в манифесте.
4. **Общие файлы трогает только тот, кто обязан.** Если правка кажется
   неизбежной в `app.py` — сначала проверить, не решается ли она папкой.
5. **Слияние веток не должно решать, чьи маршруты выживут.** Если ответ на
   вопрос «а что будет при выкладке другой ветки» — «пропадёт», значит
   место выбрано неверно.

Проверить, что модуль подключился: `/api/biro26/health` и отчёт ядра —
там видно `loaded`, `skipped`, `failed` с причинами.
