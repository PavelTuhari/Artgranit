# TBControl — материал для генерации презентации (Google NotebookLM)

> Этот документ — исходник для Google NotebookLM (или другого AI-генератора
> презентаций). Он самодостаточен: содержит позиционирование, архитектуру,
> описание всех экранов, модель данных, сценарии и тезисы по слайдам.
> Загрузите файл как источник и попросите сгенерировать презентацию /
> аудио-обзор / брифинг по предложенной структуре слайдов в конце документа.

---

## 1. Что такое TBControl (одним абзацем)

**TBControl** — операционный центр (Operations Center) торговой сети:
единая платформа мониторинга, диагностики и сопровождения магазинов,
POS-касс, Self-Service касс (SCO), Android-устройств, программного
обеспечения Front Office и всей цепочки обмена данными от кассы до
бэк-офиса. Главный принцип: **мониторим не компьютер, а способность
магазина продавать** («Can the store sell?»). Интерфейс выполнен в
стилистике профессиональных NOC-консолей (Cisco DNA Center / Unify):
тёмная тема, health-плитки магазинов, приоритеты P1–P4, единый левый
навигатор доменов.

## 2. Проблема, которую решает система

1. В торговой сети десятки магазинов и сотни устройств: Windows POS,
   Self-Service киоски, Android-терминалы, принтеры, серверы, сеть.
2. Классический мониторинг отвечает «сервер доступен», но не отвечает на
   бизнес-вопрос: **может ли магазин прямо сейчас продавать?**
3. Продажи проходят цепочку: касса (локальная SQLite) → промежуточные
   серверы магазина → центральный сервер → бэк-офис. Данные могут
   застревать на любом звене — и это видно только по жалобам.
4. Версии Front Office на кассах расползаются, обновления не проверяются.
5. Когда происходит сбой, дежурный собирает контекст вручную по кускам —
   долго и с потерями. Внешние AI-ассистенты могли бы диагностировать
   мгновенно, но им нужен полный структурированный контекст.

## 3. Ключевые возможности (карта модулей)

| Модуль | Что делает |
|---|---|
| **Обзор сети** (Executive) | Плитки STORE_HEALTH по каждому магазину (OK / DEGRADED / CRITICAL), доступность POS/SCO/Android, активные P1/P2, открытые инциденты, устаревшее ПО |
| **Мониторинг касс** | По каждой кассе два контура: HW (касса как компьютер: CPU/RAM/Disk) и APP (Front Office внутри: latency, чеки/час, ошибки). Разрезы: сейчас · сегодня · 7 дней · произвольный период. Графики по часам/дням |
| **Магазины** | Реестр с кодами `MD-CHS-001`, maintenance windows |
| **Устройства** | Технический паспорт каждого устройства (serial, asset, ОС, IP/MAC, владелец, критичность), метрики, версия софта, диагностика в один клик |
| **Приложения / Версии ПО** | Реестр приложений с Expected Version и release-каналами (DEV→TEST→PILOT→PRODUCTION); распределение версий по кассам, статусы OK/OUTDATED/FAILED |
| **Изменения / Deploy** | Change-management: `CHG-2026-0812`, окно, rollback-план, деплой на целевые магазины с автоматической verification (process/version/health/…/business) и итогом DEPLOYMENT = SUCCESS/FAILED |
| **Processing центр** | Контроль обмена данными по всей цепочке: касса → серверы магазина (их может быть несколько) → центральный → бэк-офис. Потоки со статусами OK/LAGGING/STALLED/FAIL, отставание, накопленный pending, журнал батчей, повтор передачи |
| **Узлы обработки** | Мониторинг серверов на трёх уровнях: железо, приложение обмена, база данных. Поддержка движков: Oracle, SQLite, MSSQL, MySQL, PostgreSQL |
| **События** | P1–P4 с корреляцией: root cause подавляет downstream-события (нет event storm); закрытие root cause автоматически закрывает подавленные |
| **Инциденты** | Lifecycle new→assigned→diagnosing→resolving→verification→closed, SLA-дедлайны по приоритету, обязательные RCA-поля для P1/P2 |
| **AI-досье** | Исчерпывающий MD-документ о сбое для внешних AI-провайдеров, доступ по секретному токену, автогенерация при P1/P2 |
| **SLA** | Целевые и фактические проценты по сервисам (POS ≥ 99.95% и т.д.) |
| **Журнал аудита** | Append-only журнал всех действий пользователей |

## 4. Архитектура (текстовая схема)

```text
        Агенты на устройствах и серверах
   POS/SCO (Windows)   Android   Узлы (store/central/backoffice)
        │ heartbeat        │ heartbeat        │ heartbeat + flow report
        ▼                  ▼                  ▼
   POST /api/tbc/agent/heartbeat   /api/tbc/nodes/heartbeat
   POST /api/tbc/flows/<id>/report
                     │
                     ▼
      TBControl (Flask, движок Artgranit)
      Oracle ADB — нормализованные таблицы TBC_*
                     │
      ┌──────────────┼─────────────────┐
      ▼              ▼                 ▼
   NOC-консоль   Событийный контур   AI-контур
   (SPA, тёмная  (события → корре-   (MD-досье по токену →
   Cisco-тема)    ляция → инциденты   внешний LLM диагностирует
                  → SLA → RCA)        и чинит по whitelist-API)
```

Цепочка данных продаж (Processing):

```text
POS (SQLite) ──► Промежуточный сервер магазина A/B ──► Центральный сервер ──► Бэк-офис
     flow: sales          flow: sync                        flow: docs
   (каждое звено — поток со статусом, lag, pending и журналом батчей)
```

## 5. Модель данных (Oracle, префикс TBC_)

**Master data:** `TBC_STORES` (магазины + maintenance window),
`TBC_DEVICES` (паспорт устройства + текущие метрики), `TBC_NODES`
(серверы: тип store_srv/central/backoffice, движок БД, три уровня статусов),
`TBC_APPLICATIONS` + `TBC_DEVICE_APPS` (ожидаемые и фактические версии).

**Телеметрия (append-only):** `TBC_METRIC_SAMPLES` (time series по кассам,
scope hw/app), `TBC_HEALTH_CHECKS` (диагностика компонентов),
`TBC_FLOW_LOG` (батчи передач), `TBC_EVENT_LOG` (аудит).

**Операционные:** `TBC_EVENTS` (P1–P4, корреляция через PARENT_EVENT_ID),
`TBC_INCIDENTS` (RCA), `TBC_CHANGES` + `TBC_DEPLOY_CHECKS` (деплой),
`TBC_FLOWS` (потоки обмена), `TBC_SLA_TARGETS`, `TBC_AI_DOSSIERS`
(MD-CLOB + ACCESS_TOKEN).

**Представления:** V_TBC_STORE_HEALTH (расчёт OK/DEGRADED/CRITICAL),
V_TBC_DASHBOARD_STATS, V_TBC_DEVICES, V_TBC_VERSIONS, V_TBC_EVENTS,
V_TBC_INCIDENTS, V_TBC_CHANGES, V_TBC_NODES, V_TBC_FLOWS, V_TBC_PROC_STATS.

## 6. Сценарий 1: «Магазин не продаёт» (корреляция)

1. Роутер магазина 003 перестаёт отвечать → событие **P1** «Store network
   unavailable».
2. POS-01 и POS-02 тоже недоступны, но их события автоматически получают
   статус **suppressed** с ссылкой на root cause — нет шторма алертов.
3. Из P1 в один клик (или автоматически) создаётся инцидент
   `INC-2026-10452`, назначается группе Customer IT, SLA-дедлайн 2 часа.
4. Одновременно генерируется **AI-досье** `DSR-2026-…` со всем контекстом.
5. После восстановления сети resolve root-cause события автоматически
   закрывает все подавленные события. STORE_HEALTH возвращается в OK.

## 7. Сценарий 2: «Продажи не дошли до бэк-офиса» (Processing)

1. Панель Processing показывает: поток «Центральный → Бэк-офис» в статусе
   **FAIL** (ошибка `ORA-02291 … batch B-88412 rejected`), 21 500 строк
   pending, lag 130 минут.
2. Журнал батчей потока показывает: предыдущий батч B-88411 прошёл, текущий
   отбит по integrity constraint.
3. Оператор (или AI-агент по досье) устраняет причину и жмёт «↻ Повторить
   передачу» — pending уходит, поток возвращается в OK.
4. Аналогично видно проблемы нижних звеньев: «POS-03 → сервер магазина»
   LAGGING из-за `SQLite locked`, «SCO-02 → сервер» STALLED (касса offline).

## 8. Сценарий 3: AI-диагностика по досье

1. При сбое генерируется MD-документ: описание сбоя, паспорт устройства/узла,
   метрики NOW + телеметрия за 24 часа, health checks, версии ПО, потоки
   обмена и журнал батчей, STORE_HEALTH магазина, соседние открытые события,
   рекомендуемый порядок диагностики.
2. Внешний AI-провайдер читает его по URL
   `GET /api/tbc/ai/dossier/DSR-2026-000123.md?token=<ACCESS_TOKEN>` —
   без интерактивного логина, по секретному per-документ токену.
3. Credentials для активных действий в досье **не включаются** — сервисный
   доступ выдаётся отдельно (Secret Store). AI может через whitelist-API:
   запустить диагностику, повторить передачу потока, закрыть событие,
   заполнить RCA-поля инцидента. Запрещено: менять финансовые данные,
   production-конфигурацию, security controls.
4. Каждое чтение досье учитывается (счётчик, статус new→sent→analyzed→resolved).

## 9. Сценарий 4: контролируемый деплой Front Office

1. Создаётся изменение `CHG-2026-0812`: Front Office 7.4.13, rollback 7.4.12,
   канал PILOT, окно 02:00–04:00, магазины 001–002.
2. Deploy обновляет версии на целевых кассах и прогоняет verification:
   process → version → health → database → api → sync → peripheral →
   business transaction.
3. Итог: DEPLOYMENT = SUCCESS (или FAILED с журналом по устройствам).
   Успешный PRODUCTION-деплой автоматически поднимает Expected Version —
   отставшие кассы сразу подсвечиваются как OUTDATED.
4. Кнопка rollback возвращает предыдущую версию на весь scope.

## 10. Цифры демо-стенда

- 4 магазина (Кишинёв ×3, Бельцы ×1), 16 устройств: 8 POS, 2 SCO,
  4 Android, сервер, роутер.
- 7 узлов обработки: 5 серверов магазинов (MySQL, PostgreSQL, MSSQL,
  SQLite), центральный (Oracle 19c), бэк-офис (PostgreSQL 16).
- 17 потоков обмена, ~2 700 сэмплов телеметрии за 7 дней.
- Демо-сбои: сеть магазина 003 (P1 + 2 suppressed), SQLite lock на POS-03,
  STALLED-потоки офлайн-магазина, FAIL «центральный → бэк-офис»,
  деградация промежуточного сервера B (диск 94%).

## 11. Технологии

- **Backend:** Python / Flask (движок Artgranit), Oracle Autonomous DB,
  нормализованная схема с префиксом `TBC_` (26 таблиц, 10 представлений).
- **UI:** самодостаточный SPA (один HTML, без внешних библиотек), тёмная
  NOC-тема Cisco-стиля, SVG-графики, автообновление дашборда каждые 30 с.
- **Интеграции:** heartbeat-API для Zabbix Agent 2 / Android Monitoring
  Agent с автоregистрацией устройств по коду `MD-CHS-001-AND-01`;
  flow-report API для агентов обмена; token-доступ для внешних AI.
- **Деплой:** локально + production (`https://nufarul.eminescu.md`),
  DDL через `deploy_oracle_objects.py`.

## 13. Предлагаемая структура презентации (для NotebookLM)

1. **Титул** — TBControl: Operations Center торговой сети. «Мы мониторим
   не компьютеры, а способность магазина продавать».
2. **Проблема** — слепые зоны классического мониторинга (раздел 2).
3. **Общая картина** — Executive-дашборд: STORE_HEALTH-плитки, P1/P2 (раздел 3).
4. **Мониторинг касс** — два контура HW/APP, разрезы сейчас/день/неделя/период (раздел 3).
5. **Processing центр** — цепочка SQLite → серверы магазина → центр →
   бэк-офис, статусы потоков, pending, журнал батчей (разделы 4, 7).
6. **Узлы и базы данных** — три уровня контроля, пять движков БД (раздел 3).
7. **События и корреляция** — root cause, подавление шторма (раздел 6).
8. **Инциденты и SLA** — lifecycle, RCA, дедлайны (раздел 3).
9. **Управление версиями и деплой** — expected vs current, verification,
   rollback (раздел 9).
10. **AI-досье** — полный контекст сбоя для LLM, token-доступ, whitelist
    действий (раздел 8).
11. **Технологии и архитектура** — Flask + Oracle + NOC-SPA (разделы 4, 11).
12. **Демо-стенд в цифрах** (раздел 10).
13. **Дорожная карта** — реальные Zabbix-webhook'и, авто-remediation,
    предиктивный мониторинг (Level 5 модели зрелости ТЗ).
