# OTRS: дневные отчёты уходят не полностью — разбор и исправление

**Дата разбора:** 25.08.2026
**Жалоба пользователя:** «Este o problema la expedierea rapoartelor zilnice. Deși timpul este notat, o parte din rapoarte nu vin.»

## Как устроена рассылка

1. Отчёт формируется в Oracle (`orange.una.md:4024/cloudbd.world`, 11g) и кладётся
   в очередь `OTRS.UN9MAIL_MSG` процедурой `fill_un9mail_msg` — **отсюда и берётся
   «время в отчёте»**, оно фиксируется до отправки.
2. Затем вызывается `send_email_api_php(nrmsg)`, которая через `UTL_HTTP` дёргает
   `http://api.unisim-soft.com/email_util/send_from_un9mail_msg.php?nr_msg=…`
   Ответ PHP `OK:SEND` → `STATUS=2` (отправлено), иначе → `STATUS=1` + `ERR_MSG`.
3. Сервер 192.168.0.51 (`otrs`) в отправке **не участвует** — там нет ни cron,
   ни скриптов рассылки. Вся логика в БД.

Исходник: `unisimNginx/plsql_export_correct_20260102_192722/PKG_TICKETS_MAIL_BODY.sql`,
строки 817–884.

## Три дефекта, все в одной процедуре

### 1. Переполнение буфера — 165 сбоев из 210 за 90 дней

```sql
v_req_result varchar2(4000);   -- ← объявление
...
loop
  utl_http.read_line(l_resp, buffer);
  v_req_result := v_req_result || buffer;   -- ← накапливается без ограничения
end loop;
```

Ответ PHP копится в `VARCHAR2(4000)`. Как только он перерастает 4000 байт —
`ORA-06502: буфер символьных строк слишком маленький`, письмо остаётся `STATUS=1`.

Доказательство по данным за 90 дней:

| Размер тела письма | Ушло | Застряло |
|---|---|---|
| < 4000 байт | 5214 | 145 |
| 4000–8000 | **0** | **72** |
| 8000–16000 | **0** | **17** |

Ни одно письмо крупнее 4000 байт не ушло ни разу. По дневным отчётам: средний
размер успешных — 1235 байт, застрявших — 4104. **Отчёт не приходит ровно тогда,
когда у сотрудника за день много строк работы** — именно это и заметил пользователь.

### 2. Утечка HTTP-дескрипторов — 18 сбоев

В обработчике `WHEN OTHERS` нет `utl_http.end_response`. Каждый сбой оставляет
открытый ответ; лимит одновременных запросов — 5, после чего всё падает с
`ORA-29270: чрезмерное число запросов`. То есть первый сбой тянет за собой
следующие — сбои идут сериями.

### 3. Нет повторной отправки — 6613 писем в очереди с 25.02.2024

При неудаче `STATUS` остаётся `1` и никто больше это письмо не трогает. Плюс
`SENT_DATE` затирается `SYSDATE` при каждой неудаче, поэтому исходное время
постановки в очередь потеряно. К этому же классу относятся `HTTP 508`
(39 сбоев) — шлюз режет пакетную рассылку 08:00, когда за 50 секунд уходит ~40 писем.

## Исправление

Готовый текст процедуры: [`send_email_api_php_fixed.sql`](send_email_api_php_fixed.sql).
Правки: `CLOB` вместо `VARCHAR2(4000)`, `end_response` в обработчике исключений,
3 попытки с паузой 2 и 4 секунды, `STATUS=3` как окончательный отказ,
`SENT_DATE` не затирается при неудаче.

**Условия установки:**

- ставить в `PKG_TICKETS_MAIL` (схема `TICKETS`) и в `PKG_TICKET_MAIL` (схема `OTRS`) —
  это две копии одного кода, отличаются параметром `schema=` в URL;
- нужен `GRANT EXECUTE ON DBMS_LOCK` (для паузы между попытками); если его не дадут —
  заменить `DBMS_LOCK.SLEEP` на короткий цикл ожидания;
- у учётки `haruzdar2018`, под которой велась диагностика, прав на изменение
  этих пакетов нет — установку выполняет владелец схемы.

**Что делать с 6613 застрявшими письмами:** массовый сброс в `STATUS=1` после
установки исправления приведёт к разовой рассылке за два года — почти наверняка
не нужно. Разумнее пометить всё старше 30 дней как `STATUS=3` (архив), а
переотправить только последние дни. Это изменение боевых данных, делается
только по отдельному решению владельца.

### Ещё одна найденная ловушка

`_call_worker(auth, sql, N)` — третий аргумент это **таймаут в секундах**,
а не число строк. С `N=5` отправка с тремя попытками и паузами 2+4 с рвётся
по таймауту, хотя на стороне БД успевает пройти (процедура автономная и
коммитит сама). В `install_fix.py` таймаут поднят до 120 с.

### Осталось сделать

1. Догнать 80 писем OTRS: `venv/bin/python docs/OTRS/install_fix.py --only otrs --retry-all`
2. Решить по 722 письмам TICKETS — это уведомления внешним клиентам за
   последние 30 дней, массовая переотправка может их удивить.
3. Тот же дефект живёт в схемах-двойниках: таблица `UN9MAIL_MSG` заведена
   примерно в 150 схемах БД `cloudbd` (`ARTGRANIT`, `NUFARUL`, `OFFICEPLUS`,
   `DORIMAX`, `GARABTA` и др.). Где рассылка идёт тем же `send_email_api_php`,
   письма крупнее 4000 байт теряются точно так же.

## Пункт 3: тот же дефект в других схемах (26.08.2026)

Скан всех 143 схем с очередью `UN9MAIL_MSG` (`docs/OTRS/scan_schemas.py`,
`docs/OTRS/check_access.py`) выявил тот же дефектный буфер `varchar2(4000)`
в рассыльщиках ещё нескольких схем. Правка — минимальная и универсальная:
`varchar2(4000)` → `varchar2(32767)` в объявлениях `v_req_result` и `buffer`
(скрипт `docs/OTRS/patch_buffer.py`), покрывает любое реальное письмо.

| Схема | Пакет | Застряло / >4КБ | Статус |
|---|---|---|---|
| OTRS | `PKG_TICKET_MAIL` | — | ✅ полная правка (CLOB+повторы) + очередь отправлена |
| TICKETS | `PKG_TICKETS_MAIL` | — | ✅ полная правка + застрявшие удалены (выгружены в zip) |
| GARABTA | `PKG_TICKETS_MAIL` | 71 / 0 | ✅ буфер 32767, VALID |
| VALORENERGY | `PKG_MAIL_UTL` | 0 / 0 | ✅ буфер 32767, VALID (профилактика) |
| GARABTA_CONT | `PKG_MAIL_UTL` | 0 / 0 | ⚠ пакет был INVALID и ДО правки (нет `API_MAIL_USERNAME`/`API_MAIL_PASSWORD` в spec) — оставлен оригинал, рассылка там не работает по другой причине |
| **UNI** | `PKG_MAIL_UTIL` | **713 / 607** | ⏳ нужен пароль (≠ имя схемы) |
| DORIMAX | `PKG_MAIL_UTL` | 54 / 0 | ⏳ нужен пароль (≠ имя схемы) |
| HELIOS24 | `PKG_MAIL_UTL` | 0 / 0 | ⏳ нужен пароль (≠ имя схемы) |

Мелкие FLORENTINO/LACOSTE/LEALEA/NLCOLLECTION/SORINST/GARAA (1–5 писем,
0 крупных) — **не этот дефект**: процедуры `send_email_api_php` у них нет,
письма застряли по другим причинам, не трогались.

Откат любой схемы: `venv/bin/python docs/OTRS/patch_buffer.py <схема> <ПАКЕТ> --rollback`
(копии оригиналов в `docs/OTRS/backup/`).

Также к пакетам с тем же паттерном `v_req_result varchar2(4000)`, но в ДРУГИХ
процедурах (не почтовых, а `PKG_GLOVO`/`PKG_SITE_UTIL` — интеграции Glovo/сайт),
буфер тоже мал; они шлют не в `UN9MAIL_MSG`, поэтому в этот разбор не входят,
но при желании чинятся тем же `patch_buffer.py`.
