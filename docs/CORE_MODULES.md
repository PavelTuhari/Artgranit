# Ядро портала: как подключается модуль

## Зачем это появилось

Раньше модуль добавлялся правкой `app.py`. Тринадцать модулей — девять тысяч
строк в одном файле, и каждый новый модуль означал:

- конфликт слияния с любой другой веткой, которая тоже добавляла модуль;
- риск задеть чужие маршруты или перехватить чужой адрес;
- невозможность вынести модуль целиком — его код был размазан по
  `app.py`, `controllers/`, `models/`, `templates/`, `sql/`, `scripts/`.

Правило теперь простое: **общее не трогаем**. Модуль подключается сам,
ядро следит, чтобы модули не мешали друг другу.

## Контракт

Каталог `modules/<ключ>/`:

| Файл | Обязателен | Роль |
|---|---|---|
| `__init__.py` | да, если у модуля есть страницы | экспортирует `blueprint` |
| `module.json` | нет | манифест меню: название на трёх языках, иконка, порядок |

Минимальный модуль:

```python
# modules/mymodule/__init__.py
from flask import Blueprint

blueprint = Blueprint("mymodule", __name__, template_folder="templates")

from modules.mymodule import routes  # noqa: E402,F401
```

```python
# modules/mymodule/routes.py
from modules.mymodule import blueprint

@blueprint.route("/")
def page():
    return "привет"
```

Всё. Страница откроется по `/UNA.md/orasldev/mymodule/`, модуль появится
в меню. Ни одной правки в общем коде.

**Адреса пишутся без префикса модуля** — его подставляет ядро. Так модуль
не может промахнуться мимо своей области, даже если ошибётся в пути.

## Что ядро гарантирует

| Гарантия | Как обеспечена |
|---|---|
| Маршруты модуля лежат под `/UNA.md/orasldev/<ключ>` | префикс задаёт ядро при регистрации blueprint'а — это устройство, а не договорённость |
| Модули не сталкиваются именами | имя blueprint обязано совпадать с ключом, endpoint'ы получают вид `<ключ>.<функция>` |
| Обойти префикс нечем | на время импорта модуля ядро закрывает ему `app.add_url_rule` и `app.register_blueprint` |
| Сбой модуля не роняет портал | битый импорт, отсутствующий `blueprint`, неверное имя — модуль пропускается с записью в отчёт |
| Повтор ключа отвергается | второй модуль с тем же ключом не подключается |

Почему запрет, а не проверка постфактум: Werkzeug не умеет удалять уже
добавленные маршруты. Если бы модуль успел повесить адрес на приложение,
«заметить и откатить» было бы не откатить. Поэтому вход закрыт заранее.

## Отчёт о загрузке

```python
app.extensions["module_loader"].as_dict()
# {"loaded": ["seoforge"], "skipped": {"biro26": "нет пакета модуля..."}, "failed": {}}
```

Без отчёта сбой модуля выглядел бы как «страница просто не открывается».

## Совместимость со старыми модулями

Модуль без `__init__.py` ядро пропускает молча: у него есть только манифест
меню, а страницы живут в `app.py` по старому образцу. Так сейчас устроены
`aei`, `agro`, `biro26`, `colass`, `credit`, `decor`, `digi`, `nufarul`,
`planograms`, `sda`, `servouts26`, `tbcontrol` — они продолжают работать
без единой правки.

Переносить их можно по одному, когда до них дойдут руки: ядро не требует
одномоментной миграции.

## Образец переноса: SEOForge

`modules/seoforge/` — первый модуль нового образца, полностью
самодостаточный:

```
modules/seoforge/
  __init__.py            blueprint
  routes.py              22 маршрута, адреса без префикса
  controller.py          валидация, коды ответов
  store.py               SQL через thick-воркер ERP
  csv_format.py          чистый разбор CSV
  templates/seoforge.html
  sql/113..116_yseo_*.sql контур YSEO_*
  scripts/               установщики и smoke
  module.json
```

В общем коде от модуля не осталось ничего: `app.py` его не упоминает,
`deploy_oracle_objects.py` тоже. Это закреплено тестами
`test_module_leaves_nothing_in_the_shared_app` и
`test_shared_deploy_script_is_untouched_by_the_module`.

## Что ядро занимает в общем коде

Ровно пять строк в `app.py`:

```python
from core import load_modules
...
load_modules(app)
```

Это и есть вся посадка ядра. Дальше модули добавляются без правок.

## Границы модулей за пределами кода

Ядро отвечает за маршруты и имена. Остальные пересечения модуль обязан
развести сам, и это стоит проверять на ревью:

- **Oracle:** свой префикс объектов (`YSEO_`, `DECOR_`, `CRED_`, `DIGI_`).
- **Конфигурация UNA:** свой диапазон `DB ID` (у SEOForge — `60000..60099`).
- **Файлы:** всё внутри `modules/<ключ>/`.

## Доступ к базе: пул долгоживущих воркеров (требование)

Правило для каждого модуля, который ходит в ERP, — и для каждой новой задачи,
где такая система проектируется:

1. **Никаких процессов на запрос.** Обращения к Oracle идут через
   `models/biro26_db.py` — пул долгоживущих воркеров (`--serve`). Запуск
   процесса на каждую интерогацию стоил ~1,7 с и был главной причиной
   медленного ответа сайта (замер 26.08.2026).
2. **Чтения** переиспользуют удержанное соединение: они не трогают
   состояние сессии. **Записи** (dml/plsql/script) всегда получают свежее
   соединение — они выставляют контекст сессии (`SET_ENV`: период,
   пользователь), и он не имеет права утекать в следующие запросы.
3. **Один `execute_script` — одна транзакция.** На это опирается запись
   документов в ERP; ломать нельзя.
4. **Таймаут убивает процесс** — сессия Oracle падает и откатывается.
   Это страховка от чужих блокировок, её нельзя заменять «мягким» ожиданием.
5. Выключатель на случай беды: `BIRO26_WORKER_POOL=0` возвращает старый
   транспорт (процесс на запрос). `BIRO26_WORKER_POOL_SIZE` — размер пула.

Ориентиры скорости после перехода: чтение ~0,16 с, запись ~1,1 с,
тестовый прогон 4,6 с. Если новый код снова показывает секунды на чтение —
что-то пошло мимо пула.

## Тесты

`tests/test_core_module_loader.py` — тринадцать тестов, и проверяют они не
«загрузчик что-то загрузил», а сами обещания: два модуля с одинаково
названными функциями, попытка занять чужой адрес, битый модуль рядом со
здоровым.
