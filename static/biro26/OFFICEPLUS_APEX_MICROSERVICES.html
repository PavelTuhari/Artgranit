01

Цель и инварианты

Задача (как сформулирована оператором):

  • добавить microservices на Always Free Ubuntu;
  • не сломать WordPress (officeplus.md) и продающий магазин Biro26;
  • товары, группы, клиенты и прочие справочники — копия для внешних систем;
  • копия данных WordPress → Always Free APEX БД dbOfficePlus;
  • внешние программы должны уметь делать полный backup справочников;
  • пароль ADB — в keychain; пользователь APEX OPVIEW — смена пароля при первом входе.

Инварианты production

Не трогать: Hestia vhost WordPress, public_html, MariaDB write-операции, порт Flask/gunicorn 127.0.0.1:8000, nginx proxy shop/backoffice, SSL certbot пути.

Проверка после любых правок: curl -I https://officeplus.md/ → 200; shop API /api/biro26/shop/products?limit=1 → success.

Архитектура

WordPress (MariaDB wordpress) ──READ──┐ Biro26 shop API :8000 (ERP 11g) ──READ──┼──► op-micro (cron + API :8010) │ WRITE via ORDS SQL ▼ ADB APEX Always Free dbOfficePlus ADMIN.OP_* + OPVIEW views ORDS UI /opview-ui/ + JSON /ords/opview/v_* APEX workspace OFFICEPLUS (user OPVIEW)

Источник истины для товаров/групп — ERP OfficePlus / Biro26 (не WooCommerce). WordPress — витрина (iframe магазина) + страницы/контент сайта. APEX — зеркало для отчётов, backup и внешних программ.

Почему ORDS, а не wallet

OCI отклоняет generate-wallet для APEX Application Development: нужен upgrade workload → ATP. Конвертация free APEX→OLTP API тоже запрещена. Поэтому слой op-micro/db_apex.py ходит в БД через ORDS SQL REST.

Схема зеркала ADMIN.OP_*

Префикс OP_ — только копии. ERP 11g и WordPress MariaDB не изменяются sync-ом.

ОбъектНазначение
OP_PRODUCTSТовары (cod, barcode, name, brand, category, price, payload_json…)
OP_GROUPSГруппы / дерево категорий
OP_CLIENTSКлиенты (если настроен источник clients API)
OP_WP_POSTSЗеркало wp_posts (без revision)
OP_WP_TERMSТермы WP
OP_WP_USERSПользователи WP без password hash
OP_WP_OPTIONSОпции WP (без salts/keys)
OP_SYNC_RUNЖурнал прогонов sync
OP_V_BACKUP_METAСчётчики + last_ok_sync

DDL: op-micro/sql/01_op_schema.sql · накат: python apply_schema.py (ORDS).

Объём каталога shop

Публичный API /api/biro26/shop/products отдаёт total ≈ 156 836 позиций (offset работает). Построчный ORDS MERGE для полного каталога долгий — для full load нужен batch (в roadmap). WordPress mirror (posts/users/terms/options) уже успешно синхронизировался (~45 постов без revision).

ORA-12705 и native APEX App

Вызов wwv_flow_imp.create_app_from_query из ORDS/Scheduler на этом Always Free APEX падает с ORA-12705 (NLS). Workspace при этом полноценный.

В браузере: APEX Builder → Create App from Tables → выбрать V_* (2–3 минуты). UI просмотра уже есть через ORDS HTML (ниже).

Вход в APEX Builder:

  1. URL: ords/apex
  2. Workspace: OFFICEPLUS
  3. User: OPVIEW
  4. Password: временный из keychain → система потребует свой новый пароль

Полный backup справочников (внешние программы)

  1. Рекомендуется: ORDS AutoREST JSON по views v_products, v_groups, v_clients + pagination ?limit=&offset=.
  2. Агрегат: GET http://127.0.0.1:8010/api/v1/backup/full с X-API-Key (tunnel/SSH).
  3. UI ручной: страницы opview-ui (не для автоматизации dump).
  4. Мета: OP_V_BACKUP_META / v_dashboard.
# пример SSH tunnel + full dump
ssh -L 8010:127.0.0.1:8010 ubuntu@89.168.115.20
curl -H "X-API-Key: $OP_BACKUP_API_KEY" \
  http://127.0.0.1:8010/api/v1/backup/full -o officeplus_catalogs_full.json

Что нельзя ломать

КомпонентПравило
WordPressТолько read для sync; content publish — wp-cli точечно, не full DB overwrite
artgranit.service :8000Не менять port/workers без синхронного nginx; restart только systemd
nginx conf_biro26Не удалять proxy shop/backoffice/static/UNA.md
ERP officeplus@11gMirror только читает shop API; не DDL на live ERP из op-micro
Reboot VMТолько по явной команде владельца (Always Free fragile RAM)
